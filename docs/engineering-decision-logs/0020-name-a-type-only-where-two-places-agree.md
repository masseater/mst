# 0019. 型に名前を付けるのは 2 箇所が合意するときだけにする

## 状況

[EDR 0013](./0013-draw-the-duplication-line-at-decidability.md) は、重複の検出を決定的に判定できるものだけに限ると決めた。そのとき候補から外したものが 3 つあり、「一度しか使われないヘルパー」はそのうちの 1 つだった。判定は決定的にできるが規範として成立しない、というのが外した理由である。

根拠は実測だった。非 export のトップレベル宣言 204 件のうち 140 件が 1 回しか参照されておらず、その大半は長い手続きを名前付きの段に割る書き方である。直すべき状態ではないものを 7 割方報告するルールは、既定でエラーにして抑制の口を持たないこのリポジトリの運用に乗らない。

その後、単一使用の型について同じ判断を引き継ぐべきかを問われた。0013 が数えたのは宣言全体であって、型と値を分けていない。

## 決定

型に限って、1 回以下しか参照されない宣言を lint で止める。0013 の判断を型について覆す。

分けた根拠は、名前が何を買っているかが型と値で違うことである。

値のヘルパーは、名前を付けることで長い手続きを段に割る。名前が 1 回しか使われていなくても、その 1 回の呼び出し位置には「ここで何が起きるか」という要約が残り、本体の手続きは呼び出し元から消える。読み手が得るものがある。

型エイリアスは実行時に何も起こさない。段に割る手続きを持たない。1 箇所からしか参照されない型別名が残すのは間接参照だけで、形を知りたい読み手は宣言まで移動して戻ってくることになる。さらに名前は「他でも使われているはずだ」という誤った合図を出し、変更するときに存在しない影響範囲を探させる。

型に名前を付ける理由は、2 箇所以上がその形について合意する必要があることである。合意する相手がいなければ、名前は付けない。

判定の範囲は非 export のトップレベル型宣言に限る。export された型の参照を数えるにはリポジトリ全体で import を解決する必要があり、名前だけを頼りに数えると別ファイルの同名の型と混ざる。実際にこのリポジトリには `ParsedSource` が別の構造で 2 箇所にある。0013 が引いた「決定的に判定できるものだけ」の線をここでも引いた。

あわせて、名前も本体も一致する宣言を統合させるルールを入れた。0013 が載せた `no-duplicated-body` は本体が AST ノード 8 個に満たない宣言を偶然の一致として素通りさせるが、名前まで一致していれば偶然ではない。所有権の問題であって語彙の問題ではないので、canonical-values ではなく重複検出の索引を共有する 2 本目のルールとして置いた。

## 帰結

- 非 export のトップレベル型宣言 34 件のうち 16 件（47%）が該当し、すべて使用箇所に展開した。0013 が値について測った 7 割に比べれば低いが、それでも半数に近い
- export されたトップレベル型宣言 37 件のうち 5 件は、どのファイルからも import されていなかった。1 件は 2 本のルールが共有する場所へ移し、3 件は export を外して展開し、1 件は参照が皆無だったので消した
- export を付けると単一使用の型ルールの対象から外れる。これは検出の穴として残る。塞ぐにはリポジトリ全体の型参照索引が要り、その索引は名前の衝突を import 解決で分ける必要がある。穴があることをルールの文書に書き、回避策として禁じた
- 名前も本体も一致する組は 3 つで、いずれも本体が AST ノード 1 個の単一のスカラーだった。`no-duplicated-body` の下限がこれを設計どおり素通りさせていたことが、実測で確かめられた
- 型宣言を重複検出の索引に入れたが、名前も本体も一致する型は 0 件、本体だけ一致する型も 0 件だった。`no-duplicated-body` の報告集合は変わっていない
