# 0004. tsconfig プリセットは dont-review-it のサブパス export として配る

- ステータス: Accepted
- 日付: 2026-08-10

## 文脈

このリポジトリの `tsconfig.json` は 5 つあり、`packages/utils` / `packages/dont-review-it` / `packages/lint-rule-authoring` の 3 つは 15 項目が完全に同一だった。`vp create vite:monorepo` が各ワークスペースに同じ内容を配ったものが、そのまま置かれていた。

写しであることを保っているものは何も無く、食い違ったことを報告するものも無い。実際に `strict` はこの 3 つにしか入っておらず、ルートと `apps/website` では効いていなかった。

集約するだけでは同じ状態に戻る。次にワークスペースを足す人はテンプレートが吐いた `tsconfig.json` をそのまま置き、それは動いてしまうため、レビューで指摘されるまで気づかれない。したがって「集約する」ことと「集約から外れたら報告する」ことは 1 組で必要になる。

## 決定

プリセットを `@mst/dont-review-it` のサブパス export（`./tsconfig/*`）として配り、集約から外れた `tsconfig.json` を報告するルール `no-standalone-tsconfig--extend-shared-preset` を同じパッケージに置く。

### 独立パッケージにしない

`dont-review-it` は「書き方の選択をレビューの議題にしない」ための強制装置を集めた場所であり、コンパイラオプションの選択はその一部である。プリセットと、その使用を強制するルールが同じパッケージにあることで、依存を 1 本入れれば両方が同時に効く。プリセットだけ入れてルールを入れない状態を作れないことが、この配置の目的にあたる。

サブパス export を使うのは、`tsconfig.json` の `extends` が指すのが JSON ファイルであり、JS の export では表現できないため。`plugin`（oxlint が specifier で読む）に続く 2 つ目の例外になる。

### プリセットは動く場所で 3 層に割る

土台・ライブラリ向け・アプリ向けの 3 本を置き、土台をライブラリ向けとアプリ向けの双方が extends する。

土台に入るのは動く場所によらないもの（モジュール検出の強制、成果物を出さないこと、ライブラリの型チェックを省くこと、TypeScript 拡張子の import、型のみの import の明示、未使用ローカルの検出、`strict`、`target`）。ライブラリ向けは Node の解決規則・Node の型・宣言ファイルの生成・JSON の import を足し、アプリ向けはバンドラの解決規則・DOM の型・Vite のクライアント型・アセット拡張子の import・未使用引数と switch の fallthrough の検出を足す。

土台を直接 extends することは許さない。土台は動く場所を決めていないため、そのワークスペースだけ Node 向けかブラウザ向けかが未定になる。

### 参照の書き方は 2 通りを許す

`packages/dont-review-it` は自分のパッケージ名で自分の export を解決できる。`tsc --showConfig` で実測し、実効設定が変更前と一致することを確認した。したがって自己参照を含め、依存を張れるワークスペースはすべてパッケージ名で指す。

`packages/lint-rule-authoring` だけは依存の向きが逆で（`dont-review-it` が `lint-rule-authoring` に依存している）、パッケージ名では解決できない。ここだけ相対パスで指す。指している先は同じファイルなので、共有されているという事実は変わらない。

ルールが許可する指定は、末尾一致で判定する文字列の一覧としてルールの外から渡す。パッケージ名の指定も相対パスの指定も `dont-review-it/tsconfig/library.json` で終わるので、一覧はこの 1 本で両方を覆う。一覧に置く文字列にはプリセットを所有するパッケージの名前を含める。含めないと、同じ名前のファイルを持つ別のパッケージのプリセットも通ってしまう。

### 判定は tsconfig の中身ではなく extends だけを見る

ルールが読むのは `extends` の指定だけで、`compilerOptions` の中身は見ない。プリセットを extends したうえで一部を上書きしていても報告しない。何を上書きしてよいかはルールが決めることではなく、上書きが積み上がったかどうかはレビューで見える。

oxlint が読むのは JS と TS のファイルなので、lint 対象のファイルから上へ辿って最初に見つかる `tsconfig.json` を判定の対象にする。報告は違反している `tsconfig.json` に属するファイルすべてに出す。先頭の 1 ファイルに絞ると、どのファイルに出るかが lint の実行順で決まり、実行するたびに報告位置が動く。

`tsconfig.json` は JSONC として読む。テンプレートが生成する `tsconfig.json` はコメント付きで出てくるため、JSON として読むとルールが最も効いてほしい相手を素通しする。JSONC の読み取りは `jsonc-parser` に任せる。

### lib と target は実行環境ではなく esnext に置く

`lib` を `esnext` に統一し、あわせて `devEngines.runtime` を Node 26.7.0、`engines.node` を `>=26.0.0` に上げた。

`lib` は「型として使ってよい API の集合」を決めるので、実行環境に無い API まで型が通ると、型検査を通ったコードが実行時に落ちる。テンプレートが配っていた `es2023` は Node にとって狭すぎ（`Set.prototype.union` / Iterator ヘルパ / `RegExp.escape` / `Promise.try` / `Float16Array` はいずれも Node 24 で動く）、`esnext` は Node 24 にとって広すぎた（`Temporal` が型で通るが Node 24 に無い）。Node 26.7.0 では `Temporal` が実装済みであることを実測で確認している。

この選択には穴が残る。`esnext` は TypeScript のバージョンが決める集合であって実行環境が決める集合ではないため、常にランタイムより先行する。Node 26.7.0 の時点でも `Symbol.metadata` は `lib: esnext` が型として通すが実装されていない。`typescript` を上げるたびに型の許容範囲だけが静かに広がる性質も同じところから来る。実行環境に合わせるなら `lib` はライブラリ向けとアプリ向けで別々の値を持つべきで、その形にはしていない。

## 影響

コンパイラオプションを変える議論は、プリセットを直す 1 か所に集まる。ワークスペースを足す人がテンプレートの `tsconfig.json` をそのまま置くと lint が止まる。

`strict` が全ワークスペースに効くようになった。ルートは `include` が無いために全ワークスペースのソースを巻き込んでいたので `*.ts` に絞り、型検査の対象がそれによって減っていないことを確認した。

ルートがライブラリ向けプリセットを取り込んだことで `types: ["node"]` を持つようになり、ルートに `@types/node` の直接依存が要るようになった。

`@mst/dont-review-it` は `jsonc-parser` を実行時依存として持つ。

## 検討して採らなかった案

**プリセットを独立パッケージに切り出す。** プリセットとルールが別々に入る状態を作れてしまう。プリセットだけ入れた利用者はルールの強制を受けず、集約から外れても報告されない。両者が 1 つの依存で同時に入ることがこの設計の要点なので、切り離すとその要点が失われる。

**ルールが `compilerOptions` の中身を比較して、プリセットとの差分を報告する。** `extends` を書かずに同じ内容を書いたワークスペースも捕まえられるが、正当な上書きと写しの区別がルールには付かない。区別を付けようとすると、どのオプションの上書きを許すかという一覧がルールの側に生まれ、プリセットとその一覧という 2 つの真実ができる。

**`tsconfig.json` を検査対象のファイルとして直接 lint する。** oxlint が読むのは JS と TS なので、この形は取れない。JSON を読む別の検証エントリポイントを立てる案もあるが、`vp check` 1 本で完結しなくなる。

**ワークスペースごとに専用のプリセットを用意し、一覧に足していく。** プリセットの数がワークスペースの数に追いつくと、集約したことにならない。プリセットが増えてよいのは動く場所が増えたときだけである。
