# 0015. 失敗が値に化けてよい範囲を決める

- ステータス: Accepted
- 日付: 2026-08-10

## 文脈

`dont-review-it` の走査系は、失敗を受け取らずに捨てる形を 11 箇所に持っていた。7 箇所は es-toolkit の `attempt` の分解で失敗側を受け取らない形（`const [, x] = attempt(...)` と `attempt(...)[1]`）、3 箇所は束縛を持たない `catch`、1 箇所は同じ形が別セッションの作業で新しく入ったものである。

捨てた結果はどれも「失敗を、その失敗自身の不在を表す値に置き換える」ことだった。読めないファイルは `null` になり、壊れた manifest は「workspace root ではない」になり、初期化に失敗した型チェッカは「語彙が空」になる。

いちばん重かったのは `source-files.ts` の `readdirSync` である。読めないディレクトリが空のディレクトリとして扱われ、その配下がすべて走査から消え、消えたことを何も報告しなかった。`vp run ready` は緑のまま、検査された対象の集合だけが縮む。このリポジトリが最も嫌う「lint が緑なのに検査されていない」が、まさにこの形で作られていた。

同時に、全部を投げればよいわけでもない。走査対象が存在しないことは正常な入力であり、派生キャッシュが書けないことは走査の結果を 1 件も変えない。どこまでを値で表してよいかを決めないと、今度は環境の都合で lint が落ちるようになる。

## 決定

**「対象が無い」と「対象はあるが読めない」を同じ値に潰さない。** 前者だけを値で表し、後者は表に出す。判定は runtime が失敗に付ける `code` で行う。`ENOENT` と `ENOTDIR` は「そこに無い」なので `null` になり、`EACCES` のようにそれ以外の `code` を持つ失敗は投げられる。この分岐は `lib/path-failure.ts` の `readUnlessMissing` が 1 箇所で持ち、`statSync` / `readFileSync` を包むすべての読み取りがそこを通る。分岐が 1 箇所にあるので、この境界を動かす変更は 1 箇所の変更になる。

**走査を辿る途中の読み取りには不在の逃げ道を置かない。** `readdirSync` は素で呼ぶ。再帰の各段は、直前の `readdir` が「これはディレクトリだ」と報告したものにしか降りない。そこで「無い」は正常な入力ではなく、走査の前提が崩れたことを意味する。

代わりに、走査の入口で不在を受け止める。`listRepositoryFiles` は根がディレクトリでなければ空の一覧を返す。存在しないリポジトリ根を渡すことは呼び出し側の正常な使い方であり、辿る途中の失敗とは別の事象である。不在の許容を入口 1 箇所に集めることで、途中のどこで失敗しても黙って縮まない。

**握り潰してよい失敗を 2 段の条件で決める。**

1. その失敗によって、検査される対象の集合か報告される箇所の集合が変わるか。変わるなら握り潰せない
2. 変わらないなら、環境が拒んだのか、こちらの宣言が壊れているのかを分ける。環境が拒んだ失敗は runtime が `code` を付ける。`code` の無い失敗はこちら側の欠陥なので、走査が変わらない範囲であっても投げる

このリポジトリで両方を通るのは 2 箇所しかない。

- 導出キャッシュの読み書き（`catalog-cache.ts`）。キャッシュは走査の結果から作る派生物で、読めなければ作り直し、書けなければ次回また作る。検査される対象は 1 件も変わらない。読み側は壊れたキャッシュを「キャッシュ無し」として扱う。中断された書き込みが 1 つ残っただけで以後すべての lint が落ちる状態を作らないため。書き側は `code` を持つ失敗だけを黙って見送り、直列化できない値のような欠陥は投げる
- 依存パッケージの語彙の収穫（`library-vocabulary/harvester.ts`）。[0008](0008-read-library-types-for-messages-only.md) が定めたとおり、この型情報は報告に何を書くかにしか使われず、報告される箇所の集合を変えない。型チェッカを起動できない環境で lint が落ちないことは、その EDR が明示した契約である。ここでも `code` を持つ失敗だけを見送る

握り潰す 2 箇所も、失敗を束縛したうえで条件に掛ける形で書く。受け取らずに捨てる形は残さない。

**この形を lint ルールで固定する。** `no-discarded-failure--receive-and-surface-it` を追加し、base preset に error で配線した。判定は構文としての `try` / `catch` ではなく「失敗を表す値を受け取っているか」で行う。組で返す呼び出しの分解は `catch` 節ですらないので、`catch` だけを見る判定では現物の 8 割に当たらない。

呼び先は綴りで判定する（`attempt` / `attemptAsync`）。形だけで判定すると、`Object.entries` の分解や `const [, second] = declarationsIn(source)` のような、失敗が流れていない組の分解を全部誤検知する。実測でリポジトリ内に該当する形が既に 4 箇所あった。

## 影響

読めないファイル・読めないディレクトリ・壊れた JSON は、lint と CLI を落とすようになった。落ちること自体が報告であり、これまでは同じ状況が「対象 0 件」として緑になっていた。

`readJsonFile` は壊れた JSON に対して `null` を返さなくなった。manifest が壊れている状態は「`workspaces` を宣言していない」ではなく、パスを名指しした失敗になる。

`parseJson` は `read-json-file.ts` の外から見えなくなった。`workspace-root.ts` が自前で読んで parse していた経路が `readJsonFile` に寄ったため、公開する理由が無くなった。

キャッシュの書き込み失敗のうち、`code` を持たないものは投げられる。これまでは何であれ黙って見送っていた。

`readUnlessMissing` は元の失敗を握り直さずに投げ直すので、呼び出し側は `code` をそのまま見られる。Error でない値が投げられた場合だけ、元を `cause` に入れた Error に包む。

## 検討して採らなかった案

**すべての失敗を投げる。** 存在しないリポジトリ根を渡す経路と、書けないキャッシュディレクトリを持つ環境で lint が落ちる。どちらも検査の結果を変えない事象で、落とす理由が無い。

**失敗の種別ではなく呼び出し箇所ごとに握り潰すかを決める。** 判断が箇所ごとに散り、後から足された読み取りがどちらに倣うべきか決められない。`code` を見る 1 つの条件に寄せれば、新しい読み取りは何も決めずに済む。

**`try` / `catch` の構文だけを見るルールにする。** 現物の 11 箇所のうち 8 箇所は `catch` 節ですらなかった。構文で判定すると、直した後に同じ defect が別の綴りで戻ってくる。

**リテラルの形ではなく呼び先の型で組を判定する。** 型検査器の結果が要る。ルール群は構文だけで判定する土台の上にある（[0004](0004-shape-the-lint-rule-foundation-around-tooling-limits.md)）。
