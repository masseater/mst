# 0021. 自作 lint ルールの実行時間を自分で測り、送り先は使う側に決めさせる

## 状況

自作の lint ルールが増え続けている。ルールを 1 本足すたびに lint は重くなるが、どのルールがどれだけ使っているかを見る手段が無い。遅さを最初に踏むのは lint の終了を待っている本人であり、答えが手元で得られない限り遅いルールは放置される。

上流に手段があるならそれに乗るのが先だが、2026-08-10 時点では乗れない。`vp lint` は `--debug timings` を受け付けるが、リポジトリ全体に対して実行しても何も出力しない。スレッド数を 1 にしても、対象を 1 ワークスペースに絞っても同じだった。oxc 側では、ネイティブのルールの計測は完了した issue があり、JS プラグインのルールの計測は [#19745](https://github.com/oxc-project/oxc/issues/19745) として未解決のまま残っている。自作ルールは全て JS プラグイン側にある。

## 決定

ルール生成の土台に OpenTelemetry の計装を入れ、`lint-rule-authoring` が単体で送信できるようにする。送り先は使う側が環境変数で決める。

### 計測は生成の土台に 1 箇所だけ置く

自作ルールは全て `createWorkspaceLintRule` を通る。ここでルールの visitor を包めば、ルールを個別に書き換えずに全部を覆える。後からルールが増えても漏れない。

信号はメトリクス 1 本にした。ルール名を属性に持つ所要時間の分布として持ち、ルールごとのスパンにはしない。visitor の呼び出しは AST のノード単位で起きるため、スパンにすると 1 回の lint で桁違いの量になり、無料枠の前に読む側が破綻する。分布の合計がルールごとの総時間になるので、知りたいことはこれで足りる。

あわせて lint 全体の所要時間も送る。測れるのは自作ルールが使った時間だけで、oxlint 本体のネイティブなルール、型を見る検査、プラグインの橋渡しが使った時間は分離できない。両方あれば差として読めるので、lint が重いときに原因が自分たちのルールの内側か外側かを最初に切り分けられる。実測では自作ルール合計 140ms に対し lint 全体 2331ms で、自作ルールは全体の 6% だった。

### 送信の実装をパッケージに持たせる

OpenTelemetry はライブラリの作者に「API だけを使い、SDK は利用側が組み立てる」形を示している。この形を採らなかった。

採らない理由は、ルールを書く土台が「自分の書いたルールのどれが遅いか」に単体で答えられることを、この土台の価値として持たせると決めたためである。API だけに留めると、利用者は自分で SDK を組み立てる経路を書かないと何も得られない。

代わりに、送信するかどうかと送信先を使う側が決められることを条件にした。有効化は `MST_LINT_RULE_DURATION`、送信先は OpenTelemetry 標準の `OTEL_EXPORTER_OTLP_ENDPOINT`、停止は標準の `OTEL_SDK_DISABLED` で効く。mst が名前を発明したのは有効化の 1 つだけで、送り先を決める仕組みは自前で作っていない。

### 設定は環境変数で受け、oxlint の設定では受けない

oxlint の `settings` は JS のカスタムプラグイン向けの設定だと設定スキーマに明記されており、任意のキーを置ける。実際にルールの実行時に読めることも確かめた。それでも採らなかった。

`settings` はリポジトリで共有する設定ファイルにあるため、開発者 1 人が自分の環境だけ有効にする・止めるという操作に向かない。加えて `settings` が読めるのは lint が始まってからなので、SDK の登録を最初のルール実行まで遅らせる必要が生じ、実装が余計に複雑になる。

### 受け皿は手元のコンテナに置く

lint は開発者が手元で回すツールなので、送り先の既定を手元に置いた。`grafana/otel-lgtm` を採用する。1 つのコンテナに OpenTelemetry の受け口と保存先と閲覧画面が入っており、OpenTelemetry の既定値のまま動く。リポジトリに増えるのは compose の定義だけで、実装は増えない。

### 有効なのに送れなければ lint を落とす

有効化は開発者が明示的に行う操作なので、有効にした人は送れることを期待している。受け皿を起動し忘れたまま lint が緑になると、観測しているつもりで何も残らない状態が続く。

無効のときは何も起きない。これは失敗ではなく事前の分岐であって、エラー処理として書かない。止めたければ有効化を外せばこの状態になる。

## 帰結

- OpenTelemetry の SDK は送信の失敗を例外にしない。`forceFlush` も `shutdown` も resolve し、失敗は `setGlobalErrorHandler` に登録した先へ渡る。`try`/`catch` で囲んでも何も捕まらないことを実測で確かめてから、この登録先で終了コードを立てる形にした
- 有効時の所要時間の増分は測定のばらつきに埋もれた。5 回ずつ測って無効 3716ms、有効 3545ms である。ノード単位で時刻を 2 回取ることの負荷を心配していたが、計測できる差は出なかった。粒度をファイル単位に落とす案は不要になった
- oxlint の JS プラグインは、oxlint 本体とは別に起動される 1 つの Node プロセスの中で動き、プラグインのモジュールはその中で 1 回だけ読まれる。lint が違反を検出して終了コードが 1 になる場合でもプロセスは自然に終了するので、終了直前のフックで非同期の送信を完了させられる。この flush 点が取れなければ、送信ではなくファイル出力にする必要があった
- `@opentelemetry/api` は依存を 1 つも持たないが、SDK と exporter は依存木を持つ。この土台を使う側は、計装を有効にするかどうかに関わらずその依存を受け取ることになる
- 上流の [#19745](https://github.com/oxc-project/oxc/issues/19745) が出荷されたら、この計装を外して上流に乗り換える
