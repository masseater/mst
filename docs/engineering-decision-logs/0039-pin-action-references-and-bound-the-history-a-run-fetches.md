# 0039. アクション参照の固定と履歴の取得範囲は、ポリシーの層として持つ

- ステータス: Accepted
- 日付: 2026-08-12

## 文脈

[EDR 0025](0025-check-workflow-definitions-with-our-own-policy-layer.md) は、ワークフロー定義の検査をポリシーの層に限り、構文・式への注入・ランナー名の妥当性・アクションの入力名は見ないと決めた。

そこへ 3 つの規律を足したい。ワークフローが呼ぶアクションを可変でない参照に固定すること、固定した参照が古いまま残らないこと、チェックアウトが取得する履歴の量がリポジトリの成長と切り離されていること。

3 つ目は `actions/checkout` の入力に書かれた値を見る。0025 の「アクションの入力名は見ない」という文言にそのまま当たるので、線を引き直さないと足せない。

## 決定

**3 つとも、この検査が持つ。**

- ステップの `uses:` とジョブが呼ぶ再利用ワークフローの `uses:` は、40 桁のコミットハッシュで終わり、その隣に版を書いた注釈を持つ。`./` で始まるこのリポジトリ自身への参照と `docker://` で始まるコンテナ参照は対象にしない
- チェックアウトが履歴の深さに 0 を指定していない
- ワークフロー定義を持つリポジトリは、固定した参照を引き上げる機構を持つ

**0025 の「アクションの入力名は見ない」が指す範囲を、次の線で確定させる。** 判定にそのアクションの定義が要るなら持たない。定義を知らなくても判定できるなら持つ。入力名の綴りが正しいか、その入力が存在するか、値の型が合っているかは前者で、既製の検査が上流の定義に追随して初めて答えられる。特定の入力に特定の値を書くことがこのリポジトリの規律に反するかは後者で、アクションの定義とは無関係に決まる。0025 が持たないと決めたのは前者である。

## 版が最新かどうかを検査しない

固定は、放置すれば「更新しない口実」になる。だから固定と更新は対で持つ必要がある。

しかし、ある参照が最新かどうかはリポジトリの中に書かれていない。判定するには上流のリリース状況を問い合わせるしかなく、検査の中でそれをやると、こちらが何も変えていないのに上流の公開だけで検査が落ちる。同じコミットに対する結果が日によって変わり、検査としての意味が消える。

そこで、最新であること自体ではなく、最新へ追随する機構が繋がっていることを要求する。Renovate の設定があれば満たす。Dependabot だけがある場合は、その `updates` が `github-actions` を対象に含むことまでを見る。Renovate は既定でワークフローの参照を対象にするが、Dependabot は明示しない限り何も更新しないためである。

この観点は、定義ごとの検査とは別の観点として数える。対象がリポジトリに 1 つで、定義の数と対応しない。同じ観点に混ぜると、走査証跡の「定義 1 件・問題 1 件」が定義の側に問題があるように読める。

## 履歴を全部取りにいくのを禁じ、API へ送る

全履歴の取得は、リポジトリが育つほど遅くなる。育つ理由はコミットが積まれることであって、ワークフローがやることが増えることではない。取得を全履歴にしておくと、定義を一度も変えていない実行の所要時間が、無関係な要因で伸び続ける。劣化が緩やかなぶん、どこかで壊れて気付くことがなく、遅いことに慣れていくだけになる。

報告するときは、深さを減らす方向へは誘導しない。全履歴が要るという要求は、実際には履歴について何かを知りたいのであって、履歴のデータが手元に要るわけではない。祖先関係は 2 つの参照を比べる API が直接答え、コミットの列挙もタグの読み取りもそれぞれエンドポイントを持つ。1 つの質問が 1 リクエストで済む。

クローンを後から深くする、blob を落とさずに取る、といった git の側で粘る手段は提示しない。いずれも取得量がリポジトリの大きさに引きずられる性質を残すので、この規律が避けたいものが残ったままになる。

## 既製の検査を今回も入れなかった理由

参照の固定は既製の検査が持つ領域である。[ghalint](https://github.com/suzuki-shunsuke/ghalint) が `action_ref_should_be_full_length_commit_sha` を、[zizmor](https://docs.zizmor.sh/audits/) が `unpinned-uses` を持つ。0025 が検討した actionlint はこの層を持たず、`uses:` については `{owner}/{repo}@{ref}` の形になっているかしか見ない。

ただし ghalint は Go、zizmor は Rust で書かれていて、どちらも npm に配布が無い。参照を最新のハッシュへ書き換える pinact も同じである。3 つとも registry に存在しないことを確認した。0025 が `@mst/dont-review-it` の依存を純粋な npm パッケージだけに保つと決めているので、この 3 つのいずれも今回の変更の中では導入できない。

履歴の取得範囲を規律として持つ検査は、調べた範囲では既製に無い。ghalint が `actions/checkout` について持つのは資格情報の残置に関するもので、取得量には触れていない。

導入する時点で、重なる範囲をこの検査から外す。0025 と同じ扱いにする。

## 影響

**ワークフロー定義の検査に 2 つの観点が増え、リポジトリ単位の観点が 1 つ増えた。** 走査証跡の観点は 8 つから 9 つになった。

**ワークフロー定義を持たないリポジトリでは、増えた観点は開かない。** このリポジトリには `.github/workflows/` がまだ無いので、3 つとも対象を持たない状態で入る。

**版を書いた注釈まで要求する。** 固定だけでは、その参照が何のどの版なのかを読む手段がリポジトリの中から消える。更新の差分が何から何への変化なのかも読めなくなる。
