# 0023. 報告文は禁止と修正だけにし、理由は文書に置く

## 状況

このリポジトリの自前ルールは、報告文に理由まで書いていた。禁止を述べ、`because` で理由を続け、修正指示を置き、最後に「この書き換えは直したことにならない」を並べる形である。全 29 ルール 51 メッセージのうち、50 件が理由節を持ち、25 件が `if` / `when` で修正指示を分岐させ、9 件は肯定形の `must` で「あるべき状態」を述べるだけで何が拒まれたかを名指ししていなかった。

報告文がこの形になっていたのは意図した設計ではなく、書き手ごとの判断が積み上がった結果である。契約はどこにも書かれておらず、検査する機構も無かった。

同時に、各ルールには `docs/lint/` の文書があり、そこには「なぜそれが要るか」「どう直すか」「禁じる回避策」の節が既にある。理由は 2 箇所にあり、片方だけが更新されうる状態だった。

## 決定

報告文を、禁止の言い切りと命令形の修正指示だけで構成する。理由・場合分け・禁じる回避策は文書だけが持つ。

禁止は `must not` か `is forbidden` で述べる。肯定形の `must` は使わない。満たすべき状態を述べるだけでは、目の前のコードの何が拒まれたのかが読み手に残らないためである。

理由を落とす根拠は、報告文が読まれる位置にある。報告文は違反した人が最初に読む修正指示であり、そこへ理由を畳み込むと修正指示は段落の後ろへ移動する。読み手は禁止の一文で長さに気圧され、修正指示に届く前に報告を消す最短の操作を探し始める。その操作は抑制である。抑制の口はこのリポジトリでは塞いであるので、行き先は結局レビューになる。

条件を落とす根拠は、場合分けが読み手に判断を戻すことである。判断できなければ枝は選ばれず、報告は残る。場合分けが要るほど直し方が分かれるなら、それは文書が扱う分量である。

この形を `lint-rule-authoring/no-explained-lint-message--state-prohibition-then-fix` が検査する。検査はメッセージ本文からコード片と差し込みを伏せたうえで、禁止の言い切り・命令形の修正指示・理由の接続表現・条件語・逃げ道の言い回し・手書きの文書参照・非 ASCII 文字・説明文との一致の 8 点を見る。語彙はこのルールが所有し、設定で差し替えられないようにした。ワークスペースごとに「禁止と認める言い回し」が変わると、報告文の形が揃っているという前提そのものが崩れるためである。

## 帰結

- 51 メッセージすべてを書き換えた。理由節は 0 件、条件語は 0 件、禁止の言い切りは 51 件になった。長いものは 1,000 文字を超えていたが、書き換え後はおおむね 2 文に収まる
- 報告文から落とした理由・場合分け・回避策の封じは、対応するルールの文書へ移した。文書はメッセージ末尾の参照から辿れる
- 命令形の判定は動詞の一覧との照合で行う。品詞を機械で決められないため、一覧を持つ以外の方法が無い。一覧に無い動詞で書きたくなったときは一覧に足す。この一覧はルールが所有しているので、足す場所は 1 箇所である
- 検査は `docs` と `messages` を直接持つオブジェクトを対象にするため、テストの中に置いたルール風のオブジェクトにも掛かる。既存のテスト用メッセージ 3 件が引っかかったので、同じ契約に合わせて書き直した
- `propertyNameOf` が 2 つのルールで同じ本体を持っていたことが、この作業で重複検出に引っかかった。依存の向きに従って `@mst/lint-rule-authoring` に寄せ、`@mst/dont-review-it` から import するようにした
- 検査の穴として、値が文字列リテラルでもテンプレートリテラルでもないメッセージは読めない。本文が実行時に決まるためで、ルールの文書に穴として書いた
