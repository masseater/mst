# 0025. ワークフロー定義は自前のポリシー層で検査し、構文の層は持たない

- ステータス: Accepted
- 日付: 2026-08-11

## 文脈

`docs/guidelines/enforcement.md` と `docs/guidelines/secrets-and-permissions.md` は、CI の実行単位について規範を持っている。起動の条件で自分を絞り込まないこと、失敗を成功に読み替えないこと、実行ブロックを 1 つのコマンド呼び出しに留めること、部品にトリガを持たせないこと、実行単位をまたいで結果を受け渡さないこと、権限を宣言すること。

どれも決着した基準である。しかし `.github/workflows/ci.yml` を見ている機械が 1 つも無く、守られているかどうかを判定していたのは読む人だけだった。`enforcement.md` 自身が「レビューで人が毎回同じ判定をしている項目があり、その判定を機械が評価できる; THEN MUST: その項目をガードに置き換える」と書いている。この状態はその規範に反している。

対象は YAML で、このリポジトリの lint は JS と TS しか読まない。

## 決定

**ワークフロー定義の検査を `@mst/dont-review-it` の `workflows` サブコマンドとして持つ。** 独立したパッケージには切らない。守る不変条件は「レビューで指摘すべき書き方の問題が残らない」の対象違いであり、パッケージ境界は利用者が 1 回の意思決定で入れるかどうかで切る。ワークフローの書き方を機械で決めるかどうかは、コードの書き方を機械で決めるかどうかと別の意思決定にならない。

**検査するのはポリシーの層だけにする。** 構文、式への注入、ランナー名の妥当性、アクションの入力名は見ない。この層は既製の検査が持っている領域で、`enforcement.md` の「その形式を対象にする既製の検査が世の中にある; THEN MUST: 既製のものを先に使う」に従えば自前で書く対象ではない。

**その既製の検査は、いま導入しない。** 導入する時点で、この検査から重なる範囲を外す。

## 既製の検査を今回入れなかった理由

[actionlint](https://github.com/rhysd/actionlint) が対象領域の標準で、活発に保守されている（2026-07 に更新、MIT）。ただし Go で書かれていて、npm への公式の配布が無い。[公式のインストール手順](https://github.com/rhysd/actionlint/blob/main/docs/usage.md)が挙げるのは Go のツールチェーン、ダウンロードスクリプト、Docker、pre-commit で、npm も JavaScript の API も無い。

npm 上の経路は 2 つあり、どちらも第三者による包み直しである。

- `actionlint`（2.0.6）は wasm 化したもので、最後の公開が 2022-12 である。actionlint の価値はランナー名とアクションの定義に追随し続けることにあるので、3 年半止まった版はその価値をほとんど持たない
- `github-actionlint`（1.7.12、2026-02）は上流に追随しているが、初回実行時に GitHub Releases からバイナリを取得して待避させる。公開するパッケージの依存として持つと、実行時のネットワーク取得が利用者側に伝播する。`@mst/dont-review-it` の依存はいま全て純粋な npm パッケージで、この性質を持ち込む判断は単独で下したい

したがって「既製を先に使う」を今回の変更の中で満たす手段が無い。自前で書いたポリシーの層は既製が覆う領域と重ならないので、後から既製を入れるときに捨てる必要も無い。

## 検査しないと決めたもの

規範にはあるが、この検査は見ない。理由を残す。

- **実行単位の名前が起動のタイミングを指しているか。** 名前が何を指しているかの判定が機械に落ちない
- **定義ファイル内の重複をどの量から統合するか。** `enforcement.md` は閾値を数値で固定せよと書いているが、その数値はこのリポジトリの定義ファイルの実態から決めることになっている。実行単位が 1 つしか無い現在、実態から導ける数値が無い
- **キャッシュ再利用の契約。** `vite.config.ts` の側にあり、ワークフロー定義の中に無い
- **実行の外側から取得される成果物の保管先。** 成果物を出す経路がまだ無い
- **外部状態を変える操作の対象集合と資格情報の分離。** 外へ出す操作がまだ無く、判定の材料が定義の中に現れない

前の 2 つは判定の材料が無く、後の 3 つは対象がまだ存在しない。対象ができた時点で、この検査に足すか、その時点の既製の検査に預けるかを決める。

## 起動の条件で絞り込む検査の範囲

`enforcement.md` は「ゲートとして数える実行を条件で絞り込みたい; THEN MUST: 起動した後の階層で絞り込む」と書き、続けて「ゲートとして数えないと確定でき、起動そのものの条件でしか絞り込みを表現できない; THEN MAY: 起動の条件で絞り込む」という例外を置いている。

検査はこの例外を、トリガの種類で表現する。`pull_request` と `pull_request_target` に置かれた `branches` / `paths` の類だけを報告し、`push` に置かれたものは報告しない。branch protection が要求する status check は pull request の側で生成されるので、そちらを絞り込むと「チェックが無い＝止める理由が無い」状態が作れてしまう。`push` 側の絞り込みは、その実行がゲートとして数えられないことが確定している側にあたる。

この線を引かないと、`on.push.branches: [main]` という最も普通の書き方が初日から報告に出る。逆に pull request 側まで許すと、この検査が守ろうとしている当のものが抜ける。

## 影響

**`vp run guard` に `vp exec dont-review-it workflows` が入った。** main に入る 2 つの経路のどちらもこのゲートを通る。

**`.github/workflows/ci.yml` は 1 件も報告されない。** 導入時点で違反が無かった。違反を仕込んだ入力では 6 種類すべてが報告されることを確認している。

**`@mst/dont-review-it` が `yaml` に依存する。** `@mst/agentic-documents` が既に同じ catalog の版を使っている。

**このパッケージが oxlint 以外の検査面を持つ 2 つ目の形になった。** 1 つ目は複数ファイルをまたぐ突き合わせ（`verify` と `duplicated-bodies`）で、こちらは lint のツールチェーンが読めない形式である。境界の言い方を `AGENTS.md` に足した。
