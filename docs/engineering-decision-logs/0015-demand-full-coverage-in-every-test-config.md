# 0015. カバレッジの下限を全設定ファイルに 100 で宣言させる

- ステータス: Accepted
- 日付: 2026-08-10

## 文脈

カバレッジは計測すれば数字が出るが、数字が出ることと基準が効いていることは別である。下限を宣言していない設定では、カバレッジが下がったコミットと上がったコミットが同じ扱いになる。

このリポジトリはこれまでカバレッジを計測していなかった。`@vitest/coverage-v8` が入っておらず、`vp test --coverage` は依存が無いという理由で失敗する状態だった。したがって「下限をどこに、いくつで書くか」は、まだ何も決まっていない。

[0002](0002-place-quality-gates.md) が置いた検査は、lint・型・テストの成否・build・未使用検出である。テストが「通ったかどうか」は見ているが、「どれだけのコードを通ったか」は見ていない。

## 決定

`test.coverage.thresholds` の宣言を lint ルール `dont-review-it/no-lenient-coverage-threshold--demand-full-coverage` で強制する。要求値は 4 メトリクス（`branches` / `functions` / `lines` / `statements`）すべて 100 を既定とし、下げる操作はルールのオプションだけで行う。

このリポジトリの 4 つの設定ファイル（ルート・`packages/utils`・`packages/dont-review-it`・`packages/lint-rule-authoring`）は、いずれも Vitest の短縮記法 `thresholds: { 100: true }` で宣言する。

## 根拠

### 下限は設定ファイルごとに書かせる

ルートの `vite.config.ts` に置いた `test` ブロックがワークスペースの `vp test` に伝播するかを実測した。ルート側に `coverage.reportsDirectory` を書いた状態で `packages/utils` のテストを走らせたところ、指定したディレクトリは作られず、既定の `packages/utils/coverage/` が作られた。ルートの `test` ブロックはワークスペースの実行には効いていない。

したがって「ルートに 1 回書けば全ワークスペースに効く」という形は取れない。ルールは対象になり得る設定ファイルすべてに発火し、各ファイルが自分で宣言する。

### 要求値はルール側に置き、設定ファイル側では下げられないようにする

設定ファイルに直接 90 と書ける状態では、その数字がどういう検討の結果なのかがファイルごとに散る。ワークスペースが 3 つあれば 3 つの別々の合意ができ、リポジトリ全体としての基準が存在しなくなる。

要求値をルールのオプションに置くと、下げる操作が 1 箇所への変更になり、変更そのものが差分として見える。設定ファイル側は「要求を満たしている」ことだけを書く。

### 既定を 100 にする

100 未満の下限は「許容する未検証コードの量」を宣言している。90 と書けば、テストの無いコードが 10% まで存在してよいという合意になり、その枠がどこに使われるかは誰も指定しない。実際には最も書きにくい箇所に集まる。

100 を既定にすると、枠を作るという判断が明示的な操作になる。オプションで下げた数字は 1 箇所に現れ、いつ戻すのかをコミットログに書かせられる。

### 4 メトリクスすべてを要求する

`lines` だけを 100 にした設定は一見厳しいが、行カバレッジは分岐の存在を見ない。全行を通りながら片方の分岐しか実行していないコードが満点になる。どれか 1 つが緩いと残り 3 つの意味が薄れるため、揃えて要求する。

### 数値リテラル以外は宣言と認めない

`thresholds` の値が変数参照やスプレッドで外から流し込まれていると、その設定ファイルを読んだだけでは下限が確定しない。ルールは設定ファイル 1 枚を読んで合否を決める形を保つため、数値リテラル以外を「宣言されていない」として扱う。

これは [0002](0002-place-quality-gates.md) が置いた「合否は現在のファイルで決まる」という形と同じ理由に立っている。

### 計測が有効かどうかは見ない

このルールが見るのは設定ファイルの宣言だけで、テストが実際にカバレッジを集めているかは見ない。計測の有効・無効は CLI の引数や実行環境でも変わり、設定ファイルを読むだけでは決まらない。

宣言と起動の両方を 1 本のルールで判定すると、どちらの違反も同じ 1 本の設定でしか制御できなくなる。

### 対象は `vite.config` と `vitest.config` の両方にする

このリポジトリは Vite+ を使うため設定は `vite.config.ts` に集約される（[0001](0001-adopt-vite-plus-as-the-toolchain.md)）。しかし `dont-review-it` は公開パッケージであり、Vitest を単体で使う採用者の手元では `vitest.config.ts` が別に置かれる。どちらに書かれていても同じ要求が効かなければ、採用者側では規約が空振りする。

## 影響

`@vitest/coverage-v8` が catalog とテストを持つ 3 ワークスペース、およびルートの依存に入る。ルートに入れているのは、ルートの `vite.config.ts` が coverage を宣言しており、knip がそれを未宣言依存として報告するためである。

`vp run -r test` は既定ではカバレッジを集めないため、宣言した下限はこの時点では検査されない。`--coverage` を付けて走らせたときに初めて効く。宣言を実際のゲートにするかどうか（CI をカバレッジ付きに切り替え、リポジトリを 100% まで持ち上げるかどうか）は、この決定には含まれていない。

宣言を入れた時点の実測値は、`packages/utils` が 4 メトリクスすべて 100、`packages/lint-rule-authoring` が statements 96.11 / branches 85.71、`packages/dont-review-it` が statements 93.18 / branches 84.42 / functions 99.5 / lines 97.8 である。
