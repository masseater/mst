# 0041. どのリリースが入るかを宣言が決める

- ステータス: Accepted
- 日付: 2026-08-12

## 文脈

依存の宣言には 13 件の範囲指定が残っていた。マニフェスト側に 11 件（`knip`、`std-env`、remark 系 4 件、`@types/mdast`、`@opentelemetry/*` 5 件）、catalog 側に 7 件（`@tanstack/intent`、`@types/node`、`es-toolkit`、`jsonc-parser`、`oxc-parser`、`typescript`、`yaml`）である。

範囲で書かれた宣言は、同じコミットに対して複数の答えを持つ。どれになるかを決めているのはロックファイルであって宣言ではない。ロックファイルがある限りリリースは固定されるので、日常の作業では差が見えない。差が現れるのは、ロックファイルを更新する操作、ロックファイルを持たない依存元からの解決、`--no-frozen-lockfile` で走るインストールのときで、そこでは宣言も履歴も「変わっていない」ように読める。原因を宣言まで遡るには、いつ・どの経路で解決が走ったかを再構成することになる。

[EDR 0028](0028-keep-the-catalog-for-shared-versions-only.md) が入れた依存宣言の検査は、版をどこに書くかを決めている。どんな形の版を書くかは決めていなかった。

## 決定

**版を 1 つのリリースに定める。** マニフェストの通常依存・開発依存・任意依存と、catalog のすべてのエントリで、値は `1.2.3` の形（必要なら事前リリース識別子とビルドメタデータが続く）にする。13 件をロックファイルが解決している版へ書き換えた。解決結果は変わらず、`vp why` の単一インスタンスも保たれている。

**強制は lint ルールとして持つ。** `no-version-range--pin-the-exact-version` が、リポジトリ内のマニフェストとワークスペース定義を読み、範囲のまま残っている宣言を報告する。直し方は「ロックファイルが解決している版を書く」に一意に決まるので error にする。

**CLI の検査には足さない。** `dont-review-it check` の依存宣言の検査は設定の口を持たず、すべての利用者で無条件に走る。範囲を意図的に選ぶ余地を残すには、利用者ごとに書ける設定面が要る。oxlint のルールオプションはこのパッケージが既に持っているその面であり、[EDR 0028](0028-keep-the-catalog-for-shared-versions-only.md) が置いた 3 つの error はどれも範囲かどうかを見ていないため、同じ違反が 2 経路から報告されることもない。

**既定では有効にしない。** 出荷する preset には載せず、このリポジトリのルート設定で有効にする。範囲を許すかどうかは採用者のリリース方針で決まる問いであり、`require-catalog-entry--register-shared-dependency` と同じ扱いにする。

**意図的な範囲は名前で登録する。** `intentionalRanges` に列挙された名前は、マニフェストの宣言でも catalog のエントリでも報告しない。登録する値は名前だけにして、意図している範囲そのものは書かせない。範囲を設定へ書き写すと、同じ版が宣言と設定の 2 か所に並び、片方だけ動いたときに黙って割れる。

**境界を 4 つ引いた。**

- ピア依存は見ない。範囲を広く取るのが設計上正しく、単一のリリースに寄せる対象ではない
- `workspace:` / `link:` / `file:` の値と `catalog:` の参照は見ない。前者は外部のリリースを指しておらず、後者は版を持たない参照で、指している先の catalog エントリを直接見る
- 配布タグ、リポジトリの URL、ホスト名で書いた値は報告しない。範囲の構文を持たず、どのリリースへ寄せるかが宣言の中から決まらない。直し方が一意に決まらない問いを error にしない、というルールの境界をそのまま適用した
- `engines` と `peerDependencyRules` は見ない。依存の宣言ではない

**`engines.node` の `>=26.0.0` は残す。** これは実行環境が満たすべき下限であって、入れるリリースの指定ではない。固定する側は `devEngines.runtime` が既に持っている。

## 影響

**依存を上げる操作が宣言の書き換えとして履歴に残る。** どのリリースがいつ入ったかはコミットが持ち、宣言は現在の答えだけを持つ。ロックファイルの更新と宣言の更新が同じ差分に現れるので、片方だけ動いた状態を作れない。

**catalog の値が実態と一致していることを機械が見る。** `@types/node` が `^24` のまま `26` 系へ解決されて `vite-plus` と `vitest` が二重インスタンス化した事象は、catalog の値と解決結果のずれから起きた。範囲を許さなければ、このずれは宣言の時点で存在しなくなる。

**版を上げる手数が増えた。** これまで範囲に任せていた更新は、宣言を書き換える操作になる。この手数は、どのリリースが入るかを宣言だけで読めることと引き換えに払う。

**ルールが読む材料は 2 つの読み手から受け取る。** ワークスペース一覧とマニフェストの内容は `require-catalog-entry--register-shared-dependency` と同じ読み手を共有し、catalog のエントリは新しい読み手が供給する。後者はワークスペース定義の解析を CLI の検査と共有していて、同じファイルを 2 通りに解釈する経路を作っていない。
