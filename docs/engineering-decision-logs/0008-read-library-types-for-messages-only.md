# 0008. lint が型チェッカを起動し、読んだ型はメッセージにしか使わない

- ステータス: Accepted
- 日付: 2026-08-10

## 文脈

`no-local-finite-value-set--use-or-register-canonical-values` は、有限値の語彙をローカルに定義した箇所を報告する。カタログに所有者が見つからないとき、報告が示す行き先は 2 つだった。リポジトリ内で所有者を探すか、リポジトリ内に登録するかである。

しかし実際には 3 つ目がある。`oxlint` の `AllowWarnDeny` のように、その語彙を依存パッケージの公開型が既に所有していることがある。このとき正しいのはリポジトリ側が所有者を名乗ることではなく、その型から導出することだった。実例として、`LINT_RULE_SEVERITIES` の 3 つの綴りを直に書いていた宣言を `Extract<AllowWarnDeny, "error" | "warn" | "off">` に置き換えている（25039ed）。

この 3 つ目の行き先は、それまでのメッセージ本文のどこにも現れていなかった。手で直した人が独力で辿り着くしかない状態だった。

どのパッケージのどの型が所有者かを名指しするには、構文だけでは足りない。`AllowWarnDeny` は `.d.ts` の中で別名の再エクスポートを経由しており、宣言そのものは別の場所にある。`Extract` のような型演算を通した結果を値の集合として読むには、型チェッカに解決させる必要がある。

## 決定

**lint ルールの中から TypeScript の型チェッカを起動する。** `typescript/unstable/sync` の同期 API を使い、lint 対象ファイルが属するパッケージの直接依存について、公開型に含まれるリテラルのユニオンを列挙する。

oxlint は JS プラグインを worker で回していないため、同期 RPC の制約に抵触しない。起動はプロセス内で 1 度きりで、報告を出そうとする経路に入ったときだけ遅延して走る。違反のないファイルには一切かからない。実測では起動と収穫を合わせて 200ms 未満、リポジトリ全体の lint は 1 秒弱のままである。

**この API が unstable と明示されていることを承知の上で採る。** パッケージの `exports` が `./unstable/sync` という名前で公開しているとおり、後方互換の約束はない。採る理由は、型の解決結果を読む手段が他にないことと、壊れたときの影響がメッセージの厚みに閉じることである。次の決定がその閉じ込めを担保する。

**型情報は「何を報告するか」ではなく「報告に何を書くか」にしか使わない。** 報告する箇所の集合は、この仕組みが無かったときと完全に同じである。カタログに所有者がいる場合の報告は変わらず、指紋の一致を条件とする 2 つの形（添字アクセスの元配列・静的な `Set` の初期化子）は、依存パッケージが所有していても報告しない。

判定に使わない理由は 3 つある。

1 つ目は、lint の合否が現在のファイルとカタログだけで決まるという EDR 0002 の不変条件を壊さないため。語彙索引は `node_modules` の中身に依存し、これはリポジトリの管理下にない。合否がそこに依存すると、依存を刈り込んだチェックアウトと通常のチェックアウトで結果が食い違う。

2 つ目は、EDR 0003 が抑制の口を一切作らないと決めているため。「ライブラリ由来だから免除」は形を変えた抑制の口であり、しかも「ライブラリ由来」の定義が曖昧である。ローカルの別名を 1 枚挟んだ時点で判定が揺れる。

3 つ目は、`satisfies` による導出が部分集合しか保証しないため。「食い違えば型エラーになる」という前提は半分しか成り立たず、免除の根拠にできない。

**語彙索引は lint 対象ファイルが属するパッケージの直接依存から作る。** 推移的な依存は見ない。所有者として名指しできるのは、そのファイルが実際に import できる公開 API に限られるためである。`dependencies` / `devDependencies` / `peerDependencies` の 3 欄を等しく見る。設定ファイルや lint ルール自身のように、開発時依存の型を正当に使うファイルが対象に含まれるためで、欄で絞ると所有者がいるのに「所有者なし」と報告することになる。

`workspace:` で指定されたリポジトリ内のパッケージは索引に入れない。リポジトリ内の所有者はカタログが受け持つ領分であり、両方が名乗ると同じ宣言が 2 つの経路で候補に出る。

パッケージの境界は、カタログ構築が既に持っている「最も近い package manifest を探す」判定と同じものを使う。この判定は `builder.ts` のファイル内ローカル関数だったが、2 つの用途が同じ境界を見る必要が出たため `source-files.ts` に移した。

**候補は宣言元で畳んだうえで、絞らずに全て並べる。** 同一の型宣言に別名で届く候補は 1 つにまとめる。まとめたうえで残った複数の候補は、順序で優劣を示さず全て提示する。どの所有者に属するかを人が決めるという EDR 0003 以来の姿勢を、相手がライブラリでも変えない。

**ライブラリの型が余分な値を admit する場合は、その差分をメッセージに出す。** 依存側の型がリテラル以外のメンバー（`number` など）を含むことは実際にあり、そのまま使うのではなく絞り込んで導出する必要がある。差分が読み手に見えなければ「そのまま使えばよい」と誤読される。

**型チェッカを起動できないときは語彙索引を空として扱う。** 同期 API はプラットフォーム固有のバイナリを子プロセスとして起動する。起動に失敗する環境、依存が刈り込まれた環境、API の形が変わったバージョンでは、これまでどおりのメッセージを出す。lint はここで落ちてはならない。プラットフォームのバイナリを実際に外して、lint が落ちず従来のメッセージが出ることを確認している。

**library message 用と canonical catalog 用の checker dependency を分ける。** `typescript` は `typescript/unstable/sync` を通じて lint 実行時に library vocabulary を読むため、`packages/dont-review-it` の runtime dependency に置く。この checker が決めるのは message の候補だけで、起動不能時は空の索引へ退避する。

canonical catalog は別の runtime dependency `typescript-6` を使う。こちらは owner binding の literal domain、import・spread、public export の symbol identity を repository source から解決し、lint と strict verification の正当性を決める。解決失敗を空の候補へ退避せず、その owner の entry を除外して strict problem にする。API、失敗時の扱い、合否への影響が異なるため、2 つを同じ checker instance や package 名で兼用しない。

## 影響

このパッケージの lint は、`node_modules` に型宣言が揃っていることを前提にした「良い報告」と、揃っていないときの「これまでどおりの報告」の 2 つの状態を持つようになった。合否は両方の状態で同じである。報告文が環境によって変わることは受け入れる。

`typescript` と `typescript-6` が実行時依存になった。`@mst/dont-review-it` を使う側は library message 用の同期 API と、canonical catalog 用の TypeScript 6 checker の両方を引き込む。複数の workspace が共有する `typescript` は `pnpm-workspace.yaml` の catalog に置き、この workspace だけが使う `typescript-6` は `packages/dont-review-it` の manifest で直接固定する（[EDR 0028](0028-keep-the-catalog-for-shared-versions-only.md)）。依存変更時は `vp install --frozen-lockfile` に加え、`vp why typescript` と `vp why @typescript/typescript6` で意図しない複数 instance が無いことを確認する。

候補の絞り込みをしないため、ノイズが混じる。実測では `error` / `warn` / `off` に対して `AllowWarnDeny` と `DummyRule` の 2 つが候補に並ぶ。後者は前者を内側に含む型で、語彙の所有者としては筋が悪い。順序で優劣を示さないと決めた以上、この選別は人が行う。

ルール本体はこの変更で予算（EDR 0007 のコード行数 400）に当たった。引き上げではなく分割で解いている。構文から有限値の語彙を読む責務を `finite-value-syntax.ts` に、import 先が登録済みの所有者に届くかを判定する責務を `import-route.ts` に出した。どちらも純粋な関数の集まりになったので、テストはルール越しではなく直接書ける。ルールのテストからは、これらのモジュールの単体テストと重なるケースを落とし、配線を示す 1 件ずつを残した。
