# 0032. CLI 向け config は全部入りの厳密な上位集合として出す

- ステータス: Accepted
- 日付: 2026-08-11

## 文脈

CLI パッケージにだけ意味を持つ規律ができた。citty のコマンド定義の形、標準ストリームのテストダブルの一元化、両ストリームのスナップショット固定。これらを `@mst/dont-review-it` からどう出すかを決める必要があった。

移植カタログの設計時（2026-08-09）に「preset の軸で規律を部分採用させない。全部入りの config を 1 つだけ公開する」と決めている。CLI 向けの config を足すことは、この決定と衝突するように見える。

## 決定

**`oxlintCli` を、既存の `oxlint` の厳密な上位集合として公開する。** `oxlint` のすべてのルールを同じ重大度で含み、CLI 固有の 3 ルールを足すだけで、何も外さない。

これは 2026-08-09 の決定と矛盾しない。あの決定が禁じたのは「規律の軸を利用者に選ばせる」ことである。`oxlintCli` は規律のサブセットではなく対象種別（CLI パッケージ）で切られており、利用者の判断は「このパッケージは bin を公開するか」の 1 回で終わる。どちらの config を選んでも、基礎の規律から抜けられるルールは 1 つもない。名前も規律名ではなく対象種別から付けた。

**標準ストリームのフィクスチャは `@mst/dont-review-it/vitest` から出す。** `require-standard-io-snapshot` と `no-handmade-standard-io-double` の報告メッセージは `standardIoTest` の import を修正指示として名指しする。修正指示が指す実体は、ルールを持つパッケージ自身が同梱する。ルールを採用した時点で唯一の直し方も手元に揃い、追加の採用判断が発生しない。

**リポジトリ内では、CLI 向けの追加ルールを CLI パッケージのサブツリーにだけ適用する。** ルートの lint 設定は全体を `oxlint` で覆い、`packages/dont-review-it/**` に `oxlintCli` との差分ルールを重ねる。フィクスチャは `dont-review-it` が出すので、その上流にあるパッケージ（`lint-rule-authoring`）の spec はフィクスチャを import できない。依存の向きで直し方が実行不能になる場所へ検出だけ届く状態を作らないため、適用範囲を対象種別で切る。

## 影響

**`vp run -r test` の task cycle を持ち込まなかった。** 上流パッケージの spec にフィクスチャを強制すると、`lint-rule-authoring` が dev 依存として `dont-review-it` を持つことになり、vite-plus のタスクグラフが循環で落ちる。適用範囲を切ったことで依存の向きは一方向のまま残る。

**利用者向けの採用手順が 1 行で書ける。** bin を公開するなら `oxlintCli`、しないなら `oxlint`。判断基準は [CLI の作り方](../../packages/dont-review-it/docs/cli.md) が持つ。
