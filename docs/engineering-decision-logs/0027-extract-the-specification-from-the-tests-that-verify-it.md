# 0027. 仕様は検証しているテストから抽出する

- ステータス: Accepted
- 日付: 2026-08-11

## 文脈

AI は人間の指示の不明瞭な部分を独自に解釈して進める。その解釈は実装とテストの中に埋まり、人間はコードを読まない限り気付けない。人間が最初から仕様をすべて定義する運用はしないため、「人間が書いた仕様にコードを従わせる」形は取れない。

また [0017](0017-demand-full-coverage-in-every-test-config.md) が全ワークスペースに 100% のカバレッジ下限を要求した結果、テストには「下限を満たすために分岐を踏むもの」と「守るべき振る舞いを主張しているもの」が混在し、区別する手段が無かった。

## 決定

テストを 2 種類に分ける。カバレッジ担保テストは従来どおり対象ソースの隣の `<ソース名>.test.ts` に置く。仕様担保テストはパッケージ直下の `specs/<機能名>.spec.ts` に、BDD の形（最上位 `describe` が仕様の主題、直下の `it` が日本語の主張文）で置く。

`@mst/verified-specifications` が `specs/` の `.spec.ts` から `describe` / `it` の文字列を静的に抽出し、各ワークスペース直下の `SPECIFICATIONS.md` を生成する。`verified-specifications check` は生成物の鮮度と仕様担保テストの構造を検査して `guard` の一部になり、`--write`（`guard:fix`）が再生成する。

## 根拠

### 仕様の真実の源はテストであり、抽出の向きは テスト → 文書

仕様を独立したファイル（YAML）に書き、テスト名と突き合わせる形を先に実装して捨てた。人間の指示から AI が仕様も書く運用では、仕様ファイルとテストの両方を AI が書く。突合が確かめられるのは「AI が自分の解釈を二か所へ矛盾なく書き写したか」だけで、勘違いは二か所に一貫して書かれるため捕まらない。残るのは二重記述だけだった。

抽出の向きを テスト → 文書 にすると、文書は機械が検証している主張の写しになり、二重記述が消える。「仕様はあるがテストが無い」状態は構造的に作れない。勘違いの検出点は PR レビューで、AI が解釈を変えれば生成文書に差分が出る。

### 仕様担保テストは機能単位で、ソースの隣に置かない

内部モジュールの単位で仕様を書くと、実装都合の主張が一覧を埋める。仕様担保テストは利用者から見える機能の単位（e2e 未満、ユニット超え）で書き、`specs/` に機能名で置く。`.spec.ts` は `specs/` の中にだけ存在でき、`specs/` の中には `.spec.ts` しか置けない。この対応は lint（ベースの `pattern` と `specs/**` の override）が守る。

### 実行時 API を持たない

テスト登録を行う関数を export すると、このパッケージだけ vitest へ実行時に届く必要が生じ、vitest の二重インスタンス化（`vp check` では検出できない既知の障害）の危険を持ち込む。標準の `describe` / `it` だけで書ける形にし、このパッケージは静的検査だけを行う CLI と lint preset に留めた。

### 対応関係は静的走査で判定する

テストを実行して収集する形は、skip されたテストや実行環境の差で結果が変わる。[0017](0017-demand-full-coverage-in-every-test-config.md) が「計測が有効かどうかは見ない」と決めたのと同じ理由で、この検査もソースを読んで決める。テストが実際に通っているかは `guard` の `vp run -r test --coverage` が既に見ている。

`describe` / `it` の名前が文字列リテラルでないもの、`it.each` などの動的形、`test` 関数の使用は、静的に読めないため error にする。これは 0017 の「数値リテラル以外は宣言と認めない」と同じ形である。

### 構造の大半は既存の公式ルールに任せる

中間 `describe` の禁止は `vitest/max-nested-describe`、`describe` の外のテストは `vitest/require-top-level-describe`、skip / only は `vitest/no-disabled-tests` / `no-focused-tests` が既に守る（[0016](0016-enforce-with-upstream-rules-before-writing-our-own.md)）。CLI が自前で報告するのは、公式ルールが見ない抽出可能性の不変条件（リテラルでない名前、`test` の使用、主張の無い `describe`、鮮度）だけにした。

### tsconfig の絞り込みを検査する

`specs/` がパッケージ直下にあることは「tsconfig がパッケージ全体を検査する」ことを前提にする。既存の `no-standalone-tsconfig--extend-shared-preset` は `extends` しか見ず、`include` を workspace 側に許している。`include` で `src` に絞られると `specs/` は型検査から静かに抜け、すべての検査は緑のままになる。そのため `verified-specifications check` は、仕様担保テストを持つワークスペースの tsconfig が `include` / `files` / `exclude` を宣言していたら error にする。

### 既存の仕様書駆動開発の実装との関係

仕様を永続させる形・能力名で並べる形・検証単位を具体的な主張にする形は OpenSpec と一致する。一致しないのは検証の方法で、OpenSpec の verify は AI がコードを読んで報告する形であり、仕様とテストの対応を機械が照合する仕組みは調べた範囲で存在しなかった。その照合（正確には、照合を不要にする抽出）がこのパッケージの中身である。EARS の `SHALL` は英語圏前提のため採らず、主張文は日本語の 1 文とした。

## 影響

- ルートの lint 設定から `.spec.ts` の禁止が消え、`specs/` ディレクトリの規約が入った。リポジトリの `AGENTS.md` のテスト配置規範も 2 種類に分かれた
- 全ワークスペース（website を除く）に初期の仕様担保テストと `SPECIFICATIONS.md` が入った
- `guard` に `verified-specifications check` が、`guard:fix` に `--write` が入った
- `@mst/utils` に `RepositoryProblem` が入り、agentic-documents の問題型はその別名になった

## 検討して採らなかった案

**仕様ファイル（YAML）+ テストとの突合。** 上述のとおり、AI が両方書く運用では勘違いを捕まえられない。実装済みだったが捨てた。

**承認スナップショット（人間が承認するまで guard が赤）。** AI だけで回る作業が都度止まる。PR レビューでの検出から始め、必要になれば後から強められる。

**ソースの隣に `<ソース名>.spec.ts` を置く形。** ファイル単位の仕様は内部モジュールの実装都合を仕様と呼んでしまう。機能単位に置き直した。
