# 0024. 公式のルールを既定にし、メッセージが直し方を決められないときだけ自前で書く

- ステータス: Accepted
- 日付: 2026-08-10

## 文脈

[0016](0016-enforce-with-upstream-rules-before-writing-our-own.md) で公式のルールを 256 本入れた。自前のルールは 15 本ある。どちらで守るかの判断は、そのとき「既製で足りるなら既製」とだけ書いていて、足りているかどうかを何で測るのかを決めていなかった。

決めていないことが表に出たのが `promise/prefer-await-to-then` と `no-promise-chain--use-async-await` である。文書化された 10 通りの書き方すべてで両者の判定が一致し、同じ箇所に 2 本とも error を出す。どちらかを消せばよいことは分かるが、どちらを消すのかを決める根拠が無かった。

この判断を「その都度考える」に残すと、ルールが増えるたびに同じ議論が起きる。しかも重なりは実際に違反を書いてみるまで見つからないので、気付きが属人的な作業に落ちる。

## 決定

**公式のルールを既定にする。** 同じ不変条件を守る組み込みルールがあるなら、それを使う。自前で書かない。

**自前で書いてよいのは、公式のメッセージを読んでも何を直せばよいかが決まらないときだけ。** 判定の精度ではなく、報告文が読み手を次の行動に導けるかどうかで決める。[0023](0023-state-the-prohibition-then-the-fix-in-lint-messages.md) が報告文に求めているのは禁止と修正の 2 つで、公式のメッセージがその 2 つ目を持たないなら、その不変条件については公式が答えを出し切っていない。

**自前で書いたら、同じ不変条件を見ている公式ルールを off にする。** 権威を 1 つにするためである。2 本が同じ箇所を報告すると、書き手はどちらを黙らせるかを選べてしまう。

## なぜ「メッセージ」を基準にするのか

判定の精度を基準にしなかった理由が 2 つある。

1 つ目は、精度で比べると自前が勝つ場面がほとんど無いことである。今回の突き合わせでも、公式は 10 通りすべてを捕らえ、検出しないと決めている 9 通りでは 1 件も出さなかった。自前と完全に同じ振る舞いだった。精度を基準にすると、自前を書く理由はほぼ消える。

2 つ目は、精度は上流が上げてくれるが、報告文は上げてくれないことである。上流のメッセージは一般的な言い換えまでしか書けない。「このリポジトリではこう直す」「その判断はここに書いてある」を書けるのは、リポジトリを知っている側だけである。つまり自前で書く価値があるのは、判定ではなく報告文の側にしかない。

## 「検出は公式、報告文は自前」ができない理由

この 2 つを分けられれば理想だが、oxlint の設計上できない。調べた結果を残す。

- 組み込みルールは Rust の実装で、JS プラグインから掴む口が無い。`@oxlint/plugins` の export にルールオブジェクトは無く、[JS Plugins](https://oxc.rs/docs/guide/usage/linter/js-plugins) にもその API は書かれていない
- 名前とメッセージはルールのソースに埋め込まれている。`declare_oxc_lint!` マクロが名前とカテゴリを宣言し、メッセージは `OxcDiagnostic::warn("...")` という関数リテラルで、設定から差し込む口が無い
- [Configuration](https://oxc.rs/docs/guide/usage/linter/config) の `alias` は JS プラグインに別名を与えて native プラグインとの衝突を避けるための機能で、組み込みルールの改名には使えない
- `oxc_linter` クレートは `publish = false` で、外部に API を約束していない。借りるなら git のコミット固定になり、上流が動くたびに追随の費用を払う

したがって選べるのは「報告文を所有する（自前で書く。検出も自分で持つ）」か「公式の検出に乗る（公式のメッセージを受け入れる）」の二択で、その中間は存在しない。

## 影響

**`promise/prefer-await-to-then` を off にした。** `no-promise-chain--use-async-await` が同じ不変条件の唯一の権威になる。自前を残したのは、公式のメッセージが `Prefer await to then()/catch()/finally()` で止まり、失敗経路をどこに置き直すのかを言えていないためである。自前の側は `await` を囲む `catch` 節と `finally` 節という置き場所まで書いている。

**ルールを足すときの順序が決まった。** まず oxlint のカタログを引き、同じ不変条件を守るものがあるかを見る。あればそれを入れて終わり。無いか、あってもメッセージが直し方を決められないときだけ自前を書く。

**自前ルールが減る方向に働く。** 既にある 15 本のうち、公式に同等品があってメッセージも足りているものがあれば、この方針では公式へ寄せることになる。今回の突き合わせでは該当が無かったが、oxlint がルールを増やすたびに再点検の対象になる。

## 検討して採らなかった案

**`oxc_linter` をフォークし、napi で TypeScript から呼ぶ。** TypeScript から Rust を呼ぶ手段（napi-rs）は確立していて、oxlint 自身がそれで配られている。詰まるのはその手前で、クレートが `publish = false` である以上、借りるのは API の約束が無いコードになる。名前とメッセージを変えるにはルールのソースを書き換えることになり、それはフォークの維持である。週次で動く上流に追随し続ける費用を、ルール名のために払うことになる。

**診断を後処理して名前とメッセージを差し替える。** oxlint を走らせて JSON 出力を書き換える層を挟めば、全 256 本に手が届く。名前まで変えると `oxlint-disable-next-line <自前の名前>` が効かず、`reportUnusedDisableDirectives: error` の下では書いた側が誤爆で怒られる。追記だけに留めれば壊れないが、追記する中身（各ルールについて mst がどう直すか）が今どこにも無く、それを書き下ろすのが本体になる。この案は捨てたのではなく、対応表を持ってから改めて判断する。

**上流の ESLint プラグインの JS ルールを包む。** 実際に動くことは確かめた。`eslint-plugin-promise` の `prefer-await-to-then` をルールの `create` に据えると、mst の名前・文面・文書への案内で報告される。採らなかったのは、実測で上流の JS 実装が oxlint の移植より狭かったためである。`settled["then"](handle)` を上流は取りこぼし、oxlint は捕らえる。検出を上流に預ける案が検出を落とすなら、預ける意味が無い。
