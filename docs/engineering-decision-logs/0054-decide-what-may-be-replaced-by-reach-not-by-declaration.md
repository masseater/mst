# 0054. ダブルを立ててよい対象は、宣言ではなく依存の到達で決める

- ステータス: Accepted
- 日付: 2026-08-13

## 文脈

[テストの書き方](../guidelines/tests.md)は「置き換えてよいのは、そのテストがもともと何も主張していない領域だけである」を 2 つの禁止で書いている。入力から出力が決まるプロセス内の依存を置き換えないこと、外部プロセスの失敗を作るときは置き換える位置を境界に留めることの 2 つである。

規範はあったが、強制する層が無かった。ダブルまわりのルールは 6 本あるが、どれも「その境界の正しい扱い方」か「ダブルの書き方」を見ている。`no-local-file-system-mock--use-shared-fs` はファイルシステムの扱い方を、`no-handmade-standard-io-double--use-standard-io-test` は標準入出力の扱い方を、`no-vi-mock-factory-behavior--use-spy-true-and-fixture` はダブルの中身を見る。**そもそも差し替えてよい対象かどうか**を見るものは無かった。

差し替えた対象について、そのテストは何も主張しなくなる。範囲外のものを差し替えたテストは、検証できたはずのものを自分で run から外して、残ったものを証拠として提出している。それは赤くならない。

## 決定

**`no-non-boundary-double--replace-at-the-external-boundary` を足し、差し替えの対象が外部 I/O の境界かどうかを依存の到達で判定する。**

spec に書かれた差し替えの指定子を解決し、このリポジトリのモジュールに当たったものだけを見る。解決できない指定子（node の組み込みと `node_modules`）はリポジトリの外にあり、そこが境界なので通す。

解決できた対象については、そのモジュールが外部 I/O を**直接** import しているかを見る。していれば境界そのものなので通す。していなければ import を推移的にたどり、2 つに割る。

- たどった先にも境界が無い → 入力から出力が決まるモジュールである
- たどった先に境界がある → 対象は境界の手前に立っており、間のモジュールごと run から外している。報告文はその境界のモジュールを名指しする

## 根拠

### 宣言ではなく到達で決める

「差し替えてよい対象の一覧」を設定に宣言して突き合わせる形も採れた。採らなかった。それは判定ではなく宣言の移動であり、一覧が正しいかを誰も検証しない。一覧に載せた瞬間にどのモジュールも差し替えてよくなるので、規範が設定ファイルの編集で無効化できる状態になる。

到達で決めれば、根拠はコードの側にある。あるモジュールが外部 I/O を持つかは、そのモジュールが何を import しているかで決まる。判定を変えたければ import を変えることになり、それは実装の設計変更として現れる。

### 人が宣言するのは `node_modules` のパッケージ名だけ

到達判定の入力は「どのモジュールが外部 I/O を持つか」で、3 つに割れる。リポジトリ内のファイルは計算できる。node の組み込みは名前で決まるのでルールが既定として持つ。`node_modules` のパッケージだけは中まで辿るのが高コストで、辿っても読めないことがあるため宣言に頼る。

宣言はルールのオプション `externalIoPackages` に置き、利用するリポジトリが自分の依存について書く。既定は空である。このリポジトリでは `@opentelemetry/exporter-metrics-otlp-http` を並べた。`packages/lint-rule-authoring/src/lint-telemetry.ts` がそれを直接 import しており、そこが計測値を外へ出す境界だからである。

### 既存の 3 本と重ならない

ファイルシステムと標準入出力はこのリポジトリの外にあるので、本ルールから見れば境界そのものであり報告しない。同じ差し替えを 2 本が別々の言葉で報告する状態は作らない。

## 影響

リポジトリにある差し替えの宣言 10 箇所のうち、報告されたのは 1 箇所だった。`packages/lint-rule-authoring/src/measure-rule-duration.test.ts` が `./lint-telemetry.ts` を差し替えている形で、語彙に exporter を載せるまでは「入力から出力が決まるモジュール」と読まれていた。載せた後は境界として通る。残る 9 箇所は node の組み込みか `node_modules`、あるいは外部 I/O を直接持つモジュールだった。

判定は spec のファイルシステム解決を伴うため、ルール本体は判定を注入で受け取る形にした。`no-class-as-mutable-cell--decide-in-an-iife` が索引の読み込みについて採っている形と同じで、ルールのテストは走査を伴わずに 4 つの結論だけを与えられる。

## 判定が届かない範囲

- `vi.spyOn(object, "member")` は対象がモジュールではなくオブジェクトなので、この解析が効かない。標準入出力への spy は `no-handmade-standard-io-double--use-standard-io-test` が受け持つ
- 実行時に組み立てた指定子は読めない。`forbid-unresolvable-module-specifier--write-a-statically-resolvable-specifier` が塞いでいる
- 再 export をまたぐ同定には限界がある。型情報を使わず、指定子の解決とファイルの import だけを見ている
