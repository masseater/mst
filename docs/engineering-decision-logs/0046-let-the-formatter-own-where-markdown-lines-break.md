# 0046. markdown のどこで行が折れるかは整形器に持たせる

- ステータス: Accepted
- 日付: 2026-08-13

## 文脈

markdown の段落を書き手が任意の幅で折り返しても、レンダリングされた結果は変わらない。それでも折り返しの位置は差分に現れる。1 語足しただけで段落の残り全部が折り直され、変わっていない文が変更行として並ぶ。読む側は、意味が変わった行と折り返しが動いただけの行を毎回選り分けることになる。

実測すると、リポジトリの markdown 195 ファイルのうち 10 ファイルが段落の途中で改行していた。日本語の文書は 1 段落 1 行で書かれ、英語で書かれた `skills/**/SKILL.md` と `skills/CHANGELOG.md` が 80 桁前後で折り返されていた。同じリポジトリの中で 2 つの流儀が並んでおり、どちらで書くかは書き手ごとに決まっていた。

さらに、折り返しは見た目に影響しないとは言い切れない。日本語の段落を途中で改行すると、HTML の描画で改行が空白になり、本文に無いはずの空きが入る。`0043` の本文はこれに当たっていた。

oxfmt は markdown を整形する。`vp fmt` の経路でも `.md` に届いており、`proseWrap` が段落の折り返しを決めている。既定の `"preserve"` は書き手が置いた改行をそのまま残すので、この選択は書き手に委ねられていた。

## 決定

**`proseWrap: "never"` を preset に置き、段落を 1 行に畳む。** 折り返しの位置は書き手の判断から外し、整形器が持つ。表示上の折り返しは読む側のエディタとビューアに任せる。

`vp check --fix` が畳むので、書き手は折り返しを意識しない。畳んだ結果は、英語では空白 1 つで、日本語では何も挟まずに繋がる。この使い分けは oxfmt が持っており、こちらで幅や語境界を計算しない。

導入時点の 63 ファイルを畳んだうえで、GitHub の markdown API に変更前後の両方を通し、正規化した HTML を突き合わせた。描画が変わったのは 2 か所だけで、1 つは下に書く alert の記法、もう 1 つは `0043` の日本語段落から余分な空白が消えたものだった。

## 影響

段落の折り返しがレビューの対象から消える。差分に残る markdown の行は、意味が変わった行だけになる。

`printWidth` を超える幅の表は、列ごとのパディングが落ちて最小幅になる。`0029` が分担の前提として書いた「oxfmt は markdown の表を列ごとにパディングして揃える」は、幅が収まる表にだけ当てはまる記述になった。分担そのものは変わらず、字面の権威は引き続き整形器にある。日本語を含む表のパディングは表示幅の計算が区切り行とずれており、揃っていたのは字面の上だけだった。

GitHub の alert は、マーカの次に本文が続く形（`> [!NOTE]` の次行に `> 本文`）で書くと 1 行に畳まれ、alert として描画されなくなる。マーカの後ろに `>` だけの行を置く形は畳まれず、GitHub の描画も alert のままである。alert を書くときはこちらを使う。

`.md` に対する整形はこの選択の前から効いていた。変わったのは `proseWrap` の値だけで、整形の対象は広がっていない。
