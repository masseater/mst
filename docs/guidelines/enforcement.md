# 強制の機構

この文書が守るのは、検査を通った変更と、検査されていない変更が見分けられる状態である。判定する道具と、その判定が走る経路の両方が要る。道具を足しても走る経路に入っていなければ設定に名前があるだけになり、経路を厚くしてもそこで走るものが何も判定しなければ通過の記録が増えるだけになる。

mst ではこの見分けが 2 度つかなくなっていた。まとめて走らせる入口が呼ぶ knip は、ゲートとして数えられながら 1 件も報告していなかった（[0018. 公開面を実際に使われている分だけにし、機械に見張らせる](../engineering-decision-logs/0018-narrow-the-export-surface-to-what-is-used.md)）。oxlint の correctness のルール群は、`categories` を書いていなかったために warn のままで、`vp check` の終了コードを動かしていなかった（[0012. 既定で無効な oxlint のルールを入れ、閾値と重大度を mst の判断で置く](../engineering-decision-logs/0012-adopt-oxlint-rules-that-are-off-by-default.md)）。どちらも結果が不合格ではなく空白になり、止める理由が無い状態として通過していた。

この 2 件はどちらも、走っていたかどうかの失敗である。だから節は、走ったか、落ちるか、何を守れるかの順に置いてある。守れる範囲がどれだけ広くても、走っていない検査は何も見ていない。

## 走らなかった検査を成功と数えない

対象から外れた検査と、再利用で飛ばされた検査は、どちらも走らなかったのに成功として報告される。mst ではこの形が実際に作られていた。走査の途中で読めないディレクトリを空として扱っていたため、その配下がすべて対象から消え、検査は緑のままだった（[0015. 失敗が値に化けてよい範囲を決める](../engineering-decision-logs/0015-decide-what-a-failure-may-become.md)）。キャッシュ再利用をどの範囲に効かせるかは設定が決めるので、この節はその設定が及ぶ定義すべてに効く。

- IF: ゲートとして数える実行を条件で絞り込みたい; THEN
  - MUST: 起動した後の階層で絞り込む
  - PROHIBIT: 起動そのものの条件で絞り込む
    - 起動しなかった実行は結果を持たない。落ちたのか走らなかったのかが、通過の記録から区別できなくなる
- IF: その実行をゲートとして数えないと確定でき、起動そのものの条件でしか絞り込みを表現できない; THEN MAY: 起動の条件で絞り込む
- IF: 検査や公開が失敗した; THEN
  - MUST: 失敗のまま伝播させる
  - PROHIBIT: 暗黙のスキップ・握り潰し・継続許可で成功に読み替える
- IF: パッケージ内で閉じる品質作業の対象を選ぶ; THEN
  - MUST: 依存グラフとキャッシュを持つタスクランナーに選択を任せる
  - PROHIBIT: その前段に別の絞り込みを重ねる
- IF: 実行の段取りの記述だけが変わった; THEN PROHIBIT: 対象の選択を広げる
- IF: 依存構造そのものが変わり、影響範囲を局所化してよいかを判断できない; THEN MUST: 対象の選択を広げる
- IF: 品質ゲートの走査範囲を決める; THEN MUST: 配布物に入るコードの実際の配置に追随させる
- IF: 対象集合を解決する; THEN
  - IF: 前段の結果を受け取って対象を決める構造にしたく、対象が単一に閉じている; THEN MAY: その構造を採用する
  - IF: 対象が単一に閉じていない、または前段の結果を受け取らない; THEN MUST: その操作を実行する側のコマンドの中で解決する
- IF: キャッシュ再利用の既定をまとめて切り替える設定を書く; THEN
  - MUST: その切り替えが及ぶ定義を数え上げ、1 つずつ性質を確かめる
  - PROHIBIT: 個々の定義を確かめずに、キャッシュ再利用の範囲を広げる
    - まとめて切り替える設定は、タスクとして書いた定義と `package.json` の `scripts` のどちらにも及びうる
- IF: ファイルを変更することが目的の定義を書く; THEN PROHIBIT: キャッシュ再利用の対象にする
- IF: 常駐プロセスを起動する定義を書く; THEN
  - PROHIBIT: キャッシュ再利用の対象にする
  - MUST: 常駐であることをランナーに宣言する
- IF: 既定の入力集合を、自分で書いた集合で置き換える; THEN MUST: そのタスクを実装するワークスペースの実際の入力をすべて数え上げる

## ガードが落ちることを確かめる

設定に名前が出ることは、そのガードが走ることを意味しない。mst で有効に見えて 1 件も見ていなかったガードは 2 つあり、どちらもオプションを 1 つ渡していなかったことによる（[0018. 公開面を実際に使われている分だけにし、機械に見張らせる](../engineering-decision-logs/0018-narrow-the-export-surface-to-what-is-used.md)）。新しく `plugins` に入れた系統は、違反を仕込んで報告が出るところまで確かめてから入れている（[0016. 既製のルールで守れるものは既製のルールに守らせる](../engineering-decision-logs/0016-enforce-with-upstream-rules-before-writing-our-own.md)）。

- IF: ガードを追加した; THEN
  - MUST: 違反を仕込んだ入力で、実際に報告が出ることを確かめる
  - MUST: 違反とみなさない入力で、報告が出ないことを確かめる
  - PROHIBIT: 実装や設定に存在することをもって、検出できているとみなす
- IF: 不変条件に違反したコードがガードをすり抜けているのを見つけた; THEN
  - MUST: コードを直す
  - MUST: ガードの落ちるべき入力に、その抜け道を足す
- MUST: ガードの報告に、破られた不変条件と直す方向の両方を含める
- IF: 安全で決定的な直し方がちょうど 1 つに定まる; THEN MUST: 自動修正を用意する
- IF: 有効な直し方が複数残る; THEN PROHIBIT: 自動修正を用意する
- MUST: 自動修正が安全に終えられない部分を、失敗するガードとして見える状態に残す

## 何を守れる機構かで選ぶ

判定する側は 3 種類ある。**強制**は不正な状態を自動的に拒否するもので、mst ではまとめて走らせる入口が並べるコマンドがこれにあたる。**記録**はなぜそう決めたかを保つもので、`docs/engineering-decision-logs/`、この `docs/guidelines/`、`packages/dont-review-it/docs/lint/` がこれにあたり、違反を止めない。**安定した基準**は、要求される状態と違反の境界の両方が決着しているもので、方向性だけあって境界が決まっていないものはここに入らない。`.github/workflows/ci.yml` と `.vite-hooks/` のフックはどれでもなく、まとめられた検査を起動するだけの経路である。

違反を判定するのに何を見る必要があるかで、載せられる機構がほぼ一意に決まる。1 ファイルの構文だけで決まるものは型と lint が、実行して初めて分かるものはテストが、複数のファイルや宣言をまたぐ突き合わせは検証コマンドが受ける。どの材料も揃わないものだけが、規範の散文とレビューで見る項目に残る。いまどれが動いているかは、まとめて走らせる入口の定義が持つ。

- PROHIBIT: 根拠を残したことをもって、その基準が強制されているとみなす
- MUST: その不変条件の全体を確実に守れる機構を、主たるガードにする
- PROHIBIT: 一部しか守れない機構を、主たるガードにする
- IF: 複数の機構が同じだけ確実に守れる; THEN MUST: 失敗が返るまでの距離が短いほうを採る
  - 型と lint の失敗は `vp staged` が pre-commit で返し、まとめて走らせる入口の失敗は merge か CI まで返らない
- IF: 不変条件が、ふるまいと実行時の境界を通る値の両方に掛かっている; THEN MUST: 両方に届く機構を置く
  - 片方だけを置くと、覆えなかった側が無検査のまま残る
- IF: 不変条件がどちらか一方だけに掛かっている; THEN MUST: その一方を見る機構を選ぶ
- IF: 既にその不変条件を表現できるガードがある; THEN
  - MUST: それを設定するか拡張する
  - PROHIBIT: 並行する新しい検出器を作る
- IF: 既存のガードがその不変条件を確実には表現できない; THEN MUST: 確実に守れる機構を新しく置く
- IF: どの機構もその基準を確実に評価できないと確認できた; THEN MUST: レビューで見る項目として残す
- IF: 安定した基準に対して機構を選んだ; THEN MUST: どの機構で止めたかと、選ばなかった候補では何を守りきれなかったかを、その決定の記録に含める
- IF: 選んだ機構を別の機構へ移した; THEN MUST: 移した理由を同じ場所に残す
- PROHIBIT: 機構の選択の根拠を、ガードの実装やその設定だけに残す

同じ不変条件を守る公式のルールを先に探すこと、どの順に検討するか、自前で書いてよい条件と書いたあとの後始末は [AGENTS.md](../../AGENTS.md) が持つ。決定の記録をどこに置くかも同じ文書が決めている。テストを機構として使うときの書き方は [テスト](tests.md)、ガードをどのワークスペースに置くかは [置き場所と道具](placement-and-tools.md) が持つ。

## ガードを入れる時点

守るのは、基準が決まってからガードが入るまでの間に、その基準を破れる期間を作らないことである。mst の関数の上限は、そこから逃げる番号分割を塞ぐルールと同じ変更で入っており、逃げ道が開いていた期間が存在しない（[0014. 関数の大きさに上限を置き、そこから逃げる番号分割を同時に塞ぐ](../engineering-decision-logs/0014-bound-function-size-and-forbid-numbered-splits.md)）。逆に、英語を強制するかが決まらないうちは、それを見る検査を置いていない（[0005. コメント構文に残すのは機械が読む宣言だけにする](../engineering-decision-logs/0005-reserve-comment-syntax-for-machine-read-declarations.md)）。

- IF: 基準が決着していて、機械的に検出できる違反が予見できる; THEN MUST: その基準を導入する変更、または最初の違反を直す変更と同じ変更でガードを入れる
- PROHIBIT: 二回目の発生を待つ
- IF: 議論が決着していない; THEN
  - PROHIBIT: 自動化する
  - PROHIBIT: 拘束力のある散文として書く
- IF: レビューで人が毎回同じ判定をしている項目があり、その判定を機械が評価できる; THEN
  - MUST: その項目をガードに置き換える
  - PROHIBIT: ガードを足したうえで、同じ判定をレビューで見る項目として残す

同等の検査が有効なときに人が重ねて見るかどうかと、検査が無効な環境でその項目が人に戻る扱いは [中核原則](principles.md) が持つ。

## 強制度を落とすときの形

強制度を落とす操作は、落とした範囲をそのまま恒久の免除に変える。範囲を誰が決めたかが残っているかどうかが、免除と放置を分ける。使われなくなった抑制ディレクティブ自体は、共有プリセットが error で落とす。

- IF: 既存の違反があってすぐ全体を強制できない; THEN MUST: 強制度を落とす範囲を、個別に名指しした既存のファイルに限る
- IF: パターンの単位で強制度を落とす; THEN
  - MUST: その判断と、何が守られなくなるかを決定の記録に残す
  - PROHIBIT: 記録を伴わないまま範囲を開く
- MUST: 解消済みの違反に残っている抑制を、違反そのものと同じ扱いで落とす
- MUST: 抑制を、違反したその一行だけに掛かる形に限る
  - 無効化と再有効化を対で囲むと、その間に足されたコードが、誰にも意識されないまま免除に入る
- IF: 一時的に強制度を落とした; THEN MUST: その違反が解消した変更と同じ変更で戻す

検出の形だけを外して報告を消す書き換えの判定は [レビューの指摘](review-findings.md) が持つ。lint ルールの重大度を落としてよいかは [AGENTS.md](../../AGENTS.md) が持つ。

## main に入る経路をすべて同じ検査に通す

main に変更が入る経路は 2 つある。ブランチを転送してから入れる経路では `.github/workflows/ci.yml` がゲートになり、手元の main へ直接 merge する経路では merge の時点で走る `.vite-hooks/` のフックがゲートになる。後者の配置と、fast-forward という形を `merge.ff false` で消すこと、その設定が無い手元のために `post-merge` を後ろ盾に置くことは [0009. main への merge をフル検査で止める](../engineering-decision-logs/0009-gate-the-merge-into-main.md) が決めている。

- MUST: main に変更が入るすべての経路を、同じ検査のまとまりに通らせる
- PROHIBIT: 経路ごとに実行する検査の集合を別に持つ
- IF: ゲートを迂回できる形が残っている; THEN MUST: 迂回したことを出力で見える状態にする
- IF: ゲートの有無が手元の設定に依存する; THEN
  - MUST: その設定を、依存の導入手順が毎回書き込む形にする
  - PROHIBIT: 手順を文書に書いただけで、設定されているとみなす

## 実行の定義に書いてよいもの

mst の定義ファイルは、持ってよいものが違う。`package.json` の `scripts` は、コマンドの名前と、その名前が指す 1 本の呼び出しを持つ。`vite.config.ts` は、タスクどうしの依存とキャッシュの性質を持つ。`.github/workflows/ci.yml` は、起動の条件と、走らせるコマンドの並びを持つ。このどれかで分岐・再試行・対象探索が育つと、そのコードは型も自動テストも持たないまま、その定義ファイルの上でしか実行されないものになる。手元と自動化で挙動が食い違い、失敗の原因調査が定義ファイルの評価順序まで降りていく。

- IF: このいずれかに実行ブロックを書く; THEN
  - MUST: 1 つのコマンド呼び出しに留める
  - PROHIBIT: 再試行・繰り返し・分岐・エラー処理・対象探索をそこに書く
  - MUST: それらが必要になった時点で、型と自動テストを持つリポジトリ内のコードへ移す
- IF: 同じまとまりが定義ファイルの中で増えた; THEN MUST: 単一のまとまりへの参照で解消する
- IF: 増えたものが順序を持つ手順の並びである; THEN MUST: 再利用できる部品への切り出しで解消する
  - 参照で置き換えられるのは、そのまとまりが丸ごと同じ位置で使われる場合に限る。並びの一部だけを別の場所に置きたくなった時点で、部品として切り出すことになる
- MUST: どちらを使うかの閾値を数値で固定し、検査の設定に持たせる
  - 数値はこのリポジトリの定義ファイルの実態から決める

いつ重複とみなして統合するかは [中核原則](principles.md) が持つ。リポジトリのルートから呼べる入口が委譲だけを持ち、複数ワークスペースにまたがる振る舞いをそこに実装しないことは [置き場所と道具](placement-and-tools.md) が持つ。この文書で要るのは、その規律が守られている限り、定義ファイル側へ振る舞いが染み出す経路も塞がるという関係である。

## 源と生成物

mst が源から導いている成果物は、`pnpm-lock.yaml`、`vp config` が書く `.vite-hooks/_/`、`docs/workspaces.md` と `AGENTS.md` の生成領域である。導出できるものを独立した表現として保守すると、1 つの事実が 2 か所で別々に動きはじめる。生成は、そこから手作業の入る余地を取り除く操作である。

- MUST: 真実の源から決定的に導ける成果物を、生成して得る
- IF: 生成物に対する操作が 2 つ目の表現を作りうる; THEN
  - MUST: 内容を変えたいときは、源を編集して生成し直す
  - PROHIBIT: 生成物を直接編集する
  - PROHIBIT: 1 つの生成物に 2 つ目の生成の経路を作る
- IF: 生成物をコミットしている; THEN
  - MUST: 源の変更と生成された出力を、同じ変更に入れる
  - MUST: 源から乖離したことを機械的に検出する経路を付ける
    - `docs/workspaces.md` と `AGENTS.md` の生成領域については、規範文書の検査がこの経路にあたる

自動化が所有する変換をどう扱うかの一般形は [中核原則](principles.md)、生成器の出力をコードとしてどう書くかは [コードの書き方](writing-code.md) が持つ。

## 機械だけが読み書きする成果物

読み手も保守する側も機械である成果物がある。mst では `pnpm-lock.yaml`、`vp config` が生成して git の管理から外れる `.vite-hooks/_/`、`node_modules/.cache/` に置く導出結果のキャッシュ（[0006. 導出結果のキャッシュに抽出ロジックの版を持たせる](../engineering-decision-logs/0006-version-the-derived-catalog-cache.md)）がこれにあたる。一方で `AGENTS.md` と `docs/workspaces.md` は人間向けの文書でありながら生成領域を内側に持つ。パスだけでは分けられない。

- PROHIBIT: 置かれているパスだけを根拠に、機械向けの成果物として分類する
- IF: 人も機械も読む文書である; THEN MUST: 人間向けとして扱う
- PROHIBIT: 人間に対して拘束力を持つ内容の正本を、この種の成果物に置く
- PROHIBIT: 人間向けの規範文書が、正本としてこの種の成果物を指す
- IF: この種の成果物に人間向けの規範が混ざっているのを見つけた; THEN MUST: その主題を所有する規範文書へ移す
- IF: 機械にとっての有用性と、人間に対する拘束力の所在が衝突する; THEN MUST: 拘束力のある内容を人間向けの文書に置く判断を先に取る
- MUST: この種の成果物を、機械にとっての有用性と構造の妥当性で評価する
- PROHIBIT: この種の成果物の散文を、人間向けの文章としての質を理由に差し戻す
- IF: 形式を所有するツールがある; THEN
  - MUST: 作成・更新・改名・削除を、そのツールを通して行う
  - PROHIBIT: ツールの外で手編集する
    - 所有するツールは、そのファイルには現れない索引や識別子の対応を併せて管理している
- IF: この種の成果物をいつ保守するか決める; THEN
  - MUST: 使っている側が具体的な必要を検知した時点に任せる
  - PROHIBIT: 固定の周期や、人間側の工程に紐づける
  - MUST: リポジトリ全体に効く安全性と正しさの制約を、その裁量の外側に置く

人間が読む文書の書き方と置き場所は [文書](documents.md) が持つ。

## 実行単位を分ける軸

自動化の実行単位は `.github/workflows/ci.yml` にまだ 1 つしかない。この節は 2 つ目を足した時点から効き始める。

- IF: 自動化を新しい実行単位に分けるか既存に足すかを決める; THEN
  - MUST: 起動のタイミングとライフサイクルを軸に分ける
  - PROHIBIT: 機能名・パッケージ名・担当領域を軸に分ける
- IF: 実行単位に名前を付ける; THEN MUST: 起動のタイミングかライフサイクルが読み取れる名前にする
- IF: 起動のタイミングが独立していて、失敗したときに巻き込む先が他と揃わない自動化がある; THEN MUST: 独立した実行単位に置く
  - 同居させると、一部の自動化のために宣言した広い権限を、残り全部が常時持つことになる
- IF: 複数の実行単位から使う部品を作る; THEN
  - MUST: 呼び出す側にトリガを持たせる
  - PROHIBIT: 部品自身にトリガを持たせる
- IF: 互いの結果や出力を参照し合う処理がある; THEN
  - MUST: 同一の実行単位の中に置く
  - PROHIBIT: 実行単位をまたいで結果を受け渡す

## 外へ出す操作を始めたときに効くもの

この節の規範は、実行が自分の外へ何かを出す経路が現れた時点から効く。mst にはパッケージを公開する経路も、外部状態を変える操作も、掲示される報告も、実行の外側から取得される成果物も無い。`ci.yml` が宣言している権限は `contents: read` だけで、いずれも発火しない。公開されたものは取り消せないため、経路ができてから規律を決めるのでは間に合わない。

- IF: パッケージを公開する、または外部状態を変える; THEN
  - MUST: レビューを経たリビジョンから、自動化された経路で実行する
  - PROHIBIT: 検証されていない手元の作業ツリーから実行する
- IF: 外部状態を変える操作が特定の成果物を前提にする; THEN MUST: 外部状態を変える前にその成果物の同一性を確認する
- IF: パッケージを公開する; THEN MUST: 実際に梱包される成果物そのものを公開の前に検査する
- IF: 成果物の生成側と、それを前提に外部状態を変える消費側がある; THEN
  - MUST: 生成から消費までを 1 つのまとまりとして扱う
  - PROHIBIT: 消費側だけが対象に選ばれる経路を残す
- IF: 外部状態を変える操作、または外部に問い合わせる検査を実行する; THEN MUST: 明示的な対象集合を与える
- IF: ある処理が品質作業か外部への副作用かを判別しづらい; THEN MUST: 外部への副作用として扱う
- IF: 資格情報を実行単位に渡す; THEN
  - MUST: ソースを取得する権限を、読める範囲を絞ったものにする
  - MUST: 外部に書き込む権限を、実行単位が宣言した権限としてその実行に帰属させる
- IF: 自動化が報告を生成する; THEN
  - MUST: 生成したコマンド自身が、単一の所有された経路で、決まった掲示先に出す
  - PROHIBIT: 報告の生成と掲示を別の工程に分ける
  - PROHIBIT: 複数の経路から同じ掲示先を書き換える
- IF: 報告を単一の集約先に出すか、独立した掲示にするかを迷う; THEN
  - MUST: 単一の集約先に出す
  - MAY: 1 回の実行中に何度も更新される報告に限り、独立した掲示にする
- IF: 実行の外側から取得される成果物を出力する; THEN MUST: プラットフォームの標準 API と標準 CLI から列挙・取得できる保管先に置く
- IF: 成果物が同一実行内の受け渡しにしか使われない; THEN MAY: 送り側と受け取り側が同じ機構で対になっている限り、標準 API から見えない保管先に置く
- IF: 外部から参照される成果物の集合を定義する; THEN
  - MUST: 1 箇所で定義する
  - PROHIBIT: 検査と文書、または複数の一覧に同じ集合を持たせる

資格情報そのものの持ち方、目的ごとの分け方、実行単位が宣言する権限を要るものだけに限ることは [秘密と権限](secrets-and-permissions.md) が持つ。この節が足すのは、外部へ出す操作の側でもその分離と宣言が同じように要るという条件だけである。

## 機械がどこまで判定するか

境目は重要度ではなく、判定に要る材料がどこにあるかである。材料がリポジトリの中に閉じていて、基準が構文の形か 2 つの表現の突き合わせに落ちるものは、機械が判定する。どの機構を主たるガードにしたか、選ばなかった候補を記録に残したか、置いたガードが違反を仕込んだ入力で実際に落ちるかは、材料が「なぜそう決めたか」の側にあるので残る。ある規律に対応する検査が有効かどうかは、そのつど設定の側を見て確かめる。

- MUST: レビューで見る項目を、その主題を所有する規範文書に置く
- PROHIBIT: 人が見る項目だけを横断的に集めた置き場所を作る
  - 所有者の決まっていない項目の受け皿にもなり、何を入れてよいかに答えられない置き場所として膨らむ
- MUST: レビューで見る項目に出会うたびに、これは本当に機械化できないのかを問い直す

機械が見ていないことを、その基準を満たさなくてよい根拠にしない扱いは [中核原則](principles.md) が持つ。レビューで見つけたものをどう扱うかは [レビューの指摘](review-findings.md) が持つ。
