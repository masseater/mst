# @mst/verified-specifications

## このパッケージが守るもの

AI がコードに込めた仕様の解釈を、人間が読んで誤りに気付ける形で表に出す。

AI は人間の指示の不明瞭な部分を独自に解釈して進める。その解釈は実装とテストの中に埋まり、人間はコードを読まない限り気付けない。このパッケージは仕様担保テストの主張文を抽出して人間向けの一覧を生成し、解釈の変化を PR の差分として読めるようにする。

仕様の真実の源は仕様担保テストである。テストに書かれていない主張は仕様ではなく、一覧はテストから機械が生成する。人間が一覧を直接編集することはない。

## テストの種別

- `specs/<機能名>.spec.ts` — 仕様担保テスト。パッケージ直下の `specs/` に、機能単位で守るべき振る舞いの主張を宣言する
- `<ソース名>.test.ts` — カバレッジ担保テスト。対象ソースと同じディレクトリに置き、カバレッジの下限を満たすために分岐を踏む

仕様担保テストは内部モジュールの単位ではなく、利用者から見える機能の単位で書く。e2e ほど外側ではないが、ユニットテストより外側の立ち位置になる。

## 検査

- 仕様担保テストの最上位 `describe` と直下の `it` の名前が文字列リテラルである
- `it` が最上位 `describe` の中にある
- 各ワークスペースの `SPECIFICATIONS.md` が仕様担保テストからの抽出結果と一致している
- 仕様担保テストを持つワークスペースの tsconfig が `include` / `files` / `exclude` で検査対象を絞っていない
  - 絞ると `specs/` が型検査から静かに抜け、検査は緑のまま主張だけが残る

## 規約

- IF: 振る舞いの主張を書く; THEN
  - MUST: `specs/<機能名>.spec.ts` に書く
  - MUST: 最上位 `describe` の名前を仕様の主題にし、その直下の `it` の名前を主張文にする
  - MUST: 主張文を、生成された一覧だけを読む人に伝わる日本語の 1 文で書く
  - PROHIBIT: `test` 関数を使う
    - 主張は対象を主語にした振る舞いの文であり、`it` はその文の形を促す
  - PROHIBIT: 内部モジュールの実装都合を主張として書く
    - 利用者から見えない主張が一覧に混ざると、人間が読む仕様が薄まる
- IF: カバレッジの下限を満たすためのテストを書く; THEN
  - MUST: 対象ソースと同じディレクトリの `<ソース名>.test.ts` に書く
  - PROHIBIT: `specs/` に書く
    - 主張ではない実行が一覧に混ざると、人間が読む仕様が薄まる
- IF: どちらの種別か迷う; THEN MUST: そのテストが落ちたとき仕様違反と言えるかで決める
  - 言えるなら仕様担保テスト、言えないならカバレッジ担保テスト
- IF: `SPECIFICATIONS.md` を更新したい; THEN
  - MUST: 仕様担保テストを変更し、`vp run guard:fix` で再生成する
  - PROHIBIT: `SPECIFICATIONS.md` を直接編集する
    - 一覧はテストからの生成物であり、直接の編集は次の生成で消える
