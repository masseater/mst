# require-spec-or-assets-only-in-spec-directory--move-out-or-inline

## 何を検出するか

spec 用に名付けられたディレクトリの下にある、spec でもテストデータでもないファイルを報告する。

対象を決めるのはファイル名とディレクトリ名だけである。リポジトリの木を 1 回走査し、各ファイルのパスを先頭から見て、ディレクトリの区切りのどれかが spec 用ディレクトリの名前（既定では `test` `tests` `__tests__` `spec` `specs` `__specs__`）に一致するかを見る。一致した最も外側のディレクトリが、そのファイルの属する spec 用ディレクトリになる。そのうえでファイル名を見て、spec の接尾辞（既定では `.test.ts` `.test.tsx`）で終わるか、テストデータの目印（既定では拡張子の 1 つ手前が `assets` で、その手前に語幹が残っている形）を持つかを確かめ、どちらでもなければ報告する。

**中身は読まない。** そのファイルが何を export しているか、誰かが import しているかは判定に入らない。spec 用ディレクトリの中に第三の種別のファイルが存在すること自体を見ている。

入れ子のディレクトリの下も対象になる。`test/support/clock.ts` は `test` に属するファイルとして扱われ、報告に現れる spec 用ディレクトリは `test` になる。ディレクトリそのものは報告しない。中に置かれたファイルだけを見るので、ファイルを持たないディレクトリは何も引き起こさない。

判定はファイル名だけで決まるため、`assets.ts` のように目印はあっても語幹が無いものは第三の種別になる。`.gitkeep` のような、どちらの規約にも当たらないファイルも同じに報告される。spec 用ディレクトリに置けるのは 2 種だけ、という不変条件をそのまま書いた結果であって、例外を作れば「規約に当たらないが置いてよいファイル」という 3 つ目の分類が戻ってくる。

走査の入力はリポジトリの木そのものなので、どのファイルが解析対象の glob に入っているかは結果に影響しない。走査から外れるのは、走査しないディレクトリとして宣言された名前（既定では `node_modules` や `dist` など生成物の置き場）だけである。

報告はファイルの中に位置を持たない。見つけた第三の種別のファイルは、それを抱えるワークスペース（そのファイルから最も近い `package.json` のディレクトリ、無ければリポジトリのルート）に紐づけ、そのワークスペースで検査されるファイルそれぞれに対して報告する。報告先が違反したファイル自身ではないため、そのファイルの中へ抑制コメントを置いても報告は消えない。同じワークスペースの別のファイルで抑制しても、残りのファイルが同じ報告を出し続ける。

その代わり、報告が出るのはそのワークスペースのファイルが 1 つ以上 linter に訪問されたときに限られる。ワークスペース全体が解析対象から外れていれば報告も出ない。oxlint の JS プラグインが報告位置を「今検査しているファイルの中のノード」に限っているためで、走査そのものは対象指定・ファイル単位のキャッシュ・差分実行のいずれからも独立している。

spec 用ディレクトリの規約を持たないリポジトリでは、このルールは対象を持たない。mst 自身がその状態で、テストは対象ソースと同じディレクトリに `<ソース名>.test.ts` として置く（[AGENTS.md](../../../../AGENTS.md)）。このルールは検出を早める仕組みであって、この群が成立する前提ではない。

## なぜそれが要るか

1 層目は、import の辺を塞いでもファイルは作れることである。spec が setup を別モジュールへ切り出して import する形を禁じても、切り出し先のファイルが置けるなら置かれる。置けるものは置かれ、いずれ結合側の縁（多段の再輸出、指定子を組み立てる動的 import、名前の付け替え）と組んで使われる。存在を許したまま辺だけを塞ぐ形は、逃げ道の探索を招く。

2 層目は、テストデータについての規律が全てファイル名に乗っていることである。テストデータには所有者の spec が要り、所有者以外は読めず、中身は静的な値だけである。これらは「テストデータと判定される名前を持つファイル」を対象にしている。spec 用ディレクトリに第三の種別を許すと、目印を名前から外すだけで 3 つの要求がまとめて外れる。置ける種別を 2 つに固定することが、名前を変えて規約から降りる経路を消す。

3 層目は、ディレクトリを開いた人が何を読めばよいか分かることである。この群は spec ファイル 1 つを、そのファイルだけで読める契約として保っている。ディレクトリの粒度でも同じ形にすると、「ここにあるのは契約と、契約が読むデータだけだ」と分かる。どれが本体でどれが道具かを見分ける作業が要らなくなる。

## どう直すか

そのファイルの中身を、使っている spec の中へ書き下す。setup を切り出した結果できたファイルなら、これが本来あるべき形である。複数の spec が同じ内容を必要としていても、それぞれに書き下す。この群では重複より単独可読性が優先される。

静的なデータだけを持つファイルなら、読み手の spec と同じ語幹を付けたテストデータのファイルへ移す。所有者の spec が同じディレクトリに実在することが条件になる。

production のコードが読む値なら、spec 用ディレクトリの外へ移す。そこが本来の置き場所である。

## 禁じる回避策

- 名前や拡張子を spec / テストデータの規約に合わせて種別を偽る。spec を名乗れば実行されるテストが要り、テストデータを名乗れば同じ語幹の所有者 spec と静的な中身が要る。名乗った先の条件が付いてくる
- spec 用ディレクトリの外へ出して置き場所だけ変える。spec から結合した時点で、切り出された setup の import を塞ぐ側のルールが報告する
- 抑制コメントで黙らせる。報告位置が違反したファイルの中に無く、同じ報告がワークスペースの全ファイルに出る
- そのディレクトリを解析対象の glob から外す。走査の入力はリポジトリの木であって glob ではない
- `specDirectoryNames` からそのディレクトリの名前を外す。外した時点でそこは spec 用ディレクトリではなくなるので、中の spec が読むデータは所有者の規約から外れ、切り出された setup は import の辺で報告される
- 走査しないディレクトリの宣言に、生成物ではないディレクトリを足す。宣言は生成物の置き場所を書くためのものである

## オプション

- `specDirectoryNames`（文字列の配列、任意）: spec 用ディレクトリとして扱うディレクトリ名。既定は `["__specs__", "__tests__", "spec", "specs", "test", "tests"]` で、指定すると**置き換える**（加算ではない）。パスの区切りごとに完全一致で照合する。空配列を渡した場合は既定に戻る
- `specFileSuffixes`（文字列の配列、任意）: spec として認識する接尾辞。既定は `[".test.ts", ".test.tsx"]` で、指定すると置き換える。この群の他のルールと同じ名前・同じ意味で、リポジトリ全体で 1 つの綴りに揃える前提で持っている
- `assetsNameMarkers`（文字列の配列、任意）: テストデータの目印として扱う語。既定は `["assets"]` で、指定すると置き換える。拡張子の 1 つ手前のセグメントと完全一致で照合する
- `unscannedDirectories`（文字列の配列、任意）: 走査しないディレクトリ名。既定は生成物と履歴の置き場所で、指定すると置き換える。リポジトリの木を走査する他のルールと同じ名前・同じ意味で持っている

```jsonc
["error", { "specDirectoryNames": ["__tests__"], "specFileSuffixes": [".test.ts"] }]
```

免除リストは持たない。「このファイルだけ第三の種別でよい」は、spec 用ディレクトリに置ける種別が 3 つあるという意味になり、不変条件そのものと矛盾する。
