# forbid-oversized-file--split-by-responsibility

## 何を検出するか

ファイルのコード行数が、そのファイルに適用された上限を超えていること。超えていればそのファイルに 1 件だけ報告する。

コード行数は「トークンが 1 つ以上存在する行」の個数として数える。

- 空行は数えない
- コメントだけの行も数えない。行コメントでもブロックコメントでも同じで、複数行にわたるブロックコメントはその全行が数から外れる。説明を厚く書いたことを罰しないため
- 複数行にまたがる 1 つのトークン（テンプレートリテラルなど）は、またいだ全ての行を数える。テンプレートリテラルの内側の空行も数える。物理的に読む量が減っていない以上、行数からも減らさない
- 末尾の改行はコード行を増やさない

ちょうど上限と同じ行数は報告しない。上限は「ここまでは許す」値として扱う。

何行超えていても報告は 1 件で、位置はファイル全体（Program ノード）になる。超過した行を指しても意味がないため、ファイルそのものを指す。

巨大な埋め込みリテラル（フィクスチャ文字列、埋め込みデータ）で膨らんだファイルも検出対象に含める。読む量は実在するため、リテラルであることを理由に免除しない。免除が必要ならルールの数え方ではなく、設定側で対象ファイル集合を絞ることで扱う。

ファイルの中身が実際にいくつの責務を持っているかは見ない。責務の数を機械が判定する手段はないので、行数という代理指標だけで止める。上限を通ったことは「良い」ではなく「このルールでは何も言えない」を意味する。

## なぜそれが要るか

このリポジトリは 1 ファイルが 1 つの責務に収まっている状態を守りたい。しかし責務が 2 つになった瞬間に気づける手段がない。気づくのは、たいてい読みづらくなってからであり、そのときには行数がすでに増えている。

そして分割のコストは行数に比例しない。そのファイルが外からどれだけ import されているかに比例する。大きくなるまでの時間は、そのまま参照が増えるための時間でもあるので、「大きくなってから分割する」は必ず最も高い時点で分割することになる。

だからこのルールは、責務が 2 つになったことを検出しているのではなく、責務を数え直す時点を強制的に前倒ししている。上限を超えた事実は「このファイルは 2 責務だ」という主張ではなく、「今ここで数え直せ、まだ安い」という合図である。

種別ごとに上限を変えられるようにしてあるのは、健全な長さの分布が種別ごとに違うからである。実装ファイルの仕事は抽象を 1 つ持つことなので、長さは概念の複雑さに比例する。テストファイルの仕事はシナリオを列挙することなので、同じ責務のままでも実装ファイルより素直に長くなる。両者を同じ数値で縛ると、実装側が緩すぎるか、テスト側が数値合わせの分割を強いられるかのどちらかになる。

## どう直すか

このファイルが今引き受けている責務を名前で列挙する。2 つ以上並んだなら、それぞれを自分のファイルに移す。移す先のファイル名がそのまま責務の名前になる。分割後の各ファイルは、名前が所有物を説明していて、他のモジュールがその理由で import する状態でなければならない。

列挙して 1 つしか出てこないなら、切り出すべきなのは責務ではなくファイル内の塊である。名前を付けられる手続きを関数として外に出し、呼び出し側に残るのが手順だけになるまで削る。

テストファイルでは、分割ではなくシナリオ数そのものを減らすことも正しい直し方になる。同じことを別の入り口から二度確かめている検証は落とす。

上限を変えるのは「このプロジェクトでは 1 責務あたり何行が妥当か」という判断であって、目の前のファイルを通すための操作ではない。変えるなら全ファイルに効く場所で変え、なぜ変えたかをその変更のコミットメッセージ本文に書く。

## 禁じる回避策

- 数値接尾辞による分割（`foo-1.test.ts` / `foo-2.test.ts`）。責務は「foo に関する全部」のまま変わらず、目的の記述がどのファイルにあるか分からなくなる分だけ悪化している。責務が複数あるなら名前を付けて割る（`foo.create.test.ts` / `foo.update.test.ts`）。責務が 1 つなら割らずにシナリオを減らす
- 行数を減らす目的だけのヘルパー切り出し。呼び出し元が 1 つしかなく、エクスポートされた関数が呼び出し元の外では意味を持たず、存在理由が「行を別の場所へ動かすこと」であるもの。呼び出し元の責務は 1 ミリも減っておらず、本体の置き場所が遠くなっただけになる
- 目の前のファイルを通すために上限を上げる。1 ファイルの都合で全ファイルに効く目盛りを動かすことになり、他のファイルが育つ余地まで一緒に広がる
- 1 行に複数の文を詰める、フォーマッタの折り返し幅を伸ばすなど、同じコードを少ない行数に圧縮する。行数は減るが責務は減らず、読みづらさだけが増える
- 中身を移さずに、再 export だけのファイルを足して見かけ上ファイルを分ける。分割されたのは行数だけで、責務は元のファイルに残っている
- そのファイルだけ抑制ディレクティブで黙らせる。責務が 1 つに収まっている根拠が示されないまま、超過が固定される

## オプション

`maxLines`（整数、1 以上、既定値 400）だけを取る。このコード行数を超えたら報告する。

```jsonc
["error", { "maxLines": 400 }]
```

未知のキーは schema が拒否する（`additionalProperties: false`）。上限の候補を別名で置いておくことはできない。

ファイル種別ごとに上限を変えたい場合も、ルール側には分岐を置かない。ルールが持つ上限は常に 1 つで、種別ごとの違いは設定側の `overrides` でファイルパターンを分け、同じルールを別の上限値で宣言することによって表現する。

```jsonc
{
  "rules": {
    "dont-review-it/forbid-oversized-file--split-by-responsibility": ["error", { "maxLines": 400 }],
  },
  "overrides": [
    {
      "files": ["**/*.test.ts", "**/*.test.tsx"],
      "rules": {
        "dont-review-it/forbid-oversized-file--split-by-responsibility": [
          "error",
          { "maxLines": 500 },
        ],
      },
    },
  ],
}
```

ルール内部に種別判定を埋めると、テストファイルの命名規約の定義がルールの中に固定され、リポジトリごとの規約差に追従できなくなる。上限だけを外から与える形にしておけば、種別の定義は設定を読めば分かる。
