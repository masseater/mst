# forbid-oversized-file--split-by-responsibility

## 何を検出するか

ファイルの行数が閾値を超えていること。超えていればそのファイルに 1 件だけ報告する。

行数は `context.sourceCode.lines` の要素数で数える。空行もコメント行も import 行も 1 行として数え、種類による割引はしない。末尾に改行があるファイルは、その改行の後ろが 1 行として数えられる（3 行 + 末尾改行 = 4 行）。

ちょうど閾値と同じ行数は報告しない。閾値は「ここまでは許す」上限として扱う。

何行超えていても報告は 1 件で、位置はファイル全体（Program ノード）になる。超過した行を指しても意味がないため、ファイルそのものを指す。

ファイルの中身が実際にいくつの責務を持っているかは見ない。責務の数を機械が判定する手段はないので、行数という代理指標だけで止める。

## なぜそれが要るか

このリポジトリは 1 ファイルが 1 つの責務に収まっている状態を守りたい。しかし責務が 2 つになった瞬間に気づける手段がない。気づくのは、たいてい読みづらくなってからであり、そのときには行数がすでに増えている。

そして分割のコストは行数に比例しない。そのファイルが外からどれだけ import されているかに比例する。大きくなるまでの時間は、そのまま参照が増えるための時間でもあるので、「大きくなってから分割する」は必ず最も高い時点で分割することになる。

だからこのルールは、責務が 2 つになったことを検出しているのではなく、責務を数え直す時点を強制的に前倒ししている。閾値を超えた事実は「このファイルは 2 責務だ」という主張ではなく、「今ここで数え直せ、まだ安い」という合図である。

## どう直すか

このファイルが今引き受けている責務を名前で列挙する。2 つ以上並んだなら、それぞれを自分のファイルに移す。移す先のファイル名がそのまま責務の名前になる。

列挙して 1 つしか出てこないなら、切り出すべきなのは責務ではなくファイル内の塊である。名前を付けられる手続きを関数として外に出し、呼び出し側に残るのが手順だけになるまで削る。それでも閾値に収まらないなら、閾値そのものの妥当性を疑う場面であり、次項の扱いになる。

閾値を変えるのは「このプロジェクトでは 1 責務あたり何行が妥当か」という判断であって、目の前のファイルを通すための操作ではない。変えるなら全ファイルに効く場所で変え、なぜ変えたかをその変更のコミットメッセージ本文に書く。

## 禁じる回避策

- 目の前のファイルを通すために閾値を上げる。閾値は全ファイルに効くので、1 ファイルの都合で上げた値がそのままリポジトリ全体の基準になる
- 1 行に複数の文を詰める、フォーマッタの折り返し幅を伸ばすなど、同じコードを少ない行数に圧縮する。行数は減るが責務は減らず、読みづらさだけが増える
- 中身を移さずに、再 export だけのファイルを足して見かけ上ファイルを分ける。分割されたのは行数だけで、責務は元のファイルに残っている
- そのファイルだけ lint 抑制ディレクティブで黙らせる。責務が 1 つに収まっている根拠が示されないまま、超過が固定される

## オプション

`maxLines`（整数、1 以上、既定値 100）だけを取る。この行数を超えたら報告する。

```jsonc
["error", { "maxLines": 100 }]
```

未知のキーは schema が拒否する（`additionalProperties: false`）。閾値の候補を別名で置いておくことはできない。

ファイル種別ごとに閾値を変えたい場合も、ルール側には分岐を置かない。ルールが持つ閾値は常に 1 つで、種別ごとの違いは利用側の設定で override として表現する。テストファイルだけ緩める、生成物だけ緩めるといった判断は、ルールの内部ではなく設定を読めば分かる場所に置くべきものだから。
