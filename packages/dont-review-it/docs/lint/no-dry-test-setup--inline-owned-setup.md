# no-dry-test-setup--inline-owned-setup

## 何を検出するか

spec ファイルから他のモジュールへ伸びる結合の辺を 1 本ずつ見て、その先が setup モジュールなら報告する。判定は spec を訪問したときに、その spec が書いた辺に対してだけ行う。結合されていないファイルは、どこに何という名前で置かれていても、このルールの対象にならない。

結合とみなす形は次のとおり。どれも「そのモジュールへ結合した」という 1 つの事実の別の綴りであって、扱いは変わらない。

- `import` 宣言。束縛を伴わない副作用だけの `import "./x.ts"` も含む
- 名前付き再輸出（`export { x } from`）と全再輸出（`export * from`）
- 動的 `import()` と `require()` のうち、指定子が静的に決まるもの。文字列リテラル、同じファイルの中で文字列リテラルに束縛された `const`、その 2 つだけで組み立てたテンプレートリテラルが「静的に決まる」の中身になる

型だけを運ぶ辺は見ない。`import type` / `export type` は値を運ばないので、setup を運ぶこともできない。

結合先が setup モジュールかどうかは、次の順で決まる。上から順に評価し、当たったところで止まる。

1. **許可された共通 fixture パッケージの指定子**（`allowedFixturePackages`）。以降の判定を行わない
2. **解決できない指定子**。`#` から始まる subpath import、絶対パス、実行時にしか決まらない動的 import の指定子、ワークスペースの外にインストールされたパッケージがここに入る
3. **別パッケージの公開エントリ**を指す指定子。そのパッケージを spec 以外の実行コードが 1 箇所でも参照していれば production であり、対象から外れる。参照が spec からしか来ていなければ setup モジュールとして報告する。報告に載るのはファイルではなくパッケージのディレクトリになる
4. **assets ファイル**。`require-test-assets-constants--move-setup-to-spec` と `no-cross-spec-assets-import--use-own-assets` へまるごと委ねる
5. **型宣言だけを持つファイル**。値を持たないので setup を運べない
6. **所属パッケージの公開エントリから到達できるファイル**。これが検証対象（SUT）である
7. **名前パターンに当たるファイル**（`setupModuleNamePatterns`）。報告する
8. **所属パッケージの公開エントリから到達できないファイル**。報告する
9. 所属パッケージが公開エントリを決められない場合、そのファイルを中継とみなして、そのファイルが持つ結合の辺を同じ判定へかける。4 段まで辿る

「公開エントリ」は `package.json` の `exports` / `main` / `bin` が指すファイルである。このリポジトリの `packages/dont-review-it` なら `./src/index.ts`（`.`）、`./src/plugin.ts`（`./plugin`）、`./src/vitest/standard-io-test.ts`（`./vitest`）、`./src/cli.ts`（`bin`）の 4 つがそれに当たる。到達可能性はそこから結合の辺を辿って求め、パッケージのディレクトリの内側だけを歩く。`src/lint/oxlint/rules/*.ts` が SUT として扱われるのは、`plugin.ts` がそれらを import しているからであって、名前や置き場所によるものではない。

到達可能性と、パッケージを実行コードが参照しているかどうかは、プロセスが生きている間だけ覚える。lint の実行中にファイルを足しても、そのプロセスの答えは変わらない。変わるのは次に lint を起動したときである。

`allowedFixturePackages` に載った指定子は、結合の判定より先に評価されるが、同時に設定そのものも検査される。パッケージ指定子ではないもの、パッケージの中のファイルを直接指すもの、そのパッケージが `exports` で公開していない subpath がそこに現れたら、設定が誤っていることを報告する。報告の位置は検査中の spec ファイル全体になる。設定はファイルの中に位置を持たないためで、同じ設定の誤りは spec ごとに 1 件ずつ現れる。

## なぜそれが要るか

1 層目は、spec が何を検証しているのかがそのファイルだけでは決まらなくなることである。組み立ての手順が別ファイルにあると、`it` の本文を読んでも subject が何なのかは分からず、読み手は別ファイルへ移動し、そこから更に別のファイルへ移動する。テストは契約の記述をやめて、どこかで組み立てられた何かの呼び出しになる。

2 層目は、その別ファイルが検査の外側に置かれることである。このパッケージのルール群は spec ファイルに対して形を要求する。組み立てを spec の外へ出せば、要求されている形は spec の中から消え、外に出した層は誰にも見られない。1 本のルールを回避したのではなく、spec に形を要求するという方針そのものが空洞になる。

3 層目は、共有された setup が可変状態を運ぶことである。テストは並列実行が既定なので、モジュールスコープに置かれたモック設定や書き換え可能な値は、同時に走っている別のテストへ漏れる。共有を許すと、単独可読性と並列分離が同時に壊れ、しかも壊れ方は実行順序に依存するので再現しない。

4 層目は、再利用のために作られたユーティリティ自身がテストされないことである。テストを助けるために書かれたコードは、テスト対象として扱われないまま積み上がり、それが壊れたときには、それを使っている全ての spec が同時に理由の分からない失敗をする。

この 4 つは 1 つでは足りない。読みやすさだけなら整形で足りるし、並列分離だけなら実行の分離で足りる。4 つが同じ方向を向いているために、重複を受け入れるという取引が成立する。

## どう直すか

その spec が必要とする setup を、その spec 自身の fixture の中へ書き下す。同じ setup が別の spec にも要るなら、その spec にも同じものを書く。この群では重複は削減すべき負債ではなく、単独可読性のために払う対価である。「重複しているのでまとめよう」という方向の指摘は、このルールに対しては通らない。

パッケージのディレクトリが報告された場合は、そのパッケージが spec のためだけに存在している。パッケージを消して中身を各 spec へ書き下すか、production の実行コードから使われるものへ育てるかのどちらかを選ぶ。

報告されたモジュールが実は production の一部だった場合、直すのは spec ではなく公開の側である。そのモジュールを所属パッケージの公開エントリから到達できるようにする。到達できないものを production だと主張することはできない。

共通 fixture 提供パッケージへ公開 fixture を足す道は残してあるが、3 つを同時に満たす場合に限る。

1. その形がリポジトリ規模で再発している証跡
2. その fixture が包んでいる低レベル API の直接使用を禁じる、対になるルールを同じ変更で入れること。対のルールがない fixture は境界ではなく単なる推奨であり、重複はすぐ再発する
3. その fixture 自身のテスト

## 禁じる回避策

- 動的 `import()` へ書き換える。指定子が静的に決まる限り、静的な `import` と同じ結合として報告される
- 再輸出だけの中継ファイルを挟む。中継は辿るので、辿った先が setup モジュールなら報告される
- 名前パターンに当たらないファイル名へ改名する。位置から導く判定は名前を見ないので報告は消えない
- 自分の helper を `allowedFixturePackages` へ足す。結合の報告は消えるが、リポジトリ内のモジュールを名指しした時点で設定そのものが報告されるので、通ったことにはならない
- setup を別の spec ファイルへ移して読み合う。spec は公開エントリから到達できないので、読まれた spec が setup モジュールとして報告される
- setup を assets ファイルの名前で置く。assets は静的なデータだけを持つことを別のルールが要求するので、実行される setup はそちらで落ちる
- `setupModuleNamePatterns` を空にする。名前による判定は黙るが、位置から導く判定は設定を受け取らないので動き続ける

## オプション

- `specFileSuffixes`（文字列の配列、任意）: spec ファイルとみなす接尾辞。既定は `.test.ts` と `.test.tsx`
- `setupModuleNamePatterns`（文字列の配列、任意）: setup モジュールとみなす名前のパターン。既定は `_*` / `*fixtures*` / `*harness*` / `*helper*` / `*.setup.*` / `setup.*`
- `allowedFixturePackages`（文字列の配列、任意）: リポジトリで唯一許可された共通 fixture 提供パッケージのパッケージ指定子。既定は空
- `assetsNameMarkers`（文字列の配列、任意）: assets ファイルの名前に現れる語。既定は `assets`

```jsonc
["error", { "allowedFixturePackages": ["@mst/spec-fixtures"] }]
```

パターンの照合は、結合先を解決した後のパスをリポジトリからの相対パスに直し、その各セグメントに対して行う。`*` はパスの区切りを跨がず、両端は固定される。`*helper*` は `test-helpers.ts` にも `helpers` というディレクトリ名にも当たるが、`helper` を含む文字列を持つ別のパスに巻き込みで当たることはない。指定子の文字列ではなく解決先で照合するので、別名を経由して同じファイルへ結合しても同じ結果になる。

`setupModuleNamePatterns` は既定に加算されるのではなく、既定を置き換える。空の配列を書けば名前による判定だけが黙る、という状態を表現できる必要があるためで、既定へ加算する形ではそれが書けない。

名前による判定は、位置から導く判定が届かない範囲を早く落とすための追加であって、このルールが成立する前提ではない。設定を何も書かなくても、公開エントリと結合のグラフはリポジトリの内容から決まるので、位置から導く判定は動く。

## 判定が届かない範囲

検出できないことは許していることを意味しない。ここに挙げたものは、静的解析で結合先を確定できない、あるいは確定するための情報がリポジトリに無いというだけである。

- 指定子が実行時にしか決まらない動的 `import()`。変数、関数の戻り値、実行時に組み立てられる文字列を渡す形がこれに当たる
- tsconfig の `paths` やビルドツールのエイリアスを経由した指定子。相対指定子と、インストールされたパッケージ指定子だけを解決する
- 公開エントリがビルド成果物を指しており、その成果物がまだ無いパッケージ。公開エントリを 1 つも解決できないパッケージでは、位置から導く判定が黙り、名前による判定だけが残る
- 4 段を超える中継の連なり
- そのパッケージを参照している実行コードが JavaScript で書かれている場合。参照元として走査するのは TypeScript のソースだけである
