# no-ambiguous-variable-name--rename-to-concrete-noun

## 何を検出するか

変数宣言子のうち、束縛が単純な識別子であり、その名前が設定された禁止パターンのいずれかに一致するもの。

宣言の種別（`const` / `let` / `var`）は問わない。初期化式の有無も問わないので、`let result;` も `for (const value of entries)` の束縛も対象になる。一致判定は大文字小文字を区別しない。報告位置は宣言文全体ではなく識別子そのもの。

パターンは識別子名に照合する、区切り記号なしの正規表現ソース文字列。アンカーの有無が一致の仕方を決める。`^data$` は識別子全体が `data` のときだけ一致し、`result$` はその語で終わる複合語（`parseResult`）にも一致する。

次の位置は構文上そもそも変数宣言子ではないので、対象範囲に入らない。

- 分割代入による束縛（`const { data } = payload;` / `const [value] = entries;`）。取り出す名前は元のオブジェクトの形に従うので自由に選べない
- 関数・アロー関数の仮引数。呼び出し側の契約や実装対象のインターフェースに従うことがある
- クラスのフィールド
- オブジェクトリテラルのプロパティ名。外部 API 由来の形をそのまま書く位置
- catch の束縛

禁止パターンが空、または設定そのものが無い場合は訪問者を登録せず、何も検査しない。

## なぜそれが要るか

汎用的な名前は「何かが出てきた入れ物」を指すだけで、中身の主題を指さない。`data` と書かれた束縛から分かるのは「何かのデータである」ことだけで、それが解析済みの設定なのか取得した記録なのかは分からない。略語（`res` / `ret` / `val`）は主題そのものを捨てている。`actual` は検証の作法上の役割を示すだけで、どの主題が束縛されているかを隠す。

結果として、読み手は名前ではなく代入を上流に辿ることで主題を知ることになる。宣言から使用箇所までの距離が、そのまま読み取りのコストになる。

既定の語彙は 8 項目で、一致の仕方が語彙の一部になっている。

接尾辞一致（その語で終わる名前も落とす）:

| パターン   | 落ちる例                   |
| ---------- | -------------------------- |
| `outcome$` | `outcome` / `queryOutcome` |
| `result$`  | `result` / `parseResult`   |

これらは「何かの結果の詰め合わせ」を意味する。接頭辞に何を付けても「何かの結果」であることしか伝わらないので、複合語ごと落とす。

完全一致（識別子全体がその語のときだけ落とす）:

| パターン    | 落ちる例           |
| ----------- | ------------------ |
| `^vals?$`   | `val` / `vals`     |
| `^values?$` | `value` / `values` |
| `^res$`     | `res`              |
| `^ret$`     | `ret`              |
| `^data$`    | `data`             |
| `^actual$`  | `actual`           |

完全一致にしているのは、語を含むだけの正当な名前を巻き込まないため。`interval` は `val` を内部に含み、`defaultValue` は `value` で終わり、`metadata` は `data` で終わる。これらを接尾辞一致にすると、主題を語っている名前まで落ちる。

語彙に入れる基準は「その語を見ても、束縛されている具体的な主題が一つに決まらない語」。語彙は設定データであって不変条件そのものではないので、配備先で追加・削除される前提で扱う。

## どう直すか

束縛が何を保持しているかを名指しする名詞に改名する。解析済みのスキーマ値、描画された断片、取得した記録、捕捉した例外、といった具体名を使う。

ひとつのブロックで具体名の候補が複数出てきて名前を決めきれないなら、そのブロックが複数の仕事をしている。名前を妥協するのではなくブロックを分割する。

## 禁じる回避策

- 禁止語に無意味な接頭辞・接尾辞を付けて完全一致から外す（`theData` / `res2` / `dataValue`）。一致判定は外れるが、名前が主題を語っていない状態は変わらない
- 具体名で受けてから禁止語の別名に移し替える。宣言が 1 つ増えただけで、使用箇所が読む名前は曖昧なまま
- 分割代入や仮引数の位置へ押し出して対象範囲から逃がす。これらを対象外にしているのは名前を自由に選べない位置だからであって、曖昧な名前を置いてよい場所として空けているわけではない
- 個別の違反を消すために語彙から語を外す。語彙は設定なので変更できるが、それは「この語は主題を語る」という語彙全体への判断であり、1 箇所を通すための操作ではない

## オプション

禁止する名前パターンの一覧を 1 つ取る。

```ts
[{ pattern: "^data$" }, { pattern: "result$" }];
```

各項目は `pattern` を 1 つだけ持つオブジェクトで、値は識別子名に照合する区切り記号なしの正規表現ソース文字列。`pattern` 以外のキーはスキーマが拒否する。

既定値は空配列で、その場合ルールは何も検査しない。既定の語彙はルール本体ではなく `src/lint/oxlint/lib/forbidden-ambiguous-names.ts` の `FORBIDDEN_AMBIGUOUS_NAMES` に置き、配備側の設定で注入する。語彙を単一の出所に置くのは、テストのアサーション対象の名前を検査する別ルールと同じ語彙を共有できるようにするためで、こうしておくと両者の語彙がドリフトしない。
