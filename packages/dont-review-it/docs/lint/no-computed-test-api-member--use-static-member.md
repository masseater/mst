# no-computed-test-api-member--use-static-member

## 何を検出するか

添字で書かれたメンバアクセス（`MemberExpression` の `computed`）のうち、その連鎖の根が次のいずれかであるものを見る。

- テストランナー由来のテストブロック宣言の根
- `test.extend(...)` と、そこから伸びる連鎖
- assertion の入口である `expect` 束縛と、その呼び出し結果に続くマッチャの連鎖

根は、添字の左側から `object` / `callee` / タグ付きテンプレートの `tag` をたどって識別子に着くまで降りて決める。修飾子やマッチャの名前の表を引かずに降りるので、語彙に無い名前が途中にあっても、途中の段が添字であっても根を見失わない。検出しているのは名前ではなく形なので、「テストブロックの修飾子として扱う名前の集合」がどう決まるかにこのルールは依存しない。

根の判定は共有の束縛追跡（`src/lint/oxlint/lib/spec-syntax/test-block-declarations.ts`）に載せてある。テストブロック側は `testBlockBindings()`、assertion の入口側は `assertionEntryBindings()` で、どちらも同じ追跡をする。

- グローバル注入された綴り（テストブロックは `it` / `test`、assertion の入口は `expect`）
- その綴りを import した束縛。リネーム import も含む
- 上記のいずれか、あるいは `test.extend(...)` の結果で初期化されたローカル束縛。束縛から束縛への受け直しは何段でもたどる

呼び出しの有無は問わない。値として取り出すだけのメンバ参照（`const held = it['skip'];`）も同じ違反である。連鎖の中に添字が 2 段あれば報告は 2 件で、それぞれ添字の位置に立つ。ファイル全体の束縛を読み終えてから報告するので、添字が束縛の宣言より前に書かれていても結果は変わらない。

添字の名前が静的に読めるかどうかは検出の条件ではない。読める場合は綴りルールと `forbid-it-extend--use-test-extend` が名前として解決して重ねて報告するが、形の違反と名前の違反は別の欠陥なので両方立つのが正しい。

### 意図的に広げていない範囲

| 形 | 対象にしない理由 |
| --- | --- |
| `it.skip` / `test.extend` / `expect(...).toBe` | 添字ではない。書かれた名前がそのまま最終的なプロパティ名になっている |
| `runSut()[key]` | SUT の出力への添字。連鎖の根がテスト API ではない |
| `rows[0]` | 配列の要素アクセス。同上 |
| `runner.it[member]` | 根が識別子まで解決しない。名前空間 import でテスト API を持ち込む構成を採るなら共通定義を組み直す |
| `this.#skip` | private フィールド構文は添字ではない |
| `describe[member]` | グルーピングブロックはこのルールが見るテスト API に入っていない |
| `const held = expect.soft;` を経た添字 | 束縛の追跡がたどるのは識別子の受け直しと `extend` の派生までで、メンバを取り出した束縛は根に着かない |

ファイル種別による絞り込みはしない。どのファイルにこのルールを効かせるかは共有 lint 設定の glob が決める。

## なぜそれが要るか

守っている不変条件は「テストランナー由来のテストブロック API と `expect` へのメンバアクセスは、コードに書かれた名前がそのまま最終的なプロパティ名になる形である」ことである。

1 層目は、この束の他のルールが立っている土台である。綴りルールも `forbid-it-extend--use-test-extend` も `no-vitest-context-expect--import-expect-from-vitest` も、「どの名前でどの API を呼んでいるか」を判定して不変条件を守る。添字はその判定の入口を 1 段ずらす。添字が文字列リテラルなら名前自体は読めるが、読むために各ルールが個別に添字を解決する分岐を持つことになり、判定単位を 1 箇所に置いた理由が崩れる。

2 層目は、名前が実行時にしか決まらない場合に起きることである。変数や式を添字にすると、どのルールもその段の役割を確定できない。役割を確定できないルールは、違反を見逃すのではなく違反でないと答える。報告が出ないことと違反が無いことが区別できなくなり、緑が証拠でなくなる。

そこで解決先を追いかけるのをやめ、形そのものを禁じている。名前が実行時に決まる余地を消せば、他のルールは「書かれている名前がすべて」という前提のまま動ける。テストコードで修飾子やマッチャを添字で書く必要は無いので、禁じても失うものはない。

## どう直すか

添字を静的なメンバアクセスへ書き直す。このリポジトリのテストが取っている形がそのまま直した形になる。

```ts
it.each(rows)("adds %i", (row) => {});
expect(runSut()).toStrictEqual({ total: 1 });
```

添字が文字列リテラル、または式を含まないテンプレートリテラルで、その名前が識別子として書ける場合は自動修正を持たせる。置換は添字の 1 箇所だけで済み、書き手の意図を要しないためである。`?.` で繋いだ形は `?.` のまま残す。

変数や式を添字にしていた場合、および識別子として書けない名前を添字にしていた場合は自動修正を出さない。どの修飾子・マッチャを意図していたのかをコードに書き下す必要があり、その決定は書き手に属する。

## 禁じる回避策

- テストブロックや `expect` を一度別の変数へ受け直してから添字を書く。束縛の追跡が受け直しを何段でもたどるので根は変わらず、判定も変わらない
- 文字列リテラルの添字を、式を含まないテンプレートリテラルの添字へ書き換える。どちらも同じに読む
- 添字を式にして名前の判定を外す。名前として読めなくなるだけで、形の違反はこのルールが落とす
- 修飾子を含んだ連鎖の途中に添字を混ぜる。判定は連鎖のどの段でも成立する
- 抑制ディレクティブで黙らせる。この形はスイート全体に対する規律であり、1 ファイルの都合で外れるものではない

## オプション

取らない。有効か無効かだけを設定側で決める。

添字を許す例外を設定で表現できるようにしない。その設定自体が、どのメンバを添字で書いてよいかを設定値で決める経路になり、名前を実行時に決める形を別の場所へ移しただけになる。
