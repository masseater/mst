# no-explanatory-comment--delete-or-move-to-commit-message

## 何を検出するか

コメント構文で書かれたもののうち、機械が読む宣言ではないものすべて。行コメントもブロックコメントも対象になる。

機械が読む宣言として通すのは次の 3 つだけ。

- lint の抑制ディレクティブ（先頭トークンが `eslint-disable` / `oxlint-disable` の系列）
- コンパイラディレクティブ（先頭トークンが `@ts-` で始まるもの）
- JSDoc ブロック（`/**` で始まるブロック）

shebang はコードを説明するために書かれたものではないので対象外。

JSDoc ブロックの中身が説明散文かどうかは、このルールでは判定しない。[no-detached-rationale--comment-at-explained-line](./no-detached-rationale--comment-at-explained-line.md) が担当する。二重報告を避けるための役割分担。

## なぜそれが要るか

コードを説明するコメントは、コードが変わった瞬間に嘘になる。しかも嘘になったことを何も検出しない。テストは落ちず、型検査も通り、レビューでも「コメントがある」以上のことは分からない。結果として、読み手はコメントとコードのどちらを信じるかを毎回判断させられる。

説明を残す場所はコミットメッセージの本文である。そこに書けば、その変更を加えた時点の意図として履歴に固定され、後からコードが変わっても遡って読める。コードの隣に置くと、コードと一緒に動いてしまう。

## どう直すか

コメントを削除し、書こうとしていた内容をその変更のコミットメッセージ本文に書く。

名前で意図が伝わらないためにコメントを書きたくなっているなら、名前を変える。処理の塊が何をしているか説明したくなっているなら、その塊を名前付きの関数に切り出す。どちらもコメントより強く、コードが変わればついてくる。

## 禁じる回避策

- コメントの先頭に機械が読むディレクティブの綴りを付けて判定を通す。ディレクティブとして成立しない綴りを置くのは、抑制の口を偽装しているだけで、説明散文が残ることに変わりはない
- 説明散文を JSDoc ブロックに移して判定を外す。JSDoc は `no-detached-rationale--comment-at-explained-line` が受け持つので、移した先で報告される
- 説明を文字列リテラルや到達しない式として書く。コメントでなくなっただけで、コードが変わったときに嘘になる性質は同じ

## オプション

取らない。有効か無効かだけを設定側で決める。
