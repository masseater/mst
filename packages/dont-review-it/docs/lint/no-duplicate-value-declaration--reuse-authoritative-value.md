# no-duplicate-value-declaration--reuse-authoritative-value

## 何を検出するか

production の TypeScript ソースで、名前と本体の両方がリポジトリ内の別の値宣言と一致し、かつ 2 つのうち少なくとも一方が export されている宣言。

対象は名前を持つ値で、次の 3 つの形。

- 束縛（`const` / `let` / `var`）。型注釈と初期化子を本体とする
- 関数宣言。型引数・引数・戻り値の型・本体・`async` と `generator` の別を本体とする
- クラス宣言。型引数・親クラス・`implements` 節・本体を本体とする

束縛の種別は本体に含めない。`const` を `let` に書き換えても一致は外れない。

宣言が立っている深さは問わない。トップレベルの宣言も、関数やブロックの内側に立つ宣言も同じ索引に入る。深さを問わないのは、公開された宣言と同じ名前・同じ本体のローカル宣言を関数の内側へ押し込む形を、距離を取っただけで検出から外さないためである。

### export されている側が組に要る

同じ名前・同じ本体の宣言が 2 つあっても、どちらも export されていなければ報告しない。ファイルの外から参照されない宣言は、その名前の権威を主張していない。短い名前が別々の場所で同じ形になることは普通に起きる。

この条件があるので、本体の大きさに下限を置かない。1 行の定数でも、数行の補助関数でも、名前まで一致していれば偶然ではない。

### 一致の判定

本体を AST に直し、位置情報を落とした構造を文字列にして比べる。そのうえで名前を 2 つに分けて扱う。

- 宣言の中に閉じた名前（引数、局所の束縛、内側の関数名とクラス名、型引数）は、現れた順の記号に置き換える。引数名を変えても振る舞いは変わらないので、綴りの差で一致を外せてはいけない
- 宣言の外に開いた名前は綴りのまま残す。ただしその名前がこのファイルの import に由来するなら、綴りではなく解決先（相対指定子を解決したモジュールと、そのモジュールから取り出した名前）で比べる。別名を付けて import しても、指しているものが同じなら一致とみなす

プロパティの綴りは名前の置き換えから外す。`{ id }` と `{ id: held }` は、`held` が束縛の別名であっても同じ本体になる。逆に `.size` と `.length` は別の本体である。

コメントと空白は落ちる。文字列と数値のリテラルは綴りごと残る。

### 索引の範囲

索引はリポジトリ根から作る。根は lint の実行ディレクトリから上に辿って決める。パッケージのディレクトリから lint を走らせても、リポジトリ全体から走らせたときと同じ索引を見る。

テストファイルと、テスト用ディレクトリの配下は索引に入らない。判定は [no-duplicated-body--import-the-existing-declaration](./no-duplicated-body--import-the-existing-declaration.md) と同じものを使う。

一致した組は両方の位置で報告する。どちらが権威かを機械は決められないので、片方だけを報告して残る方を暗に正しいことにはしない。

### 報告の 2 つの形

報告された宣言自身が export されている場合と、export されておらず相手が export されている場合とでメッセージを分ける。後者は、そのファイルの読み手が公開されている宣言に届かないという事実を含めて報告する。名前と位置だけを告げると、読み手は「別物だ」と判断して抑制に向かう。

## なぜそれが要るか

同じ名前の値が 2 箇所にあると、片方だけ直しても何も落ちない。型検査もテストも通る。

値には型と違うところが 2 つある。1 つは実行されることで、分岐した 2 つは同時に動く。どちらの振る舞いが出るかは呼び出し元がどちらを掴んだかで決まり、その差は例外にもテスト失敗にもならずに残る。もう 1 つは規模が小さいことで、行の塊を見る検出は一定の大きさを持つ塊を対象にするため、短い定数や数行の補助関数はその下をくぐる。くぐった先に受け手がいなければ「小さいから見逃す」が事実上の規律になる。小ささは重複してよい理由にならない。

公開された宣言と同じ名前のローカル宣言がとくに悪いのは、名前解決の性質による。参照側は近い方を掴む。ローカル宣言は公開された宣言を黙って覆い隠すので、読み手には「同じ名前だから同じもの」に見えたまま別の実体が動く。覆い隠していること自体は、コードの上に痕跡を残さない。

自動修正を持たないのは、どちらが所有者かを機械が決められないからである。export されている側は候補の手掛かりであって決定ではない。所有者の選択は責務の配置の問題で、綴りからは導けない。

## どう直すか

報告に並んだ位置を全部読んでから、その値が表す事実をどのモジュールが所有すべきかを決める。決めたら、そこから export して他の全箇所は import する。

消す順序を逆にしない。参照先を作ってから消す。片方を消すだけの修正は参照を切る。

ローカルな再宣言であれば、削除して import に置き換える。覆い隠していた側が消えるので、参照は残った 1 つに届く。

所有者を選ぶときは、報告に並んだ順序で選ばない。先に書かれた方を選ばない。export されている方を無条件に選ばない。その値が誰の責務かで選ぶ。

## 禁じる回避策

- 片方の名前を変える。名前が違って本体が一致する状態になり、本体が十分に大きければ [no-duplicated-body--import-the-existing-declaration](./no-duplicated-body--import-the-existing-declaration.md) が引き続き報告する
- 引数名や局所の束縛の名前を変える。宣言の中に閉じた名前は位置で正規化するので一致は外れない
- 呼んでいる関数を別名で import し直す。import された名前は解決先で比べるので一致は外れない
- `const` を `let` に書き換える。束縛の種別は本体に含めない
- ローカル宣言を関数の内側へ押し込んで距離を取る。索引は宣言の深さを問わない
- 片方をテストファイルへ移す。索引がテストを見ないことを、重複を隠す口として使わない
- 本体に意味の無い記述を足して一致から外す。重複は残ったまま、報告だけが消える
- リントの無効化で黙らせる
- 「この名前だけは 2 つあってよい」という除外の設定。用意しない。2 つ目の所有者を設定で正当化すると、分岐は同じ速度で進む

## 何を検出しないか

- どちらも export されていない同名同本体の組。権威を主張しているのは公開された側だけである
- 名前が違って本体だけが一致する宣言。[no-duplicated-body--import-the-existing-declaration](./no-duplicated-body--import-the-existing-declaration.md) が本体の大きさを条件に扱う
- 名前が一致して本体が違う宣言。1 つの名前が 2 つの意味を持っている状態で、直し方は統合ではなく改名になる。このルールの指示（1 つに寄せろ）と噛み合わないので入れていない
- 型宣言。型エイリアスとインターフェースはこのルールの対象ではない
- 再エクスポート。宣言を伴わず既存の値を通すだけの記述は、このルールが求める直し方そのものである
- 名前を持たない既定エクスポート。名前を単位に見るルールなので受け皿が無い。既定エクスポート自体は [no-default-export--use-named-export](./no-default-export--use-named-export.md) が別に禁じている
- 1 つの名前に決まらない分割束縛。`const { first, second } = split();` は索引に入らない
- 一方が他方を参照して作られた宣言。派生は本体が一致しないので、条件を満たさない
- 意味が同じで書き方が違う宣言。判定は正規化後の一致であって、値としての同値性ではない

## 導入時に測ったもの

索引に入った production のソースは 212 ファイル、そこに立つ値宣言の名前は 2132 種類だった。名前と本体が一致し、かつ一方が export されている組は 0 件である。並行して書かれていた 2 組（いずれも 1 行の文字列定数を、公開された宣言とは別のファイルでローカルに宣言し直したもの）は、この索引で検出できることを確認したのち、書いた側が統合して消えた。
