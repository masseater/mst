# no-sut-independent-assertion--assert-fixture-subject

## 何を検出するか

spec ファイルの中で、マッチャまで届いたアサーションを入口にする。`expect(...)` に加えて `expect.soft(...)` / `expect.poll(...)` を同じ入口として読み、`not` / `resolves` / `rejects` を挟んだ綴りも同じ 1 本として読む。マッチャに届いていない `expect(...)` は入口に入らない。

対象のファイルはファイル名の接尾辞で決める。既定は `.test.ts` と `.test.tsx` で、`specFileSuffixes` で差し替えられる。

読むのは 2 つの位置である。`expect(...)` の第一引数（被験体）と、マッチャに渡された引数（期待値）。どちらも型アサーション・`satisfies`・非 null 表明・括弧・オプショナルチェーン・`await` を剥いでから読む。

報告は 2 通りある。

### 1. 突き合わせる値がすべて spec の中に閉じている

被験体とすべての期待値が「spec の中に閉じた由来」しか持たないとき報告する。期待値を取らないマッチャでは、被験体だけを見る。

閉じた由来とは次のものである。

| 形                                                | 例                                              |
| ------------------------------------------------- | ----------------------------------------------- |
| 書き出された値                                    | `"a"` / `true` / `-1` / `` `a` `` / `undefined` |
| 書き出された値だけで組み立てた式                  | `1 + 1` / `["a", "b"]` / `{ id: "a" }`          |
| 閉じた値どうしを繋いだ演算・条件・連結            | `true ? "a" : "b"` / `` `id ${"a"}` ``          |
| その場で書き出した値から読んだメンバ              | `["a"][0]` / `({ id: "a" }).id`                 |
| spec の外の名前による構築で、引数も閉じているもの | `new Headers({ accept: "text/plain" })`         |
| 書き換えようのない値で埋めた束縛                  | `const id = "a"` の `id`                        |

束縛は連鎖の終端まで辿る。辿った先が自分自身へ戻る束縛は、値に届かないものとしてそこで打ち切る。

**束縛が抱えている値は、書き換えようのないものだけを閉じたものとして読む。** 配列・オブジェクト・構築した値を束縛が抱えている形は、閉じていないものとして扱う。`const written = new Set()` を SUT に渡し、戻ってきてから `written.size` を読む形では、値を書いたのは spec でも、読み出す中身を決めたのは SUT だからである。参照を持っている者は誰でも書き込める以上、束縛の初期化子の形だけでは「SUT を通っていない」と言えない。アサーションの中にその場で書き出した値は、他の誰も参照を持てないので閉じたまま読む。

### 2. 被験体と期待値が同じ値に届く

由来が閉じているかどうかに関わらず、被験体と期待値が同じ束縛に届くとき報告する。`not` を挟んでも報告する。`not` が付けば常に失敗するアサーションになるだけで、結果が SUT と無関係である点は変わらない。

比べる前に、型レベルのラッパに加えて**スプレッドだけの複製**を剥がす。`{ ...report }` と `[...report]` は `report` に届く。複製の複製も剥がす。名前を写した束縛（`const copied = report`）も、束縛を辿って同じところに届く。

## 意図的に広げていない範囲

| 形                                             | 対象にしない理由                                                                        |
| ---------------------------------------------- | --------------------------------------------------------------------------------------- |
| 片方だけが閉じている形                         | 期待値を spec に書き下すのは正しい形である。被験体が SUT 由来なら比較は落ちうる         |
| 被験体がリテラルで、期待値が SUT 由来の形      | 比較自体は落ちうる。読みにくさは名前の側のルールが見る                                  |
| fixture から受け取った束縛に由来する被験体     | 分配で受け取った名前は spec が値を書いていない。呼び出し記録を持つモックも同じ          |
| spec の外から取り込んだ値                      | 取り込んだ定数は SUT が変われば変わる。SUT が輸出する既定値の表を突き合わせる形はここ   |
| 呼び出しの結果                                 | 何が返るかは spec が書いた値ではない。SUT を通る経路はここに入る                        |
| spec が宣言した名前による構築                  | その名前が指す宣言が変われば結果が変わる                                                |
| 束縛が抱えている配列・オブジェクト・構築した値 | 参照を渡された側が中身を書き換えうる。読み出した値が spec の書いた値だとは言えない      |
| マッチャを伴わない `expect(...)`               | 何も主張していないこと自体は `no-matcherless-expect--assert-with-matcher` が引き受ける  |
| 弱いマッチャ                                   | 何が無検査で残るかは `forbid-weak-matcher--use-exact-matcher` が見る                    |
| メンバ経路どうしの突き合わせ                   | 同じ経路を書いた 2 つの式は別の束縛に届きうる。被験体の側のメンバ経路は別のルールが見る |

呼び出しの結果を閉じた由来に入れないのは実装の都合ではない。spec が SUT に届く経路はほとんど呼び出しであり、呼び先の名前が spec の外にあることだけを根拠に「閉じている」と読むと、グローバルに注入された SUT を spec の内側と読み違える。構築だけを spec の外の名前で開いてあるのは、そこが唯一「SUT を呼ばずに値を組み立てる」経路だからである。

## なぜそれが要るか

守っている不変条件は「アサーションの結果が SUT の変化で変わること」である。

被験体も期待値も SUT を通っていなければ、そのアサーションはコードを何に変えても同じ結果を出す。落ちうる形をしているだけで、落ちる条件が SUT の側に無い。

この形は書き手の不注意より、他のルールの要求から生まれる。「この `it` には落ちうるアサーションが要る」と報告された書き手が最も安く応じる方法が、`expect(true).toBe(true)` を 1 行足すことである。件数を数える側からは正しいアサーションと区別が付かないので、要求は満たされたことになり、`it` は緑のまま何も検査しない。自分自身との比較も同じ性質を持つ。

近い担当は 2 つあるが、どちらもここを見ない。`no-vacuous-host-object-equality--assert-parsed-value` は比較する値の型を見るので、スカラどうしの比較は対象にならない。`forbid-weak-matcher--use-exact-matcher` はマッチャの綴りを見るので、完全一致マッチャで書かれたこの形は素通りする。数合わせを散文の禁止に残すと、束の中で最も件数を要求するルールがそのまま逃げ道を作る。

## どう直すか

fixture が返す被験体をアサーションする。

```ts
const test = baseTest.extend("stem", () =>
  specStemOf("report.test.ts", DEFAULT_SPEC_FILE_SUFFIXES),
);

test("drops the suffix from the file name", ({ stem }) => {
  expect(stem).toBe("report");
});
```

何を検査したいか決まっていないなら、アサーションを足すのではなく `it` を消す。件数を埋めるために足したアサーションは、足しても件数の意味を戻さない。

自分自身との比較は、期待値を spec に書き下した形に直す。

```ts
const test = baseTest.extend("suffixes", () => specFileSuffixesFrom([]));

test("ships a suffix for each spec file extension", ({ suffixes }) => {
  expect(suffixes).toStrictEqual([".test.ts", ".test.tsx"]);
});
```

## 禁じる回避策

- リテラルをいったん fixture に通して、被験体の由来だけ整える。SUT を呼ばずにリテラルを返す fixture は [no-fixture-construct-in-use--yield-sut-output](no-fixture-construct-in-use--yield-sut-output.md) が落とす
- 期待値の側だけを SUT 由来にして、被験体は spec の中に閉じたままにする。それは落ちうるアサーションなので本ルールは報告しないが、被験体の名前が何も指していない形として [no-expect-forbidden-subject-name--rename-to-concrete-subject](no-expect-forbidden-subject-name--rename-to-concrete-subject.md) の対象に入る
- 被験体を局所束縛に写してから比べる。束縛は連鎖の終端まで辿る
- スプレッドで複製してから比べる。`{ ...subject }` も `[...subject]` も同じ値に届く
- 型アサーション・非 null 表明・括弧で包んで見た目を変える。剥がされる
- `not` を挟む。常に失敗するアサーションになるだけで、SUT と無関係な点は変わらない
- 完全一致マッチャに替えて形を整える。マッチャの綴りは本ルールの入口条件ではない
- 抑制ディレクティブ

## 同じアサーションを見る他のルールとの関係

[no-vacuous-host-object-equality--assert-parsed-value](no-vacuous-host-object-equality--assert-parsed-value.md) とは、spec の中で構築したホストオブジェクトどうしを比べる形で重なる。先に直すべきは被験体が SUT を通っていないことなので、本ルールの報告が残っているうちはそちらを直しても解決しない。両方が発火する構成では、本ルールの報告を先に読む。

`no-expect-synthetic-subject--yield-from-fixture` は被験体が spec の中で組み立てた値であることを、位置だけで見る。本ルールは期待値の側まで見て、両方が閉じているときだけ報告する。被験体がリテラルで期待値が SUT 由来の形は、あちらが報告して本ルールは報告しない。

`no-expect-mirrored-subject--assert-observable-contract` は、fixture が被験体を組み立てた式を期待値に書き写す形を見る。被験体と期待値が同じ束縛に届く形は両方に当たる。直し方は同じ（期待値を外から書く）なので、どちらの報告から読んでも同じところへ着く。

## オプション

`specFileSuffixes` だけを取る。既定は `.test.ts` と `.test.tsx` で、この束のルールが同じ範囲を共有する。

個別のケースを外す設定は置かない。外せる口を 1 つ作れば、そこへ数合わせのアサーションを移すだけで本ルールを通せるようになる。
