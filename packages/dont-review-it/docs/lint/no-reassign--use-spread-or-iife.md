# no-reassign--use-spread-or-iife

## 何を検出するか

代入の形をとる変異をすべて検出する。守っている不変条件は「すべての束縛は単一代入であり、その最終値は宣言箇所で確定している」ことで、名前が指す値を知るために宣言行より後ろを読む必要がない状態を保つ。

判定は構文形状だけで行う。型情報もスコープ解析も使わない。

| 形状                                     | メッセージ                | 例                                                        |
| ---------------------------------------- | ------------------------- | --------------------------------------------------------- |
| 再束縛可能な宣言                         | `reassignableDeclaration` | `let pending = 1;` / `var queued = 2;`                    |
| 既存の識別子束縛への書き込み             | `identifierAssignment`    | `pending = 2;` / `pending += 2;` / `pending ??= 2;`       |
| 識別子束縛の増減                         | `identifierUpdate`        | `pending++;` / `--pending;`                               |
| 既存オブジェクトのプロパティへの書き込み | `propertyAssignment`      | `base.count = 1;` / `items[0] = 3;` / `items.length = 0;` |
| プロパティの増減                         | `propertyUpdate`          | `base.count++;` / `--items[0];`                           |
| プロパティ代入を隠した標準呼び出し       | `mutatingCall`            | `Object.assign(base, patch);`                             |
| プロパティの削除                         | `propertyDeletion`        | `delete base.count;`                                      |
| 宣言を伴わないパターン代入               | `patternAssignment`       | `[first, second] = pair;` / `({ count } = holder);`       |

再束縛可能な宣言は、実際に再代入されているかを問わず報告する。「後で代入する」という意図が宣言の形に出た時点で、宣言箇所は最終値を示していない。

`mutatingCall` が対象とするのは次の 5 つだけで、いずれも計算プロパティを経由しない直接の呼び出しに限る。`Object.assign` / `Object.defineProperty` / `Object.defineProperties` / `Object.setPrototypeOf` / `Reflect.set`。第一引数の内容は検査しないので、その場で作った新規オブジェクトを渡す非破壊的な用途も報告される。第一引数が既存の束縛かどうかを判定するにはスコープ解析か型解析が要り、かつその用途はスプレッドで書けるためである。

`for (entry of entries)` のように、反復構文の頭が宣言ではなく既存の書き込み先である形も、同じ分類で報告する。頭が識別子なら `identifierAssignment`、メンバ式なら `propertyAssignment`、パターンなら `patternAssignment` になる。

型アサーション、`satisfies`、非 null 表明、省略可能連結は透過的に剥がしてから判定する。`(base.count as never) = 1` も `base!.count = 1` も `delete base?.count` も、包んでいない形と同じく報告される。剥がさない実装では、包むだけで検出を外せてしまう。

報告位置は形状ごとに次のとおり。代入と増減は書き込み先そのもの、削除は `delete` 式全体、変更系呼び出しは呼び出し式全体、宣言は宣言文全体。

## 何を検出しないか

例外は閉じた列挙である。ここに載っていない形は違反として扱う。

**宣言時の単一束縛。** `const` 宣言全般（1 文に宣言子が複数ある形を含む）、パターンを使った新規宣言（配列パターン、オブジェクトパターン、rest を伴う形）、`using` / `await using` 宣言、`for (const entry of entries)` や `for (let key in holder)` のように反復ごとに新しい束縛を作る反復構文のループ変数。

`for (var entry of entries)` は例外に含めない。`var` は関数スコープの 1 つの束縛を毎回上書きするだけで、反復ごとに別の束縛が生成されないためである。

**実行時の束縛を持たない宣言。** `declare let pending: number;` のような環境宣言と、`declare module "m" { ... }` の内側の宣言。宣言ファイル（`*.d.ts` / `*.d.mts` / `*.d.cts`）はファイル全体を対象外にする。`namespace Registry { let pending = 1; }` のように `declare` を伴わない名前空間は実行時の束縛を作るので対象に含まれる。

**クラスが自身の状態を初期化・維持するための、直接の `this` / `super` への書き込み。** 唯一の構文的な例外であり、範囲は狭い。

- 書き込み先のルートが**直接** `this` または `super` であるものに限る。`this.a.b = next` のように 1 段でも深いパスは違反
- その `this` を所有する最も近い非アロー関数スコープがクラスメンバであること。コンストラクタを含むメソッド、アクセサ、フィールド初期化子、`accessor` フィールド、static 初期化ブロックが該当する
- アロー関数は自身の `this` を持たないので判定時に透過する。クラスメンバの中に書いたアロー関数は例外に含まれる
- 自前の `this` を持つ通常の関数は、クラス本体の中に書かれていても例外の対象外
- オブジェクトリテラルのメソッド内の `this` と、どの関数にも属さないトップレベルの `this` は対象外
- 代入・複合代入・増減が対象で、削除式（`delete this.x`）は対象外
- パターン代入の内部要素として `this.x` を書いた形（`[this.count] = pair;`）も対象外

この例外は、クラスに状態を持たせる書き方を機械的に通すためのものであって、その代入が正当であることの根拠ではない。

**書き込みでない参照。** プロパティの読み取り、比較、条件式での使用。

**同名だが別の対象への呼び出し。** `helpers.assign(base, patch)`、`globalThis.Object.assign(base, patch)`、`Object["assign"](base, patch)`、`Object.keys(base)` はいずれも `mutatingCall` の対象外である。列挙したグローバル名からの、非計算の直接参照だけを見る。

**プロパティ削除にあたらない削除式。** `delete parse(text)` のようにメンバ式を対象にしていない削除式。

**そもそも評価対象にならない形。** 書き込み先が識別子でもメンバ式でもパターンでもない形。実行時に成立しない構文であり、この不変条件の対象ではない。現行のパーサは `(parse(text) as never) = 1` を構文エラーにするため、この分岐に到達する入力は今のところ存在しない。

## なぜそれが要るか

**読解コストが宣言箇所に閉じる。** 再代入がありうると、ある名前の値を確定するにはスコープ全体を追う必要がある。単一代入を強制すると、宣言行を読んだ時点で値が確定し、以降の行を読まなくてよくなる。効き方はスコープが長いほど大きい。

**未初期化の中間状態が構文上なくなる。** 先に宣言して各分岐で代入する書き方は「まだ値が入っていない状態」を必ず作り、代入し忘れた分岐という失敗の形を許す。分岐を即時実行関数の内側に入れて各経路から return させると、外側から見えるのは確定済みの値だけになり、その失敗の形自体が消える。

**参照の共有が遠隔作用にならない。** オブジェクトを他所に渡した後で中身を書き換えると、渡した先の挙動が呼び出し順に依存する。新しい値を作って渡す形に固定すれば、渡した時点の値が後から変わらない。

**部分的な禁止は必ず抜け道を残す。** これが 8 形状を 1 本のルールに束ねている理由である。再束縛可能な宣言だけを禁じても、`const` で束ねたオブジェクトのプロパティを書き換えれば同じことができる。プロパティ代入だけを禁じても、同じ変更を `Object.assign` という関数呼び出しの形に言い換えれば通る。識別子への代入だけを禁じても、パターン代入の構文で同じ再束縛ができる。いずれも同一の不変条件を破る操作であり、破り方が違うだけである。

## どう直すか

直し方は 2 つの型に集約される。何をしようとしていたかで選ぶ。

1. **既存のオブジェクトを「編集」したかった。** 既存の値を変えずに新しい値を作る。スプレッドで新しいオブジェクトを組み立てる、キーを除くなら rest 分解で残りを取り出す、コレクションなら `map` / `filter` / `reduce` で新しいコレクションを得る
2. **値が後で決まる（分岐・探索・集約・例外処理）。** 即時実行関数の中で決め、各経路から return する。外側からは単一代入の宣言に見える

派生する定型は次のとおり。

| もとの形                   | 置き換え先                                         |
| -------------------------- | -------------------------------------------------- |
| 条件で 2 通りに決まる値    | 条件演算子                                         |
| 多分岐で決まる値           | 即時実行関数の中の分岐から return                  |
| 例外処理で決まる値         | 即時実行関数の中の try / catch から return         |
| 合計・畳み込み             | `reduce`                                           |
| 条件に合う要素の収集       | `filter` / `map`                                   |
| 見つかったら打ち切る探索   | 即時実行関数の中のループから return                |
| インデックスを進めるループ | 反復構文、またはインデックスを受け取る反復メソッド |
| キーを 1 つ取り除く        | rest 分解で残りを取り出す                          |

**特殊だが頻出する形が 2 つある。**

エラーに情報を足したい場合、スプレッドではエラー相当のオブジェクトを組み立て直せない。プロトタイプが失われ、非列挙の `message` も落ちる。変更系 API も使えない。サブクラスを定義し、コンストラクタ引数から読み取り専用のフィールドとして受け取る形にする。既存ライブラリのエラー型を模しているなら、自前のサブクラスより、そのライブラリが公開している実際のエラー型を使うほうがよい。

テストで実オブジェクトのメソッドを差し替えたい場合、変更系 API でオブジェクトを書き換える形は、可変性の回避であると同時に型検査の回避でもある。差し替え先が本来のシグネチャと照合されない。テストフレームワークが提供するスパイ / モック API を使う。実シグネチャに対して型検査され、復元もできる。

**クラスに逃がすことは一般的な直し方ではない。** 構文的な例外があるため、代入をクラスの内側へ移せば報告は止まる。しかし可変状態は消えておらず、置き場所が変わっただけである。報告を止めることだけを目的に導入されたクラスは回避策であり、認めない。

状態を持つ抽象を「管理された可変境界」として扱う整理は次のとおりだが、この方針を運用として採るかは未決である。コールバックやフレームワーク制御下の呼び出しをまたいで状態を保つ必要があり戻り値で次の値を渡せないこと、変更が呼び出し箇所ごとの場当たりなクラスではなく再利用される 1 つの狭い部品に集約されていること、利用側には読み取り専用のインターフェースと不変なスナップショットだけを渡すこと、状態を持つことを名前とドキュメントで明示すること。新しい可変境界を作ることは設計上の判断であり、lint の自動的な修復手段ではない。

## 禁じる回避策

いずれも構文だけを変えて同じ可変性を残すものであり、報告が消えても不変条件は満たされない。

- 変更系 API への言い換え。プロパティ代入を関数呼び出しに置き換えるだけで、意味は同じ
- 変更系 API を別名に束縛してから呼ぶ、または計算プロパティ経由で呼ぶ。構文形状では検出できないが、規約上は違反として扱いレビューで拒否する
- 単一の値だけを入れた可変コレクションをセル代わりに使い、その場で入れ替える。添字で入れ替える形（`cell[0] = next`）は `propertyAssignment` で検出される。単一要素の配列だからといって除外を入れてはならない。連想配列や集合のメソッドで入れ替える形は構文形状で検出できないので、規約上の違反としてレビューで拒否する
- 型アサーションや非 null 表明で書き込み対象を包む。剥がしてから判定するので報告は消えない
- 即時実行関数の内側に再束縛可能な宣言を隠す。スコープが小さくなっても再束縛可能であることは変わらない。即時実行関数はその宣言を消すための道具であって、隠す場所ではない
- 報告を止めることだけを目的としたクラスの導入

## 抑制の扱い

このルールは現時点でいかなる抑制も受理しない。専用の抑制ディレクティブの記法（トークン名、理由の区切り、対象範囲の指定）が未決であり、記法が決まるまで抑制に該当する形は存在しないためである。

違反が構造的に避けられないことは、それ自体では抑制を書いてよい根拠にならない。避けられないことと、抑制してよいことは別である。決まるまでは抑制せず、違反のまま残してレビューに上げる。

代入でしか操作できない外部 API だけは例外で、抑制ではなく `assignOnlyTargets` で扱う。書き手が個別に黙らせるのではなく、書き込み先を名指しした 1 つのリストが全ファイルに効く形にしてある。名指しされていない書き込み先は、避けられなくても報告される。

記法が決まったときに満たす条件は次のとおり。汎用の lint 無効化コメントは受け付けずこのルール専用のディレクティブに限る（汎用の無効化はどのルールを何のために止めたのかが残らず、後から棚卸しできない）。ディレクティブはルール名を明示し、対象は直後の 1 文だけに限定する。理由の記述を必須とし、理由が空のものは無効として違反を報告し続ける。他ルールのディレクティブと連続するコメント行に紛れていても認識できるようにする。

なお、このリポジトリが採用しているリンタの汎用無効化コメントがこのルールに実際に効いてしまうかは未検証である。配線後に確認して、効く場合の対処を決める必要がある。

違反が本質的でない場合（カウンタ、アキュムレータ、局所的な遅延初期化など）は、抑制ではなく前掲の直し方に寄せる。

## no-array-mutation--derive-new-array との分担

代入の形をとる変異は、添字代入（`items[0] = next`）と `length` への代入まで含めて、型を見ないこのルールが担当する。

レシーバ自身を書き換えるメソッド呼び出しはこのルールでは検出しない。取りこぼしではなく分担の線である。レシーバの静的型を見ないと同名の別 API と区別できず、構文形状だけで判定するというこのルールの前提に乗らないためである。配列の破壊的メソッドは、レシーバの静的型が配列的だと判定できる限りにおいて no-array-mutation--derive-new-array が担当する。

どちらの構文検出にも乗らない形が残る。レシーバの型が `any` / `unknown` または型注釈のない値である場合、実行時にしか決まらないキーで呼ぶ場合、`call` / `apply` / `bind` や関数値として受け渡してから呼ぶ場合、非配列型へキャストして隠した場合、そして連想配列や集合の破壊的メソッド。これらは「検出されないが許可ではない」扱いとし、規約上は違反としてレビューで拒否する。

## オプション

`assignOnlyTargets`（文字列の配列、既定は空）だけを取る。代入でしか設定できない外部 API の書き込み先を、配備先が名指しして足す。

```jsonc
["error", { "assignOnlyTargets": ["RuleTester.describe", "RuleTester.it"] }]
```

ルール自身が持つのは `process.exitCode` の 1 つだけで、これは**常に**通る。オプションが名指しするのはそこに足す分であり、置き換えではない。`process.exitCode` を残すために書き並べる必要はないし、書いても消せない。

`process.exitCode` だけをルールに持たせているのは、これが言語処理系の側の事情だからである。プロセスの終了コードを module スコープの入口から返す手段は代入しか無く、`process.exit` は書き込みの完了を待たない。どの配備先で書いても同じ制約がかかる。一方、oxlint の `RuleTester` が `describe` / `it` を static setter でしか受け取らないことは、lint ルールを書く配備先だけの事情である。そちらはオプションで名指しする。

載せる条件は「その API が代入以外の設定手段を持たないこと」であって、「書き換えたい対象であること」ではない。

照合するのは、計算プロパティを経由しない `受け手.プロパティ` の形の完全一致である。`process['exitCode'] = 1` は照合されず報告される。`process.env = {}` も別のプロパティなので報告される。

**検出形状を切り替えるオプションは持たない。** 形状は同一不変条件の別表現なので、形状ごとに切り替えられる設定が存在すると「プロパティ代入は禁止するが、それを関数呼び出しに言い換えた形は許す」という、抜け道が最初から開いた設定を作れてしまう。`assignOnlyTargets` が絞るのは形状ではなく、名指しした書き込み先 1 つずつである。

重大度は設定側で決めるが、全形状で同一にすること。形状間で差をつけると、実質的にオプションを持たせたのと同じになる。ルール自身はファイル種別で対象を絞らない。宣言ファイルだけは、実行時の束縛を持たないという理由で対象外にしてある。テストコードや生成コードを外すかどうかは設定側の `overrides` で決める話であり、ルールには持たせていない。

## 保留にした判断

- `var` をこのルールで検出するかは、他ルールとの二重検出になりうるとして保留されていた。このリポジトリの現行 lint 設定では `var` の宣言も再代入も何も報告されないことを実測で確認したので、二重検出は起きないと判断して検出対象に含めた
- 検出対象とする標準 API の列挙を、リフレクション経由のプロパティ定義・削除・プロトタイプ差し替えといった同等の別経路まで広げるかは未決。現状は 5 つの閉じた列挙のまま
- 抑制ディレクティブの記法、抑制に承認記録を必須とする運用を採るか、汎用無効化コメントが効いてしまうかは、いずれも未決
- 「管理された可変境界」を設計上の例外として文書化する運用を採るか、共有の可変境界部品を用意するかは未決
