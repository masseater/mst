# no-expect-call-expression--yield-from-fixture

## 何を検出するか

spec ファイルの中の、matcher 呼び出しまで到達した expect チェーンについて、`expect(...)` に渡された第一引数を見る。

起点は matcher の呼び出しである。受け手が `expect(...)` の呼び出しに解決できるものだけを見る。間に挟まったメンバー参照は名前を問わず辿る。`not` / `resolves` / `rejects` を列挙して辿ると、列挙外の修飾子を 1 つ挟むだけで検出を外せるためである。`expect.soft(...)` / `expect.poll(...)` も受け手として辿る。`expect.assertions(2)` のような名前空間のユーティリティ呼び出しは、根が `expect` の呼び出しではないので構造的に外れる。

対象のファイルはファイル名の接尾辞で決める。既定は `.test.ts` と `.test.tsx` で、`specFileSuffixes` で差し替えられる。

第一引数は、型アサーション・`satisfies`・非 null アサーション・括弧・オプショナルチェーン・`await` を剥いでから読む。剥いだ結果が次のいずれかであるとき報告する。

| 剥いだ結果           | 例                              |
| -------------------- | ------------------------------- |
| 呼び出し式           | `expect(summarise(input))`      |
| `new` 式             | `expect(new Report(input))`     |
| タグ付きテンプレート | `expect(summarise\`${input}\`)` |

3 つを 1 つの範囲に入れているのは、不変条件から見て同じ違反だからである。subject を `expect` の中で生産している点は共通で、どれか 1 つを外すとその形に包み直すだけで検出を外せる。

もう 1 つ、裸の識別子でありながら「引数を取る関数」として宣言されているものを報告する。宣言が読めるのは、そのファイルの中の `const` / `let` / `function` 宣言に解決したときだけである。判定材料は 2 つで、順に見る。

1. 束縛に書かれた型注釈が関数型であれば、その型の仮引数の個数を見る
2. 型注釈が無ければ、初期化子が関数リテラルであるかを見て、その仮引数の個数を見る

既定値付きの仮引数も残余引数も仮引数として数える。「引数なしのサンク」ではないからである。

この判定は、matcher が呼び出し記録を読むもの（`toHaveBeenCalled` 系）であるときは行わない。それらの matcher は subject を呼ばないため、引数を取る関数を渡しても実行は起きない。テストダブルを fixture から受け取って呼ばれ方を見る形は、この群が指定している直し方そのものであり、そこを塞ぐと直し方が消える。

### 意図的に広げていない範囲

| 形                                   | 対象にしない理由                                                                                     |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| 裸の識別子                           | subject はアサーションの外で生産されている。この不変条件は満たされている                             |
| メンバー式・配列リテラル・条件式など | 根が識別子でない形は `no-expect-projected-subject--use-tostrictequal-on-subject` が引き受ける        |
| オブジェクトリテラル                 | 合成した subject を禁じる別ルールが引き受ける                                                        |
| インラインの関数リテラル             | 呼び出し式ではない。裸の識別子でもないので、上と同じく射影側のルールが落とす。2 本が同じ形に鳴らない |
| import で入ってきた識別子            | 宣言が別ファイルにあり、この実行系では仮引数を読めない。読めないものを違反として扱わない             |
| 仮引数として束縛された識別子         | 同上。fixture から分割代入で受け取った subject がここに入る                                          |
| 初期化子が呼び出しの結果である束縛   | 何が返るかは静的には決まらない。テストダブルのファクトリがここに入る                                 |

最後の 3 つは実装の都合ではなく、静的解析の原理的な限界である。ここに隠せば検出は届かないが、届かないことは許していることを意味しない。禁じる回避策の節に名前を挙げてある。

## なぜそれが要るか

守っている不変条件は「アサーションが受け取る値は、fixture が既に生産して渡した subject である」ことである。

`expect` の中で関数を呼ぶと、given / when / then の when が then の内側に潜る。テストは「この subject はこの性質を持つ」ではなく「この式を実行した結果はこうなる」という手続きの記述に戻る。読み手は、何が subject なのかをアサーションの中から復元しなければならなくなる。

壊れ方はもう 1 層ある。この群の他のルールは、いずれも「fixture が返した subject」を基準に判定している。期待値が subject の構築式の写しになっていないか、subject が根そのものか、呼び出し記録を値として覗いていないか。subject が `expect` の中で生まれると、これらの判定は起点を失う。1 か所で subject の出所を崩すと、他の検査が黙って空振りする。空振りしている位置は報告からは見えない。

したがってこのルールは、他のルールが立っている土台を作っている。緩めた分だけ、緩めた場所ではなく別のルールの検出が減る。

## どう直すか

実行を fixture に移し、返った値を fixture が返す。it はその束縛を検証するだけにする。

```ts
const test = baseTest.extend("stem", () =>
  specStemOf("report.test.ts", DEFAULT_SPEC_FILE_SUFFIXES),
);

test("drops the suffix from the file name", ({ stem }) => {
  expect(stem).toBe("report");
});
```

例外を検証する場合は、fixture が引数なしのサンクを返し、it はそのサンクの識別子を渡す。渡っているのは識別子であって呼び出し式ではないので、この読みでは落ちない。matcher には例外メッセージを完全一致で比べるものを使う。文字列を渡す `toThrow` 系は `forbid-weak-matcher--use-exact-matcher` の置き換え対象である。

サンクは引数を取らないものにする。呼ぶために必要な値は fixture の中で閉じ込める。引数を取る関数を渡すと、その引数ごと実行がアサーションの中に持ち込まれる。

## 禁じる回避策

- 呼び出しを it の先頭の文に出して変数に受ける。この読みからは消えるが、`require-it-only-expect--move-setup-into-fixture` に当たる
- 呼び出しを型アサーション・`satisfies`・非 null アサーション・括弧・`await` で包む。剥がされる
- 呼び出しを `new` 式やタグ付きテンプレートに置き換える。同じ検出範囲に入る
- 引数を束ねた関数を渡して実行を隠す。宣言が読める範囲では落ちる
- サンクの宣言を別ファイルに移す、あるいはファクトリの呼び出し結果として受ける。仮引数が読めなくなるので報告は消えるが、アサーションの中で実行が起きることは変わらない
- 呼び出しを fixture に移したうえで、fixture 側で結果を組み替える・射影する・包む。fixture 側の構築とコピーと射影は別のルールが引き受ける
- 抑制ディレクティブ

## オプション

`specFileSuffixes` だけを取る。既定は `.test.ts` と `.test.tsx` で、この群の 9 本が同じ範囲を共有する。

対象外にする呼び出し先の名前を並べるオプションは置かない。名前を 1 つ載せた時点で、そこへ包むだけでこのルールを通せるようになる。
