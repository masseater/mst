# require-spec-file-for-assets--create-matching-spec

## 何を検出するか

テストデータのファイルに、それを所有する spec が同じディレクトリに実在するかを見る。実在しなければ報告する。

テストデータかどうかはファイル名だけで決まる。ファイル名をドットで区切ったとき、拡張子の 1 つ手前のセグメントが目印の語（既定では `assets`）であり、その手前に語幹が残っていることが条件になる。`order.assets.ts` は該当する。`assets.ts` は語幹が空なので該当しない（テストデータではなく `assets` という名前のモジュールである）。`order.assets.test.ts` も該当しない。拡張子の手前にあるのは `test` であって目印ではないため、これは spec 側の名前として読まれる。目印の後ろに何の拡張子が来るかは判定に入れていない。`order.assets.mts` も `order.assets.json` も同じにテストデータとして扱う。拡張子を差し替えるだけで規約から降りられる形を、判定の側に残さないためである。ただし実際に報告が出るのは linter が構文解析の対象として訪問したファイルに限られる。`.mts` は訪問されるので報告されるが、`.json` は訪問されないため、判定が該当するにもかかわらず報告は出ない。

所有者は「同じディレクトリにある、同じ語幹の spec」ただ 1 つである。語幹は目印より前の部分で、`vite.config.assets.ts` の語幹は `vite.config` になる。探しに行く名前は、語幹に spec の接尾辞を付けたもの全部で、そのどれか 1 つがファイルとして実在すれば所有者がいるとみなす。実在するのがディレクトリだった場合は所有者と認めない。同じ名前のディレクトリを置いて所有者になりすます形を残さないためである。

**存在だけを見る。中身は読まない。** 所有者の spec が空でも、このルールは通す。中身が実行されるテストを持つかどうかは `require-test-block-for-spec-file--add-test-or-delete-file` の担当で、こちらが兼ねると「所有者がいない」と「所有者に中身がない」が 1 本の設定でしか制御できなくなる。名前だけ合わせた空の spec を置く回避は、2 本が揃って初めて塞がる。

報告の位置はファイル全体（Program ノード）になる。ファイルの中に指すべき行が無いためである。

判定は**訪問したファイルごと**に行う。したがって、当該ファイルを解析対象から外せば、このルールは発火しない。JSON のように linter が解析しない形式のテストデータも同じ理由で報告されない。存在関係の検査をリポジトリの木の走査に置いて対象指定から独立させることは、oxlint の JS プラグインが報告位置を「今検査しているファイルの中のノード」に限っているため、ルール単体では実現できない。所有の判定そのものは、訪問したファイルのパスとファイルシステムだけで決まる純粋な関数として書いてある。リポジトリの木を入口にする実行形態を足すときは、その関数をそのまま呼べる。

## なぜそれが要るか

1 層目は、所有者がいないデータは誰も直せないことである。テストデータを書き換えてよいかどうかは「これを読んでいるテストが何を期待しているか」で決まる。読み手が 1 つに定まっていれば、その 1 つを見れば判断できる。読み手が 0 のとき、判断材料が無いのではなく、そもそも判断する理由が無い。値が正しいかどうかを確かめる手段がどこにも無いまま、ファイルだけがリポジトリに残る。

2 層目は、所有者の存在が「読み手は 1 つ」という規律の前提になっていることである。テストデータを所有者以外に読ませない規律は、所有者が実在して初めて意味を持つ。所有者が 0 のファイルは、その規律から見れば「誰の物でもないので誰が読んでも所有者違反にならない」ように見えてしまう。存在を要求する側と、読み手を 1 つに絞る側の両方を機構に載せると、どちらから見ても同じ 1 つの spec が所有者になる。

3 層目は、テストが消えてもデータは消えないことである。テストを削除するとき、そのテストが読んでいた別ファイルまで一緒に消す作業は、消し忘れても何も赤くならない。数回繰り返すと、ディレクトリには「いつ書かれたのか、何を確かめるためのものだったのか、今も正しいのか」がどれも答えられないファイルが積み上がる。所有者の存在を機構が要求していれば、テストを消した瞬間に孤児として現れる。

## どう直すか

そのデータを読んで何かを確かめる spec を書き、ファイル名をデータの語幹に合わせる。データが実際に何かの検証に使われているなら、これが本来あるべき形である。

書けないなら、そのデータは検証に使われていない。値を実際に読んでいる spec があるなら、その spec の中へ値を書き下してテストデータのファイルを消す。読んでいる spec が無いなら、ファイルごと消す。

データが大きすぎて spec の中に置くと読めなくなる、という理由でファイルを分けているなら、分けたまま所有者を書く。ファイルを分けてよい理由は大きさであって、複数の spec で共有したいからではない。

## 禁じる回避策

- 名前だけ合わせた空の spec を置く。存在の検査は通るが、実行されるテストを要求する別のルールが報告する。所有とは「誰かが実際にそのデータを使って確かめている」ことであって、同じ語幹のファイルが並んでいることではない
- 別の語幹の spec に読ませて「使われている」ことにする。読まれていることと所有していることは違う。所有者以外が読む形は、テストデータの読み手を 1 つに絞るルールが報告する
- 同じ語幹の spec を別のディレクトリに置いて所有者だと主張する。所有はディレクトリと語幹の両方で判定する。別ディレクトリの同名 spec は自分のデータを持っているだけで、こちらのデータについては何も知らない
- 拡張子を変えて規約から降りる。目印の後ろの拡張子は判定に入れていないので、`.ts` を `.mts` にしても報告は消えない
- 目印を名前から外して、テストデータではない普通のモジュールに見せる。このルールの対象からは外れるが、外れた先で spec からしか読まれないモジュールになるため、切り出された setup を塞ぐ側のルールが受け止める
- 目印の後ろにもう 1 段セグメントを足して、拡張子の手前から目印をずらす。判定はずれるが、その名前は spec の接尾辞に当たるか、どちらの規約にも当たらない第三の種別になる。前者なら実行されるテストを要求され、後者なら spec 用ディレクトリの中で種別違反として報告される
- `assetsNameMarkers` を空配列にして対象を消す。空配列は既定に戻るので消えない。実在しない語を目印に指定すれば対象は空になるが、それはルールを無効化したのと同じであり、有効にしたまま 1 ファイルを免除したことにはならない

## オプション

- `assetsNameMarkers`（文字列の配列、任意）: テストデータの目印として扱う語。既定は `["assets"]` で、指定すると**置き換える**（加算ではない）。エントリは拡張子の 1 つ手前のセグメントと完全一致で照合する。空配列を渡した場合は既定に戻る
- `specFileSuffixes`（文字列の配列、任意）: 所有者の spec として認識する接尾辞。既定は `[".test.ts", ".test.tsx"]` で、指定すると置き換える。この群の他のルールと同じ名前・同じ意味で、リポジトリ全体で 1 つの綴りに揃える前提で持っている

```jsonc
["error", { "assetsNameMarkers": ["assets"], "specFileSuffixes": [".test.ts"] }]
```

免除リストは持たない。「このファイルだけ所有者がいなくてよい」は、所有者がいないデータが 1 つあってもよいという意味になり、規律そのものと矛盾する。抑制ディレクティブについても同じで、報告が消えたことと所有者ができたことは無関係である。
