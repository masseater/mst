# no-invariant-default-parameter--remove-unused-option

## 何を検出するか

production source のローカル関数がリテラルの既定値を持つ仮引数を宣言していて、その関数の参照がすべて静的な直接呼び出しであり、すべての呼び出しで仮引数の実効値が一つに固定されている状態を検出する。

対象は名前を持つ関数宣言と、識別子に束縛された function expression または arrow function である。既定値と実引数として比較するのは `null`、boolean、有限 number、string のリテラルである。有限 number は符号なしのリテラルに加え、単項 `+` / `-` を直接付けた形も比較する。`-0` は `0` と異なる実効値として扱う。引数の省略と、グローバルの `undefined` を明示した呼び出しは、既定値を渡したものとして数える。

関数が export されている、関数自体が値として別の場所へ渡されている、`call` や `apply` を介している、対象の引数までに spread がある、実引数が動的な式である、のいずれかなら報告しない。ファイルに見えていない呼び出しが値を変える可能性を閉じられないためである。

overload signature を持つ関数実装も報告しない。見えている呼び出しが一つの値しか使っていなくても、signature が宣言する option の契約まで削除してよいとは決められない。

通常の function が仮引数の初期化子または本体から自分の `arguments` を参照する場合も報告しない。仮引数と実引数を削除すると `arguments.length` と `arguments[index]` が変わり、値を本体へ埋め込むだけでは修復できない。arrow function 内の `arguments` は外側の function に属するため、この除外には含めない。

対象の仮引数より前にある仮引数の初期化子が対象を参照する場合も報告しない。仮引数は左から右へ初期化されるため、先行する初期化子が後続の仮引数を読むと、その binding は TDZ にある。値へ置換すると元の `ReferenceError` が消え、実行結果を変える。TypeScript ではこの直接参照自体が type error になる。反対に、後続の初期化子が既に初期化された対象を読む形は報告し、そこにある resolved reference も値へ置換する。

対象 function の内側に unshadowed global `eval(...)` の直接呼び出しがある場合も報告しない。direct eval は仮引数の lexical binding を名前で読めるためである。`eval!`、`eval as typeof eval`、`eval satisfies typeof eval`、`<typeof eval>eval` は emit 時に wrapper が消えるので同じく direct eval として扱う。ローカルに束縛された `eval`、`(0, eval)(...)`、`eval?.(...)` は direct eval ではなく、仮引数環境を名前解決しないので除外しない。

TypeScript の `this` pseudo-parameter は emit されないため、callsite の実引数位置には数えない。

テスト、fixture、story のソースは対象にしない。テスト用 helper の既定値は production API の将来用 option ではなく、各ケースを組み立てるための入力になるためである。

## なぜそれが要るか

仮引数は、呼び出し側が値を選べるという契約を作る。すべての呼び出しが同じ値しか選んでいないなら、その契約に利用者はいない。関数本体を読む側は、値が変わる経路を探し、分岐ごとの挙動を追うが、実際には片方の経路しか到達しない。

既定値はこの状態を見えにくくする。呼び出し側に引数が書かれていないので、検索結果には値が現れず、関数の宣言だけが柔軟性を主張する。option を消して値を本体へ戻すと、実際の呼び出し契約と宣言が一致する。

この判定は参照の閉じた関数だけに限る。export や callback を報告しないのは、別の呼び出し元があるかもしれない状態を「固定」と誤認しないためである。

## どう直すか

残す仮引数の初期化子と関数本体で、対象の仮引数へ解決する参照をすべて報告された実効値へ置き換える。その後で対象の仮引数を削除し、各呼び出しから対応する実引数を削除する。同じ名前の別 binding は置き換えない。

値が本当に変わる契約であるなら、足りないのは異なる値を使う実在の呼び出し元である。将来変わるという見込みだけでは仮引数を残さず、値を選ぶ要件が生じた変更で仮引数を戻す。

自動修正は持たない。通常の修正は仮引数の削除だが、既に別の形で書かれた呼び出し元をこの option に統合するのが正しい場合もあり、選択は一つに定まらない。

## 禁じる回避策

- 同じ値を渡す呼び出しを増やす。呼び出し件数は増えても実効値は一つのままである
- リテラルを定数や条件式へ包んで静的判定から外す。値が変わる経路を作らず、検査の材料だけを隠している
- 関数を export して検査対象から外す。外部契約を増やしても、実在する利用者は増えない
- function を一度別の変数へ代入してから呼ぶ。参照が閉じていることを検査できなくなるだけで、option の利用者は増えない

## 何を検出しないか

- object の property として渡される option。property の alias、spread、destructuring を追うにはファイル内の関数 binding とは別の解析が要る
- export された API。リポジトリの外にある callsite を列挙できない
- env、CLI、manifest、schema から入る設定。値の writer と解決順を所有する機構で検査する必要がある
- リテラル以外の既定値と実引数。式の意味が同じかどうかを構文だけで決めない
- 非有限 number と、数値リテラル以外へ単項演算子を適用した式。静的な有限 scalar として比較できない
- overload signature を持つ関数実装。signature が宣言する option 契約をローカル callsite だけでは削除できない
- 自分の `arguments` を読む通常の function と、direct eval を含む function。引数を消すと関数本体から観測できる実行環境が変わる
- 先行する仮引数の初期化子から参照される後続の仮引数。TDZ にある binding を固定値へ変える修復は元の失敗を保存しない
