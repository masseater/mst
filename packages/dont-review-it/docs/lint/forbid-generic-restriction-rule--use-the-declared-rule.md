# forbid-generic-restriction-rule--use-the-declared-rule

## 何を検出するか

禁止する対象を自分の設定配列から受け取る既製ルールが、有効なまま設定に書かれている状態。

対象のルール名は表が持つ。既定は 8 本で、値はルール本体にある。表の各行は「既製ルールの名前」と「その禁止を受け取るこのパッケージのルール」の 2 つを持ち、受け手の欄が空の行もある。

読む単位はオブジェクトのプロパティ 1 つである。キーの最後の `/` 以降が表の名前と一致し、値が無効と書かれていないものを報告する。`eslint/` や `typescript/` を付けた綴りでも付けない綴りでも同じ 1 行を指す。

判定の単位をプロパティ 1 つにしているため、書かれた場所は問わない。ルートの `vite.config.ts` が持つ `lint.rules` も、その隣の `lint.overrides[].rules` も、設定から切り出された `packages/dont-review-it/src/configs/upstream-rules.ts` の `UPSTREAM_RULES` も、同じ 1 つの形をしている。層を足しても、別のファイルへ切り出しても、報告は同じ場所に出る。

値の読み方は 4 つに分かれる。

- `off` / `allow` / `0` は無効として通す。`[水準, 設定]` の形なら先頭を読み、`LINT_SEVERITY.OFF` のように名前付き定数のメンバーとして書かれていればそのメンバー名を水準として読む
- `error` / `deny` / `warn` / `1` / `2` は有効として報告する。`warn` を通さないのは、報告が出る限り禁止はそこに書かれているからである
- 水準として読めない式（別の場所の束縛、呼び出し、オブジェクト）は報告する。報告を止めるのは「無効と書かれていること」だけである
- 上のどれでもない文字列は読まない。ルール名をキーに持つ表であっても、値が水準の語彙から外れているなら、それはリンタに渡る表ではない

## なぜそれが要るか

1 層目は、既製ルールが禁止を自由文字列 1 本でしか運べないことである。禁止と、その禁止が要る理由と、代わりに何を使うかは別々の情報なのに、構造として持てるのは禁止だけになる。代替が伝わらないので、報告を受けた側が置き換え先をその場で決め、決め方が呼び出しごとに散る。

2 層目は、設定を継承した側が同じキーを書き直すと配列が丸ごと置き換わることである。上流で宣言済みの禁止は黙って消え、消えたこと自体はどこにも報告されない。禁止が 1 本減った設定と、もともと禁止が無い設定は、出力の上で同じ形をしている。

3 層目は、禁止の所在が 1 箇所であることが他の検査の前提になっていることである。このパッケージは禁止を各ルールの表へ外出しし、その表を入力として突き合わせる検査を持つ。既製ルールの配列はその入力に入らないので、禁止が 2 箇所に分かれた時点で、突き合わせが「全部の禁止を見ている」と言えなくなる。前提が崩れたことは、検査の緑と区別が付かない。

近さの問題でもある。既製ルールの配列に 1 行足す操作は、専用ルールの表にエントリを足す操作より短い。短いほうが選ばれるので、遠いほうを規範で守らせるのではなく、近いほうを閉じる。

## どう直すか

既製ルールの配列に書かれた禁止を、表が名指しするルールのエントリへ移す。移すときに代替の指示文を書く。既製ルールでは書けなかった情報であり、これを書かずに移すと、次に報告を受けた人が置き換え先をもう一度決めることになる。移し終えたら、既製ルール側の記述を消す。無効にして残すのではなく消す。

移し先は、報告が名指しする 1 本とは限らない。既製ルールが 1 本で 2 つの単位を禁じられる場合があり、`no-restricted-imports` がそれにあたる。モジュールを丸ごと禁じていた行はモジュール単位の受け手へ、そのモジュールの特定の名前だけを禁じていた行は export 単位の受け手へ移す。報告が名指しするのは、そのルールが主に禁じている単位のほうである。

受け手の欄が空の行に当たった場合は、そのルールを書く。何を拒み、どう直すかを名前が言うルールを 1 本作れば、禁止の所在は 1 箇所に戻る。

どちらも取れない場合に限り、`exceptions` に登録する。登録には理由が要る。何がその禁止をこのパッケージのルールで表現できないものにしているのかを書く。理由の無い登録は報告される。

## 禁じる回避策

- 既製ルールを別の名前で登録し直して通す。プラグイン名を替えただけの綴りは最後の `/` 以降で照合するので通らない。上流のルールの実装を別名で再公開した場合は設定からは見分けが付かないが、それは禁止の所在を隠す操作であり、許されているわけではない
- 設定を分割し、検査対象でないファイルに有効化を書く。判定の単位はプロパティ 1 つなので、切り出した先でも同じ形が読まれる
- 水準を設定ファイルの外の束縛へ逃がし、読めなくして通す。読めない式は無効と書かれていないものとして報告される
- 表から行を外して通す。外した瞬間、その既製ルールに書かれた禁止は誰にも突き合わされなくなる
- `exceptions` の理由欄に内容の無い文字列を書き、形式だけ整える。空白だけの理由は報告されるが、それらしく見える無内容な文字列は機械では見分けられない

## 検出が届かない範囲

リンタの起動引数で与えた水準、エディタの設定、CI の個別ステップで足した指定は、リポジトリのファイルに現れないため読めない。上流のルール実装を別名で再公開した場合も、設定の側からは別のルールに見える。

`exceptions` に登録されたまま、対応する記述がどこにも無くなった行は、この検査では報告できない。報告する場所が無いためである。死んだ登録行の棚卸しは、各表の行とその行を消費する検査の対象範囲を突き合わせる検査が受け持つ。

## オプション

- `restrictionRules`（`{ rule, substitute }` の配列、任意）: 禁止を設定配列から受け取る既製ルールの表。ここに書いた行は既定の 8 行に**足される**。置き換えではない。既定を消す操作が設定 1 行で書け、その結果が「何も報告されない」という形でしか現れることを避けるためである。`substitute` を書かない行は、受け手が無い行として扱われる
- `exceptions`（`{ rule, reason }` の配列、任意）: 有効なまま置くことを認める既製ルールと、その理由。既定は空。`reason` が空、または空白だけの行は報告される

```jsonc
[
  "error",
  {
    "exceptions": [
      { "rule": "no-restricted-syntax", "reason": "この形を名指しするルールをまだ書いていない" },
    ],
  },
]
```

既定の表を丸ごと差し替える口は持たない。差し替えられると、このパッケージが持つ既定の禁止がどれだけ消えたかを、消えた側から読む手段が無くなる。
