# no-cross-spec-assets-import--use-own-assets

## 何を検出するか

リポジトリ内のファイルが、自分の持ち物ではないテストデータファイルへ結合していることを検出する。

テストデータファイルかどうかは名前で決まる。`<ステム>.<マーカー>.<拡張子>` の形で、マーカーが既定では `assets` のものが該当する。拡張子が何であるかは問わないので、`order.assets.ts` も `order.assets.json` も同じ扱いになる。ステムにドットが含まれていてもよい（`vite.config.assets.ts` のステムは `vite.config`）。

持ち主は 1 つだけである。**同じディレクトリにあり、同じステムを持つ spec ファイル**がそれで、`order.assets.ts` の持ち主は隣の `order.test.ts` になる。別ディレクトリにある同じステムの spec は持ち主ではない。この定義は `require-spec-file-for-assets--create-matching-spec` と共有していて、あちらが「持ち主が必ず 1 人いること」を、こちらが「持ち主以外は読まないこと」を受け持つ。

読み手は spec に限らない。production のモジュール、スクリプト、ツールの設定ファイル、どこから結合しても報告する。守っている不変条件は「持ち主以外が読まない」であって「他の spec が読まない」ではないため、読み手の種類で判定を変えない。

### 結合とみなす書き方

- `import` 宣言。束縛を伴わない副作用 import も含む
- 名前付き再輸出（`export ... from`）と全再輸出（`export * from`）
- 型だけの `import` / `export`。値を運ばなくても、そのファイルの形へ結び付いていることは変わらない
- モジュール指定子が実行前に決まる動的 `import` と `require`。指定子がリテラル、同一ファイル内の `const` に束縛された文字列、静的な部分だけで組み立てたテンプレートリテラルのいずれかであれば、`import` 宣言と同じに扱う

報告の位置は、その結合を書いている文または式そのものになる。

### 指定子をどう解決するか

判定は指定子の綴りではなく解決先で行う。相対指定子だけを見ていると、別名を 1 枚かぶせるだけで持ち主の外にあるデータを読めてしまうためである。

- 相対指定子。拡張子が無い形、`index` を省いた形、ビルド後の拡張子（`.js` / `.mjs` / `.cjs`）で綴った形も、実在するファイルへ解決する
- パッケージ指定子。読み手の位置から上へ `node_modules` を辿ってワークスペース内のパッケージへ解決する。`exports` が宣言したサブパスも、宣言を通らない深いパスも、どちらも辿る
- tsconfig の `paths`。読み手に最も近い `tsconfig.json` を読み、そこに宣言が無ければ相対指定子で `extends` した先を辿る。ワイルドカードを持つ宣言が複数一致した場合は、前方の一致が最も長いものを採る

解決先が中継ファイルだった場合は、そのファイルが再輸出している先を辿り、行き着いた先がテストデータファイルなら報告する。中継が何枚あっても辿る。

## なぜそれが要るか

読み手が 1 つだけなら、その spec は自分のテストデータを自由に作り替えられる。値を足しても、形を変えても、影響が及ぶ先はそのファイル自身の中で閉じている。

2 つ目の読み手ができた瞬間、その性質が失われる。片方の都合でデータを直すと、もう片方の期待値が黙って変わる。変わったことは編集した側からは見えず、壊れたことに気付くのは無関係なテストが落ちたときになる。結果として、持ち主だったはずの spec も、他のテストを確認しない限り自分のデータへ触れなくなる。共有された setup が持ち込む問題がそのまま入ってくるということであり、「データだけだから」はその問題を免除しない。

テストデータを spec の外に置いてよいとした理由は、大きな静的データを spec 本文に置くと契約が読めなくなるからであって、複数のテストで使い回すためではない。このルールは、置き場所を外に出すことと共有することを切り離す。

読み手を spec に限らないのも同じ理由からで、production のモジュールがテストデータを読んでいれば、そのデータはもう「テストのために自由に書き換えてよい値」ではなくなっている。

## どう直す

自分のステムのテストデータファイルを作り、必要な値をそこに書く。データがテスト間で重複することは、この群では正しい状態であって削減の対象ではない。値が小さいなら、ファイルを作らずに spec の中へ直接書く。

読み手が spec ではないなら、その値は production の値である。テストデータの側から取り出し、production のモジュールとして持ち主を決めて、そこから読む。

中継ファイルを経由して報告された場合、直す場所は 2 つある。中継ファイル自身も持ち主ではない読み手として報告されているので、中継を消し、各読み手が自分のデータを持つ形にする。

## 禁じる回避策

- 共有のテストデータファイルを作り、複数の spec から読む。読み手の数を数えているのではなく、持ち主以外が読んでいることを見ている
- 動的 `import` や `require` へ書き換える。指定子が実行前に決まる限り、同じ結合として報告される
- 別ステムのテストデータを再輸出する中継ファイルを置く。中継は何枚でも辿る
- パス別名やパッケージ指定子を経由して読む。判定は指定子の綴りではなく解決先で行う
- 同じステムのテストデータファイルを別ディレクトリに置き、自分の持ち物だと主張する。持ち主はディレクトリとステムの両方で決まる
- 読み手が spec ではないから対象外だと考える。読み手の種類は問わない
- 抑制ディレクティブで黙らせる

指定子が実行時にしか決まらない動的 `import`（変数や実行時に組み立てた文字列を渡す形）は報告できない。どのファイルへ結合するかが実行時の値でしか決まらず、静的解析では結合先が確定しないためである。検出できないことは、その書き方が許されていることを意味しない。

## 検出が届かない範囲

- 中継として辿るのは再輸出だけである。テストデータを `import` して別の名前で宣言し直すファイルは、それ自身が持ち主ではない読み手として報告されるので、その位置で止まる。読み手を遡って報告することはしない
- パッケージの `exports` がワイルドカードで宣言したサブパス（`"./data/*"` の形）を経由した指定子は、どのファイルへ行き着くかを展開しないため辿れない。ワイルドカードを持たないサブパスと、宣言を通らない深いパスは辿る
- インストール済みパッケージの解決は実際のパス（シンボリックリンクの解決先）で行う。リポジトリ自体がシンボリックリンクの下に置かれている場合、パッケージ指定子経由の結合は辿れない
- `#` で始まるサブパス import は解決しない

## オプション

- `assetsNameMarkers`（文字列の配列、任意）: テストデータファイルの名前が持つマーカー。既定は `assets` で、指定した場合は**置き換え**になる。`require-spec-file-for-assets--create-matching-spec` と `require-test-assets-constants--move-setup-to-spec` が同じ語彙を読むので、3 つには同じ値を渡す
- `specFileSuffixes`（文字列の配列、任意）: spec ファイルの接尾辞。既定は `.test.ts` と `.test.tsx` で、指定した場合は置き換えになる。持ち主が誰かと、報告文をどちらの形で出すかがこの語彙で決まる

```jsonc
["error", { "assetsNameMarkers": ["assets"], "specFileSuffixes": [".spec.ts"] }]
```

持ち主以外の読み手を個別に許す設定は持たない。例外を設定で書けるようにすると、報告を受けた側が自分のデータを作る代わりに例外を足す経路ができ、共有されたテストデータがそこから戻ってくる。
