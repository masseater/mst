# forbid-expectless-it--assert-or-delete-it

## 何を検出するか

テストブロック 1 つの本体に書かれたアサーションが 0 本であること。

アサーション 1 本は「matcher の呼び出しまで到達した `expect` チェーン 1 つ」である。数え方は上限側の `forbid-multi-expect-it--split-into-separate-it` と同じ判定（`lib/spec-syntax/assertion-entries.ts`）を共有する。`not` / `resolves` / `rejects` を挟んでいても 1 本、`expect.soft(...)` / `expect.poll(...)` から始まるチェーンも 1 本。`expect.assertions(...)` / `expect.hasAssertions()` のような `expect` 名前空間のユーティリティ呼び出しは、何も主張しないので 0 本のままである。

数えるのは**直接本数**、つまりブロックのコールバック本体の中に書かれた分だけである。上限側が到達本数（呼び先と fixture の分を足したもの）で見るのに対して、下限側は直接本数で見る。ヘルパや fixture に置いた `expect` は、そのブロック自身が何も主張していない状態を変えないためである。ブロック本体の中の無名コールバック（配列の反復など）に書かれた分は、最も内側のブロックが同じブロックなので直接本数に入る。

テストブロックの判定は共有の起点判定（`lib/spec-syntax/test-block-declarations.ts`）に従う。名前が文字列またはテンプレートで書かれていて、末尾にコールバックが渡されていて、呼び出し連鎖の根がブロックの綴りに解決される呼び出しが対象になる。`it.skip` / `it.todo` / `it.fails` / `it.each(rows)(...)` のような修飾形も、別名で import した束縛も、fixture ビルダから派生した束縛も同じブロックとして扱う。修飾の一覧はこのルールが持たない。

実行が抑制される修飾が付いていても違反である。抑制は「その主張を今は流さない」であって「主張が無くてよい」ではない。

報告位置はブロックの宣言そのものである。落ちる行が無いので、指し示せるのは名前を名乗っている宣言だけである。

### 意図的に広げていない範囲

| 形                                                                 | 対象にしない理由                                                                                                        |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| 直接本数が 1 本以上のブロック                                      | 下限だけを見る。何本まで許すかは `forbid-multi-expect-it--split-into-separate-it` が持つ                                |
| コールバックを渡していない宣言（`it("name")` / `it.todo("name")`） | 共有の起点判定ではテストブロックにならない。ランナーはこれを todo として報告するので、green を作らない                  |
| 名前を文字列で書いていない宣言（`it(() => {})`）                   | 同じく共有の起点判定でテストブロックにならない                                                                          |
| グルーピングブロック（`describe`）の本体                           | テストブロックではない。テストブロックが 1 つも無い仕様ファイルは別のルールが見る                                       |
| fixture ファクトリの本体                                           | テストブロックの宣言ではないので構造的に外れる                                                                          |
| 実行時に決まる matcher（`expect(subject)[chosen](expected)`）      | matcher には到達しているので 1 本と数える。上限側と同じ数え方を保つためで、この形自体は `require-it-only-expect` が見る |
| 仕様ファイル以外                                                   | `specFileSuffixes` が拾う拡張子の外は見ない                                                                             |

## なぜそれが要るか

守っている不変条件は「green の意味は、書かれた主張が通ったことである」ことである。

1 層目は、そのブロックが落ちる条件を持たないことである。本体が空のブロック、コメントだけのブロック、アサーション本数の宣言だけのブロックは、実行しても失敗しうる箇所が無い。実装をどう壊しても green のままなので、回帰を検出する能力はゼロである。

2 層目は、レポートが読み手に与える情報が実態と食い違うことである。ブロックの名前はレポートに並ぶので、読み手は「その振る舞いは検証されている」と読む。名前だけが振る舞いを主張していて、コードは何も主張していない。弱い matcher は少なくとも一部を検証しているが、この形は何も検証していないので、green の意味からより遠い。

3 層目は、この形の生まれ方である。実装を消したときにアサーションだけ消してブロックを残す、書きかけのブロックを名前だけ置いて埋め忘れる。どちらも差分としては数行で、レビューでは「ブロックが 1 つ増えた／減っていない」としか見えない。人間の注意で防ぐ前提を置けないので、機械で止める。

そして、この束の他の 2 本はこの形を素通りする。上限側は「多すぎる」しか見ず、本体の形を見るルールは「expect 以外の文がある」しか見ない。本体が空なら、どちらの条件にも当たらない。下限は別の 1 本が持つ必要がある。

このリポジトリの仕様ファイル 175 本に対してこのルールを走らせると、報告は 0 件だった。既存のテストを直させるためのルールではなく、これから入る空のブロックを止めるためのルールである。

## どう直すか

二つに一つである。

そのブロックが名乗っている振る舞いについて主張を書く。fixture が subject を返し、その subject を 1 本の完全一致で固定する。何を主張すべきかがその場で決まらないなら、ブロックを消す。名前だけのブロックは仕様の穴を「検証済み」に見せるので、無いほうが状態として正確である。消したことは差分に残るので、後から書き直す判断もできる。

「とりあえず何か書いて通す」は直し方ではない。リテラル同士の比較のような自明なアサーションで埋めると `no-expect-projected-subject--use-tostrictequal-on-subject` に当たる。埋める先が思いつかない状態は、そのブロックが何を名乗るべきか決まっていない状態である。

## 禁じる回避策

- **アサーション本数の宣言（`expect.assertions(1)` / `expect.hasAssertions()`）だけを置いて数を満たす。** 何も主張していないので数えない
- **自明なアサーション（リテラル同士の比較など）で埋める。** subject が裸の識別子でないので `no-expect-projected-subject--use-tostrictequal-on-subject` が落とす
- **検証をヘルパや fixture に移してブロックを空にする。** 直接本数で見るので下限は満たされない。加えて、ブロック本体に置いたヘルパ呼び出しは `require-it-only-expect--move-setup-into-fixture` に当たる
- **消す代わりに `it.skip` / `it.todo` / `it.fails` を付けて残す。** 抑制されていても違反として扱う。抑制はレポートから名前を消さない
- **下限を設定で下げる。** 下限は 1 に固定してあり、オプションにしていない。0 を選べるようにすると、設定を書き換えるだけでこのルールが無効になる
- **抑制ディレクティブ**

## オプション

- `specFileSuffixes`: 仕様ファイルとして扱う拡張子。この束のルールで同じ値を使う

下限は 1 に固定でオプションを持たない。上限も持たない。上限は `forbid-multi-expect-it--split-into-separate-it` が到達本数で見る側で持ち、下限はこのルールが直接本数で見る側で持つ。2 本が別々の数え方を 1 つのルールに同居させると、同じブロックについて下限と上限で本数が食い違う。
