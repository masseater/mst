# no-broad-lint-disable--use-next-line-with-reason

## 何を検出するか

コメントの中身の先頭トークンが、広い抑制を意味するディレクティブであるもの。行コメントもブロックコメントも対象になる。

対象は次の 4 つ。

| 綴り                                          | 掛かる範囲                                         |
| --------------------------------------------- | -------------------------------------------------- |
| `eslint-disable` / `oxlint-disable`           | 対応する再有効化まで。無ければファイルの終わりまで |
| `eslint-disable-line` / `oxlint-disable-line` | そのコメントが書かれた行の全体                     |

判定は先頭トークンの完全一致で行う。コメントの中身を trim し、最初の空白までを取り、上の 4 つと一致するかを見る。

- 中身が空白だけのコメントは先頭トークンを持たないので、ディレクティブではない
- ディレクティブ名の直後に改行が入り、対象ルール名が次の行に書かれている形も、先頭トークンは変わらないので検出される
- 散文の途中に綴りが現れるだけのもの（`// this repository never writes eslint-disable` など）は、先頭トークンが一致しないので対象にならない
- `eslint-disable-next-line` / `oxlint-disable-next-line` は完全一致しないので対象にならない。前方一致で判定していないため、`-next-line` が `-disable` に引っかかることはない

`eslint-enable` / `oxlint-enable` は、それ自体が抑制を開くものではないので報告しない。無効化と再有効化を対にして範囲を囲んだ形は、対の先頭にある無効化の側で報告される。

報告位置はコメント自体。報告メッセージには、実際に使われていたディレクティブの綴りと、それに対応する次行専用の綴りが入る。どれが引っかかり、何に置き換えればよいかが出力だけで分かる。

## なぜそれが要るか

広い範囲を無効化する抑制は、「この違反 1 つを抑制したかった」を「不定の範囲を恒久的に免除した」に変える。抑制を書いた人はその 1 行のことしか考えていないのに、範囲が開いている間に足されたコードは、誰にも意識されないまま免除の中に入る。

引き継いだことは何も検出しない。lint は通り、テストは落ちず、レビューでも「抑制コメントがある」以上のことは分からない。ルールをどれだけ書いても、この形の抑制コメント 1 行で骨抜きになる。抑制の作法自体を縛らない限り、lint による強制が「効いている」状態は保てない。

## どう直すか

次の 1 行だけに掛かる形へ切り替える。抑制するルールを名指しし、`--` の後になぜその行で抑制が成立するのかを書く。

```ts
// oxlint-disable-next-line no-console -- CLI はここに結果を書き出す
console.log(result);
```

抑制が、違反を出したその 1 行だけに掛かる状態になる。範囲が閉じているので、後から書かれたコードが免除に入ることはない。理由が隣にあるので、後で読む人がその抑制を残すか消すかを判断できる。

## 禁じる回避策

- **無効化と再有効化を対にして範囲を囲む。** 範囲が閉じられていても、開いている間に足されたコードが免除に入る事実は変わらない。違反行ごとに 1 つずつ抑制を書く
- **抑制コメントが多すぎると感じて範囲を広げる。** 抑制の数が多いのは元のコードの側の問題であって、抑制の書き方の問題ではない。広げるのではなく元のコードを直す
- **`-line` の形に理由を添えて通そうとする。** 理由の有無で判定は変わらない。掛かる範囲が違反行に絞られていないことが問題である
- **コメントをやめて lint 設定側で範囲ごと無効化する。** glob でファイルやディレクトリを指定して強制度を落とせば、コメントは消えるが免除の範囲はむしろ広がる。設定側で落とすのは、なぜ落としているのかと、いつ戻すのかを設定ファイルに残せる場合に限る

## オプション

取らない。有効か無効かだけを設定側で決める。
