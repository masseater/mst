# @mst/lint-rule-authoring

## このパッケージが守るもの

lint による強制が、書かれた時点でも、時間が経った後でも、実際に効いている。

採用者は「このリポジトリで独自の lint ルールを書く人」である。ルールを 1 本も書かない利用者にも、抑制の作法を強制するルールは効く。逆にルールを書く人向けのルールは、ルールが 1 本も無ければ違反が発生しないので空振りするだけで害がない。だから採否を分けず、全部入りの config を 1 つだけ出す。

## 全体を貫く不変条件

- **ルールの出所が ID から一意に決まる。** oxlint プラグイン名をパッケージ名（スコープなし）にする。ID は長くなるが、短縮して出所が消えるコストの方が高い
- **ルールと、その説明と、その検証が離れない。** 1 本のルールについて実装・テスト・文書の 3 点が揃って初めて 1 単位になる
- **説明の権威が 1 箇所にある。** ルールの散文は `docs/lint/` の文書ファイルだけが持つ。ルールのメタデータが持つのは、機械が索引や見出しを組み立てるために要る最小限の項目だけ
- **抑制の口が塞がれている。** 広い範囲を一括で無効化するコメント 1 行でルールが骨抜きになる状態を作らない

## 提供するもの

| 入口                              | 中身                                                               |
| --------------------------------- | ------------------------------------------------------------------ |
| `@mst/lint-rule-authoring`        | factory・severity 語彙・テスト基盤・このパッケージの oxlint config |
| `@mst/lint-rule-authoring/plugin` | oxlint が `jsPlugins` の指定子で読むエントリ                       |

## ルールの書き方

ルール定義は factory を通す。ワークスペースごとの別名は関数ではなくファイルで持ち、各ワークスペースは自分のパスを渡した呼び出し結果を `src/create-rule.ts` から 1 つ named export する。

factory はちょうど 1 つである。同じ変換を別名で 2 つ export すると、どちらを使うべきかが設計上の曖昧さになる。

変換関数が足すものは 2 つ。

- `meta.docs.url` に、そのルールの文書の完全 URL
- すべての報告メッセージ本文の末尾に、リポジトリ相対の文書パス

文書の在り処はワークスペースの位置とルール名から機械的に決まる。ルールの作者がパスを書くことはない。

ルール定義が持つメタデータは、1 行の説明文と、根拠になっている規範文書の一覧だけにする。詳しい例示や判断の背景は文書ファイルだけが持つ。両方に持たせると、メタデータと文書が別々に古くなる。

## 強制度

自前ルールは既定でエラーにする。警告で出すと、警告が積み上がったまま誰も直さない状態になり、「効いている」が崩れる。例外的に警告へ落とす場合は、なぜ落としているのかと、いつ戻すのかを設定ファイル側に残す。

## テストの置き場

テストは対象と同じディレクトリに、対象と同じ名前で、`.test.ts` として置く。`tests/` や `-spec/` のような隔離ディレクトリを作らない。

ルールのテストは、通るべきコード片と落ちるべきコード片の 2 系統を持つ。通るべき側には、そのルールが誤検知しやすい境界を明示的に置く。落ちるべき側には期待する報告メッセージ ID を添える。コード片には名前を付ける。

## 設定ファイル

lint 設定はルートの `vite.config.ts` の `lint` ブロックに集約する。`oxlint.config.ts` / `.oxlintrc.json` / `.oxfmtrc.json` / `vitest.config.ts` は作らない。

## コメント

実装の根拠をコードコメントに書かない。なぜそうしたか、何を検討して採らなかったかはコミットメッセージの本文に残す。
